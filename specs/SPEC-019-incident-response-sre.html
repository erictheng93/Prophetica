SPEC-019 Incident Response & SRE

優先序：P1（可作為 P0 啟動條件的基礎能力）

版本：v0.1.1

更新日：2026-05-28

依賴：SPEC-002, SPEC-007, SPEC-008, SPEC-013, SPEC-017, SPEC-024

1. 目的

建立「事件管理」的產品行為標準，讓用戶在系統異常時可以清楚知道服務狀況、預計恢復時間、補償與風險處理方式，並確保事故後有可追溯的 SRE 記錄與回顧。

2. 產品可見行為範圍

  • 平台不可用、下單受阻、行情延遲、充值/提現暫停、客服系統不可用、風險預警升級。
  • 對外通報包括：公開事故頁、應用內公告橫幅、客服頁更新、必要時短信/Email（依合規流程）。
  • 事故影響只限在事件範圍內，不以猜測性文案宣稱所有模組均異常。

3. 事故分級（S0~S3）

等級 判定條件 可見回應
S0 全域無法下單、帳戶不可登入、風險/支付核心全域中斷 立即上線事故公告；啟用戰情頁；指定回復時間點預估
S1 核心交易或金流受阻，影響高於 10% 的活躍用戶 24/7 升級處理；持續更新進度；明確列出已受影響功能
S2 單一模組退化（例如某市場結算/行情） 明確列出退化範圍與修復預估，非所有服務同時列為故障
S3 低風險輕微異常，可有延遲但可正常交易 在客服系統與內部通報即可，必要時短訊息通告

4. 事故生命周期（面向用戶）

  1. 偵測：監控告警或工單觸發。
  2. 評估：5 分鐘內定義事故等級與受影響服務邊界。
  3. 宣告：公告頁至少顯示 5 個欄位（狀態、影響範圍、預估恢復、回歸窗口、最後更新時間）。
  4. 修復：每 30 分鐘更新一次一次狀態（S1/S0 每 15 分鐘）。
  5. 恢復：恢復生效後立即廣播「部分/全部恢復」，並保留 24 小時追蹤窗。
  6. 回顧：72 小時內完成復盤摘要，對外摘要不必立即公開全部技術細節。

5. 用戶體驗要求

  • 任何 S1 或 S0 事故，必須顯示「影響服務清單」與「暫停/降級項目」。
  • 任何公告應清楚寫明「目前仍可進行的操作」與「暫時停用的操作」。
  • 事故結束後，若事件造成已完成訂單可重放或資料延遲，需在公告頁補充說明。
  • 事故通知文案預設用繁體中文與簡短英文摘要。
  • 客服工單在事故期間可直接掛接事故編號，避免用戶重複回報。

6. 外部溝通與帳務處理邊界

  • 不在事故期承諾金額承擔，僅公告技術恢復進度與可能影響。
  • 涉及充值、交易、佣金或審計的異常，需先通過「事故影響評估」後再決定補償/人工處理。
  • 客服只能提供流程說明，不得在事件未完成前做主觀猜測。
  • 若事故持續超過 2 小時，啟用主管級公告人員與法務/合規同步回報。

9. 服務特定 Runbook

9.1 redemption-expiry-sweeper 停擺

SPEC-024 §3.2 / §7 expiry sweep binary redemption-expiry-sweeper（services/_binaries/redemption-expiry-sweeper）負責每 5 分鐘掃 redemption_orders WHERE state='committed' AND expires_at < NOW()，呼叫 RedemptionService::expire_order 寫 entitlement_expiry ledger 與 advance 訂單 + entitlement 狀態 為 expired，並把對應銅幣由 Liability.UnredeemedEntitlement.{user_id} 結轉為 Revenue.EntitlementBreakage。

面向內容
事故分級 S3（latent；無玩家可見影響）。理由：sweeper 停擺只延遲「未消費過期 entitlement → breakage 收入認列」與「order 狀態轉 expired」之背景流程；玩家錢包 / 庫存 / 在用 entitlement 一律不受影響，前端 UI 仍正確顯示「已過期但未結轉」 的條目（依 entitlement 之 expires_at）。資金不變、 INV-2 / INV-3 / INV-4 / INV-6 / INV-7 全部保持 invariant； breakage 收入認列僅延遲，不漏不溢。
偵測 SPEC-007 §6.4 budget 之上加 redemption_expiry_sweep_lag_seconds (gauge) — 當前時間與最舊 state='committed' AND expires_at < NOW() row 的 expires_at 差距。> 30 分鐘觸發 S3 告警；> 24 小時升 S2（財報 breakage 認列窗口可能跨期延誤）。
初步處置 (1) 確認 binary 是否在運行；若 down，systemctl restart / k8s rollout restart 即可。binary 是 cron-loop，啟動後第一次 pass 會清掉所有積壓（受 REDEMPTION_EXPIRY_BATCH_SIZE batch 上限保護）。 (2) 若 binary 在運行但 lag 仍上升，檢查 PG redemption_orders 表是否異常龐大、index idx_orders_committed_expires 是否被 drop / disabled。 (3) 不動玩家錢包 / 不發補償公告 — 見「外部溝通」。
緊急 oneshot 設 REDEMPTION_EXPIRY_ONESHOT=1 跑單發版本（k8s Job / cron 一次性 trigger），與 cron-loop 並行安全（兩者都用 ledger_idempotency_key_for_expiry(order_id) 去重）。 可作為 cron-loop 修復前的人工降載方式。
外部溝通 不對玩家公告。本 runbook 之事故對玩家完全 invisible（錢包正確、UI 正確、可繼續兌換）。對內部財務 ping 一聲告知本日 / 本週 breakage 收入認列延遲，並提供預期補認列 時間（= sweeper 恢復 + 一輪 pass）。
事故結束條件 redemption_expiry_sweep_lag_seconds 連續 3 個 sample 回到 ≤ 10 分鐘； SELECT COUNT(*) FROM redemption_orders WHERE state='committed' AND expires_at < NOW() ≤ 一輪 batch size（預設 500）。
RCA 重點 binary 為單點 — 是否該升級為 multi-replica（k8s leader election / advisory lock）？目前判斷：lag 容忍度寬（24h 內無實質影響）， single-replica 簡單可靠，待真有重大 lag 事件再評估。

8. 可驗收（產品）

  • [ ] S0/S1 事故在 5 分鐘內完成等級判定並公告。
  • [ ] 事故公告含完整影響範圍與更新時間。
  • [ ] S1/S0 事故更新間隔符合 15~30 分鐘。
  • [ ] 72 小時內完成事故回顧摘要與責任歸檔。
  • [ ] 事故結束後，客服與公告內容一致且可由工單追溯。
