1. Objective

在每次互動式帳號登入成功或失敗時，系統必須記錄登入事件，包含來源 IP、根據 IP 推估的登入地點、User-Agent 解析出的登入裝置，以及必要的安全風險訊號。此資料用於帳號安全稽核、客服排查、事故追查、未來異常登入偵測、MFA step-up 與登入通知。

本 SPEC 的登入主體包含一般玩家 user、管理員 admin、營運 / 客服主管 manager、代理 affiliate，以及未來新增的任何可互動登入後台或前台的帳號類型。服務對服務憑證、cron job 與機器帳號不屬於本 SPEC；它們應走服務憑證稽核或操作留痕。

本功能不得宣稱取得精準 GPS 位置。登入地點僅能以「根據 IP 推估」方式呈現，並需保留資料來源與可信度欄位。

工程實作計畫：SPEC-022-login-event-intelligence-implementation-plan.html

2. Scope

2.1 In Scope

  • 登入成功時寫入 login event。
  • 登入失敗時寫入 login failure event；若可識別登入主體，需關聯 principal_type 與 principal_id。
  • 所有互動式登入主體都必須覆蓋：user、admin、manager、affiliate。
  • 從可信 proxy header 或 remote address 取得 client IP。
  • 根據 IP 推估國家、城市、區域、ASN / ISP。
  • 解析 User-Agent 取得瀏覽器、作業系統、裝置類型與可用的裝置型號資訊。
  • 建立可查詢、可稽核的登入事件資料模型。
  • 支援內部後台或客服安全查詢最近登入紀錄。
  • 定義資料保存期限、遮罩規則、存取權限與第三方 provider 風險。

2.2 Out of Scope

  • 精準 GPS 定位或背景定位。
  • 以瀏覽器 fingerprinting 作為唯一裝置身份。
  • 自動封鎖登入、完整風控引擎或風險分數模型。
  • 登入通知、可信裝置、passkey / MFA 政策調整；這些應另開 SPEC 或在 SPEC-010 中延伸。

3. Data Model

建議建立 login_events 表或等價事件儲存結構。欄位名稱可依服務既有命名調整，但語義必須完整保留。資料模型不得只依賴 user_id，因為 admin、manager、affiliate 可能不在一般玩家 user table 內。

4. IP Resolution

系統必須只信任來自已知 proxy / load balancer 的轉發 header。不得無條件採用任意 client 傳入的 X-Forwarded-For，避免 IP spoofing。

部署在 Cloudflare 後方時，建議優先順序如下：

  1. CF-Connecting-IP，僅當 request 來源確定來自 Cloudflare。
  2. X-Forwarded-For，僅當 request 來源確定來自已知 reverse proxy / load balancer；取第一個未被信任 proxy 覆蓋的 client IP。
  3. X-Real-IP，僅當 request 來源確定來自已知 proxy。
  4. TCP remote address fallback。

IP 解析結果需記錄 ip_source，以便稽核與排錯。

5. Principal Coverage

所有登入入口都必須接入同一個 login event 記錄契約，不得由各 app 各自用不同格式記錄。至少包含下列入口：

登入主體 典型入口 記錄要求
user玩家 web app、LIFF、未來 native app必須記錄 principal_type = user、principal_id、user_id、session、IP、地點與裝置。
adminAdmin app、SSO、hardware MFA 流程必須記錄 principal_type = admin、principal_id、admin role、auth method、IP、地點與裝置；完整查詢需 audit trail。
manager營運 / 客服主管後台必須記錄 principal_type = manager、principal_id、role、IP、地點與裝置；高敏操作另需呼應 SPEC-018 操作留痕。
affiliate代理後台、代理登入 API必須記錄 principal_type = affiliate、principal_id、affiliate account id、IP、地點與裝置；信用帳戶管控另呼應 SPEC-011。

若某登入入口因架構限制暫時無法同步寫入事件，必須在同一個 durable transaction 內 enqueue transactional outbox，或透過 message queue 等價機制補寫，並保證最終可查詢。不得因 app 分離導致 admin 或 affiliate 登入缺失。若 login event table 與 outbox / queue 都不可用，登入流程可 fail-open，但必須寫入不含完整登入情報的 error summary、累加 metrics、觸發告警，且不得聲稱該登入事件已被持久化。

6. Geolocation

IP 地點查詢需支援 provider 抽象，避免業務邏輯綁死單一供應商。可接受來源包含 Cloudflare geo headers、MaxMind GeoIP2、IPinfo 或經審核的等價服務。

  • Geolocation 失敗不得阻塞登入。
  • Provider timeout 應使用短 timeout 與 fallback，避免拉高登入延遲。
  • UI、通知與客服後台需標示為「根據 IP 推估」。
  • 若使用第三方 API 查詢 IP，需確認隱私政策、資料傳輸區域與保存條款。

7. Device Parsing

裝置資訊應由 User-Agent 解析取得。解析失敗時，登入事件仍需寫入，並將相關欄位標示為 unknown 或 null。

User-Agent 可被瀏覽器、App WebView、VPN 工具或自動化程式改寫，因此不得作為強身份識別。若未來要做可信裝置，必須另行設計 device token、長期 cookie、passkey、MFA 或 session binding。

8. Privacy, Retention, And Access Control

  • IP address、User-Agent、登入地點與 ASN / ISP 應視為個人資料或敏感稽核資料。
  • 一般客服列表預設遮罩 IP，例如 203.0.113.xxx；只有授權角色可查看完整 IP。
  • 完整登入事件保存期限需設定產品預設值；MVP 建議 180 天，可由合規需求調整。
  • 超過保存期限的事件需刪除、彙總或匿名化。
  • 不得記錄密碼、OTP、access token、refresh token、session secret 或第三方 OAuth token。
  • 不得將完整登入情報寫入一般 application log；必要時僅記錄 event id。
  • 後台查詢完整登入事件必須產生 audit trail，呼應 SPEC-018。

9. Product And Admin UX Requirements

  • 使用者安全頁可顯示最近登入時間、約略位置、裝置類型與瀏覽器。
  • 客服 / 管理員後台可依 principal type、principal id、user、IP、時間範圍、event type 查詢登入事件。
  • 所有位置文字必須使用「約略位置」或「根據 IP 推估」等表述。
  • 若地點或裝置解析失敗，UI 應顯示「未知」而不是空白或錯誤。
  • MVP 不主動通知使用者新登入；登入通知需另行定義觸發條件與誤判處理。

10. Non-Functional Requirements

項目 要求
登入延遲事件寫入與 geolocation 不得使登入 P95 額外增加超過 100ms；第三方查詢建議走非同步 enrichment。
可用性Provider 不可用時登入流程仍需成功，事件以 geo_source = null 或 unknown 寫入。
稽核性事件需可追溯 IP 來源、provider、解析時間與查詢人員。
安全性完整 IP 與 User-Agent 查詢需受 RBAC 控制。
資料最小化只保存登入安全與稽核必要欄位，不收集 GPS 或不必要 fingerprinting 訊號。

12. Testing Strategy

  • Unit tests：覆蓋 IP header 解析優先序、可信 proxy 判斷、spoofed header 拒絕、User-Agent parsing fallback、identifier normalization / HMAC。
  • Integration tests：覆蓋 user、admin、manager、affiliate 的登入成功 / 失敗事件寫入、未知帳號依 login_surface 正確分類、geolocation provider timeout fallback、資料欄位不含 secret。
  • Authorization tests：覆蓋客服、管理員、一般使用者對完整 IP / 遮罩 IP 的查詢權限。
  • Migration tests：確認 login_events schema 可正確建立、索引符合常見查詢。
  • Manual QA：以桌面、手機、WebView / LIFF 登入，確認後台顯示約略位置與裝置資訊。

13. Success Criteria

  • 每次 user、admin、manager、affiliate 登入成功都會產生一筆可查詢的 login_success 事件。
  • 登入失敗會產生 login_failure 事件，且不保存密碼、OTP、token 或 session secret。
  • 成功登入事件必須包含 principal_type 與 principal_id；一般玩家事件額外包含 user_id。
  • 未知帳號的登入失敗必須保留 login_surface、attempted principal_type 與可用的 account_identifier_hash / key version；identifier 無法標準化時需以 failure_reason 標記。
  • affiliate 登入事件的 affiliate account id 必須落在 principal_external_id 或等價受控欄位，不得塞入 risk_flags。
  • IP 解析只信任明確設定的 proxy header，並保留 ip_source。
  • Geolocation 與 User-Agent parsing 失敗不阻塞登入。
  • UI / 後台不得將 IP geolocation 表述為精準位置。
  • 完整 IP、User-Agent 與登入事件查詢受 RBAC 與 audit trail 保護。
  • 測試覆蓋 IP spoofing 防護、provider fallback、登入事件寫入與查詢授權。

14. Boundaries

14.1 Always

  • 所有互動式登入入口都寫入同一份 login event contract。
  • 使用可信 proxy allowlist 判斷 client IP。
  • 將 geolocation 標示為 approximate。
  • 保留 provider 失敗時的 graceful fallback。
  • 在登入事件中避免保存任何 secret。

14.2 Ask First

  • 新增第三方 geolocation、VPN detection 或 device intelligence provider。
  • 變更登入事件保存期限。
  • 將登入事件資料外送至第三方分析或風控服務。
  • 啟用自動封鎖、MFA 強制觸發或使用者登入通知。

14.3 Never

  • 只記錄一般玩家登入而漏掉 admin、manager 或 affiliate 登入。
  • 宣稱 IP geolocation 是精準 GPS 位置。
  • 無條件信任 X-Forwarded-For。
  • 用 User-Agent 作為唯一可信裝置身份。
  • 保存密碼、OTP、access token、refresh token、session secret。
  • 把完整登入情報寫入一般 application log。

15. Open Questions

  • 正式部署是否一定經過 Cloudflare？若不是，需列出各環境可信 proxy / load balancer 清單。
  • 登入流程目前由哪個 service 作為唯一寫入點？Web、Admin、LIFF 是否共用認證服務？
  • admin、manager、affiliate 是否共用同一個 identity table，或分屬不同資料表？需決定 principal_id 的來源與唯一性。
  • MVP geolocation provider 優先使用 Cloudflare header、MaxMind local DB，還是外部 API？
  • 登入事件保存期限採 180 天、365 天，或依地區合規要求分流？
  • 哪些後台角色可查看完整 IP？哪些角色只能看遮罩 IP？
  • 是否需要在第一版加入 VPN / Tor / proxy detection，或延後至 SPEC-010 風控規則擴充？
