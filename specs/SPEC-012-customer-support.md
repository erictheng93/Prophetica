# SPEC-012 — 客服與爭議升級

> 版本：v0.1.0 · 最後更新：2026-05-05
> 依賴：SPEC-001, SPEC-004, SPEC-006
> 被依賴：—

---

## 1. Objective

建立 24/7 客服體系，處理玩家一般查詢、KYC 異議、結算申訴、責任博弈個案、技術故障。

## 2. 服務管道與 SLA

| 管道 | 適用情境 | SLA（首次回應）| 備註 |
|------|---------|--------------|------|
| 站內 Help Center | 標準查詢 | 自助 | FAQ + 知識庫 |
| 站內工單 | 帳號 / 結算 / 一般爭議 | 24 hr | 中文 / 英文 |
| Email | 同上 | 48 hr | service@{domain} |
| Live Chat | 緊急（已登入用戶）| 5 分鐘 | 中文 / 英文 / 日文 |
| 電話客服 | RG 高風險、Compliance、紛爭 | callback 4 hr | 僅 Compliance 案件 |
| 高 VIP 專線 | KYC 高 tier 用戶 | 2 hr | 邀請制 |

## 3. 工單系統

### 3.1 分類

| 分類 | 路由 | 優先級 |
|------|------|--------|
| 帳號登入 | T1 | 標準 |
| 儲值問題 | T1 → 金流組 | 高 |
| KYC 問題 | T1 → KYC 組 | 標準 |
| 結算爭議 | T2 → Compliance | **高** |
| 技術 bug | T1 → Engineering | 標準 |
| 責任博弈 | T2 → RG 客服 | **高** |
| 安全事件（被盜帳）| T2 → Security | **緊急** |
| 法務 / 監管 | T3 → Legal | 緊急 |

### 3.2 工單狀態機

```
NEW → ASSIGNED → IN_PROGRESS → AWAITING_USER → RESOLVED → CLOSED
                                       │
                                       ↓
                                   ESCALATED  ← Tier 升級
```

### 3.3 SLA 違反告警

- 24 hr 未首次回應 → P1 告警 → Team Lead
- 72 hr 未解決 → P0 告警 → 客服主管 + Compliance

## 4. 客服權限分級

| 角色 | 可執行操作 |
|------|-----------|
| T1 | 查詢用戶資訊（去 PII）、回覆工單、調整單筆設定 |
| T2 | 解凍帳戶、KYC 重啟、回覆爭議、執行 RG 個案 |
| T3 | 帳本調整提案（需 4-eye）、代表平台對外溝通、SAR 提交 |
| Admin | 配置 FAQ、調整客服系統設定 |
| Compliance | 結算 reversal、SAR 簽核、監管溝通 |

> 工程師**不直接**處理客服工單。技術問題由客服轉至 Engineering team backlog。

## 5. 客服查詢介面

### 5.1 玩家檔案頁面

客服可查（須留稽核 log）：

- 基本資訊（去除身份證號等 PII，僅 hash 後 4 碼）
- KYC tier 與歷史
- 儲值 / 交易 / 結算紀錄
- RG 評分歷史
- 最近 30 日工單

### 5.2 不可直接看的資訊

| 資訊 | 取得方式 |
|------|---------|
| 證件影像 | 透過 Compliance 申請 + 主管簽核 |
| 完整身份證號 | 同上 |
| 完整信用卡號 | 不可取得（PCI DSS）|
| 完整密碼 hash | 不可取得 |

### 5.3 操作日誌

每筆客服操作（查詢、修改、回覆）寫入 `audit_logs`，包含：

- 操作員 user_id
- 目標 user_id
- 操作類型
- 操作前後資料（修改類）
- 工單關聯 id
- 時間戳、IP、User-Agent

## 6. RG 個案處理流程

呼應 SPEC-006：

### 6.1 主動關懷流程（系統觸發）

```
RG 評分 71-85 → 系統自動建立工單，分派給 RG 客服
RG 客服在 4 hr 內聯絡用戶
依用戶反饋：
  - 用戶承認問題 → 提供 RG 工具（限額、冷靜期、自我排除）
  - 用戶否認 → 持續監控，定期回訪
  - 用戶不回應 → 維持監控，無強制動作
```

### 6.2 玩家主動求助

- Help Center 顯著位置「責任博弈協助」入口
- 客服有專屬腳本與培訓
- 提供合作戒癮機構聯繫資訊
- 不嘗試「挽留」玩家，遵循 player-first 原則

### 6.3 親友通報

- 接受第三方通報，但**不可直接以親友通報為據停權**
- 通報觸發系統 review，通報內容**不對玩家揭露**
- 客服可在後續 RG 評估中參考
- 確認問題嚴重 → 客服聯繫玩家，邀請其自我排除

## 7. 結算申訴處理

呼應 SPEC-004 §5（申訴窗口）：

### 7.1 客服分流

- 玩家提交申訴 → 工單分類為 `dispute`
- T2（Compliance 組）優先處理
- 24 小時申訴期內**所有**申訴必須回覆狀態（即使尚未裁決）

### 7.2 客服範本回應

- 我們已收到您的申訴，將於 24 hr 內進行裁決
- 裁決過程中我們將參考所有持倉者意見
- 裁決結果為最終，但您可申請進一步審查（升級 T3）

### 7.3 升級到 Compliance

- 案件涉及金額 > USD 1,000 → 直接升級
- 案件涉及多人申訴 → 直接升級
- T2 無法判定 → 升級

## 8. 工具與系統

### 8.1 推薦工單系統

- **Zendesk** 或 **Freshdesk**（成熟、整合強）
- 自建：Linode 上的 OS Ticket / RT（成本低但維護高）

決策：**MVP 用 Zendesk**，DAU > 100k 後評估遷移。

### 8.2 Live Chat

- **Intercom** 或 **Crisp**
- 整合 user context（自動帶入 user_id、KYC tier）

### 8.3 知識庫

- 整合於 Zendesk
- 內容由客服 + 法務協作維護
- 多語：繁中、簡中、英文、日文（首發）

## 9. 客服培訓

### 9.1 必修課程

| 課程 | 對象 | 頻率 |
|------|------|------|
| 平台規則與 ToS | 全員 | 入職 + 年度更新 |
| RG 識別與介入 | T2 RG 客服 | 入職 + 半年更新 |
| AML / 可疑交易識別 | T2/T3 | 入職 + 年度 |
| 個資保護（GDPR / 個資法）| 全員 | 入職 + 年度 |
| 玩家心理學 | T2 RG | 入職 |
| 系統工具操作 | 全員 | 入職 |

### 9.2 認證

- 完成課程 → 內部認證
- 認證每年 refresh
- 處理 RG / Compliance 案件需通過對應認證

## 10. 績效指標

| 指標 | 目標 |
|------|------|
| 首次回應時間（FRT）| < SLA 90% 達成 |
| 解決時間（RT）| < 24 hr 80% 達成 |
| CSAT | > 85% |
| RG 案件介入有效性 | 6 個月後該玩家 RG 評分下降 |
| 工單再開率 | < 10% |

## 11. 客服系統與帳本整合

當客服執行影響帳本的操作（如：退款、補償、扣回）：

- 不直接寫入帳本
- 透過 `compensation` API 提案，需 4-eye 簽核（T3 + Compliance）
- 帳本變動寫入 `Txn type = 'cs_compensation'`，附工單 id 為 correlation
