SPEC-024 — 銅幣兌換、虛擬商品與會員 Entitlement

優先級：P2
版本：v0.1.0 · 最後更新：2026-05-27
依賴：SPEC-002, SPEC-005, SPEC-010
被依賴：未來商城前端 SPEC（待立案）

變更紀錄

v0.1.0

首版。回應 SPEC-000 §5 Q-10 業主決議「銅幣點數僅可用於購買虛擬商品或兌換特定服務」之正面流程定義。本 SPEC 涵蓋：(1) catalog / SKU / 庫存模型；(2) redemption order 生命週期與 idempotency；(3) entitlement 生命週期狀態機（issued → fulfilled → consumed / refunded / expired）；(4) 對應 ledger 分錄與 INV-6 carve-out 需求（由 ADR-0007 governance）；(5) v1 凍結 entitlement 不可轉贈 之邊界（Q-10 雖允許各商品規格另行定義，但本 SPEC 選擇最保守解；放寬須另寫修訂版本並補 KYC / AML 評估）。實作細節見 SPEC-024 implementation plan。

1. Objective

定義會員以銅幣（SPEC-002）換取平台內虛擬商品或服務權益之完整流程；同時把 Q-10 所允許的正面用途規格化，避免「禁止會員轉點，但商城又沒寫好」之灰色地帶被當作後門。

名詞：本 SPEC 統一以 redemption（兌換）指「會員以銅幣換取站內權益」之單一動作；以 entitlement（權益）指「兌換後會員所持有、可在後續時刻消費或被 fulfilled 之站內憑證」。

2. Scope & Non-goals

2.1 In Scope（本 SPEC v0.1）

  • Catalog / SKU 資料模型（含商品分類、定價、庫存、上下架）
  • Redemption order：placement、idempotency、扣點、寫入 ledger
  • Entitlement 生命週期：issued → fulfilled | refunded | expired
  • Fulfillment 觸發：同步交付（數位 token / 啟用碼）與非同步交付（人工服務 / 外部 partner 履約）
  • 取消 / 退款窗口（fulfillment 前可退；fulfillment 後不可退，除非 SPEC-012 客服流程介入）
  • Entitlement 到期與「未使用銷貨折讓」（breakage）收入認列
  • 新 ledger txn_type 與 Chart of Accounts 擴展（由 ADR-0007 governance）
  • 新不變式 INV-7（user_id 同人綁定 + UnredeemedEntitlement 非負），呼應 SPEC-002 §5 INV-1 ~ INV-6
  • 反洗錢 / 反濫用觸發點：高頻 / 大額兌換之 SPEC-010 偵測 hook

2.2 Out of Scope（本 SPEC 不處理）

  • 會員間點數轉移 / 贈送：由 SPEC-002 §4.4.7 + Q-10 永久禁止。任何兌換流程不得提供「指定收件人為他人」之收件欄位。
  • Entitlement 之轉贈：本 SPEC v0.1 凍結為 不可轉贈。Q-10 雖允許「各商品規格另行定義轉贈規則」，本 SPEC 行使該允許之「最保守解」— 所有 entitlement 與兌換時的 user_id 綁死，且不得轉移擁有權。未來放寬必須另開 SPEC 修訂版本，並一併補 KYC tier 升級 / SPEC-010 AML 偵測 / Entitlement 二級市場政策三項評估。
  • Entitlement 兌回銅幣：永久禁止；fulfillment 後 entitlement 只能被消費或過期，不可逆向轉成 Player.Wallet。
  • 外部資產（金幣 / 法幣）出帳：兌換物之外部成本由 Liability.AccountsPayable.{partner_id} 與 Bank.OperatingAccount.* 獨立軌道處理（SPEC-011 §6.4 既有），與本 SPEC 之 player wallet outflow 完全零交集。
  • 商城 UI / UX / 推薦演算法 / 行銷活動：留給未來前端 SPEC。

3. Domain Model

3.1 Catalog · SKU · Stock

實體 說明 關鍵欄位（規格層）
CatalogItem 商品主檔；一個 item 可有多 SKU（如顏色 / 規格） item_id, kind（digital / service / physical）, status，visibility，category
SKU 可被兌換之最小單位；定價與庫存掛在此 sku_id, item_id, price_minor_units（銅幣，對齊 SPEC-002 §3.2），fulfillment_mode，entitlement_ttl_days
Stock 數位 / 服務商品多為「無限庫存或合約上限」；實體商品須對接外部 inventory sku_id, kind（unlimited / finite / partner_managed），available_qty，reservation_ttl_seconds

v1 邊界：本 SPEC 預設只開 kind = digital 與 kind = service 兩類；physical 為保留欄位，未啟用前任何商品 PR 不得設此值（CI 檢查）。

3.2 Redemption Order

一張 redemption order 對應「會員 A 以 N 銅幣兌換 SKU 之單次嘗試」。狀態機： 

[draft] → [submitted] → [accepted] → [committed] → [fulfilled]
                                          ↓             ↓
                                     [refunded]    [refunded](客服特批)
                                          ↓
                                      [expired]
                                          ↓
                                     [breakage]
  • submitted：玩家確認下單；後端校驗 SKU 在線、庫存可預留、會員 KYC 門檻達標、會員可用銅幣 ≥ 售價 + buffer
  • accepted：庫存預留成功（reservation_ttl_seconds 內未進入 committed 則自動釋放）
  • committed：寫入 ledger 之 redemption_purchase 交易成功， Liability.UnredeemedEntitlement.{user_id} 已產生餘額； entitlement 已 issued
  • fulfilled：履約已完成（數位即時，或服務 worker 回報）；entitlement 進入 fulfilled 終態
  • refunded：取消窗口內或客服核准之退點；ledger 反向 redemption_refund
  • expired → breakage：超過 entitlement_ttl_days 仍未 fulfilled；entitlement 作廢，liability 結轉為 Revenue.EntitlementBreakage

3.3 Entitlement 生命週期

每筆成功的 redemption order 都會在 committed 時 issue 一筆 entitlement。Entitlement 為 非可轉移之站內憑證，與兌換時的 user_id 永久綁定。

狀態 進入條件 離開條件
issued redemption order committed fulfilled / refunded / expired
fulfilled 履約 worker 回報成功；或同步交付完成 consumed（若有「使用」語意）；否則為終態
consumed 票券 / 服務時段被實際使用（非必經） 終態
refunded 取消窗口內取消，或客服核准退點 終態
expired 超過 entitlement_ttl_days 仍非 fulfilled 自動結轉 breakage 後為終態

不可轉移強制點：entitlement 表必含 owner_user_id 欄位，所有查詢 / 履約 / consumption API 必須以該欄為唯一所有者識別，禁止任何「指定他人為 owner」「贈送」「轉售」介面。對應 INV-7（見 §5）。

3.4 Fulfillment 模式

fulfillment_mode 典型商品 履約延遲 備註
digital_immediate 站內頭像框、徽章、表情包 commit 後 < 1s 同 transaction 寫入 ledger + entitlement + 啟用，最簡
digital_code 第三方平台啟用碼 commit 後 < 30s 從 vault 抓未發放 code；entitlement 變為「持碼狀態」
service_async VIP 諮詢、人工服務、外部 partner 履約 分鐘 ~ 數日 worker 訂閱事件、回報結果；entitlement 在 issued 至 fulfilled 間

4. Ledger 整合

全部 4 個新 txn_type 與 3 個新 Chart of Accounts 科目， governance 走 ADR-0007。本節為規格層；分錄範本 / migration / SDK validate 變更見 SPEC-024 implementation plan。

4.1 新增 Chart of Accounts 科目

負債（Liabilities）
  └─ Liability.UnredeemedEntitlement.{user_id}   會員已扣點但尚未 fulfilled 之憑證；本質仍是平台對玩家之負債（換成「給商品 / 服務」之承諾）

收入（Revenue）
  └─ Revenue.VirtualGoodsSales.{sku_kind}        虛擬商品 / 服務銷貨收入（按 SKU 分類聚合）
  └─ Revenue.EntitlementBreakage                  未消費過期憑證認列之 breakage 收入

4.2 新增 ledger txn_type

txn_type 典型分錄（簡述） 觸發點
redemption_purchase Player.Wallet.{X} +Y / Liability.UnredeemedEntitlement.{X} -Y order 進入 committed
entitlement_fulfillment Liability.UnredeemedEntitlement.{X} +Y / Revenue.VirtualGoodsSales.{kind} -Y 履約 worker 回報成功
redemption_refund Liability.UnredeemedEntitlement.{X} +Y / Player.Wallet.{X} -Y fulfillment 前取消，或客服核准退點（需 SPEC-012 4-eye）
entitlement_expiry Liability.UnredeemedEntitlement.{X} +Y / Revenue.EntitlementBreakage -Y 過期 sweep job

所有四種 txn_type 中 Player.Wallet.{X} 與 Liability.UnredeemedEntitlement.{X} 之 X 必須是 同一個 user_id；跨 user 配對由 INV-7 擋下（§5）。Proto enum 新增 4 個值之具體 ID 配置由 ADR-0007 §4 與 plan §3 定義。

4.3 INV-6 carve-out 需求

新增 redemption_purchase 為 Player.Wallet.* outflow 的合法新目的地 — 即 ADR-0006 §4.1 INV-6 表的 (g) 行： 

(g) Liability.UnredeemedEntitlement.{user_id}
    僅限：
      - txn_type = redemption_purchase
      - 配對之 Player.Wallet.{user_id} 與 Liability.UnredeemedEntitlement.{user_id} user_id 完全相同
      - metadata 必含：sku_id、order_id、idempotency_key、audit_log_id

此 carve-out 為「平台負債型態轉換」而非「銅幣變現」：玩家未取得外部資產， 平台對玩家之總負債維持不變（Player.Wallet 減少 = UnredeemedEntitlement 增加），呼應 ADR-0006 §1.2 R-1 紅線之精神。

5. 不變式擴展

本 SPEC 對 SPEC-002 §5 INV 表做兩件事：擴展既有 INV-2 / INV-4，新增 INV-7。governance 由 ADR-0007 追認（同 ADR-0006 對 Frozen / INV-6 之模式）。

ID 等式 / 規則 檢查頻率 違反處理
INV-2（擴展） Σ(Player.Wallet.*) + Σ(Player.Locked.*) + Σ(Player.Frozen.*) + Σ(Liability.UnredeemedEntitlement.*) = 平台對玩家負債總額 每 5 分鐘對帳腳本 記錄 Suspense.Reconciliation，啟告警 + 人工稽核
INV-4（擴展） 每個 Liability.UnredeemedEntitlement.X 任意時刻 ≥ 0（無 chargeback 例外） 每筆變動 拒絕交易；不得 issue 超出餘額之 entitlement 履約
INV-7（新增） txn_type ∈ {redemption_purchase, entitlement_fulfillment, redemption_refund, entitlement_expiry} 之交易中，所有 Player.Wallet.{X} 與 Liability.UnredeemedEntitlement.{Y} entries 之 user_id 必須相同（X = Y），即禁止跨會員兌換。 每筆 commit（DB CONSTRAINT TRIGGER） 該筆交易拒絕提交；視同 INV-6 等級違規

為何需要 INV-7：若僅靠 INV-6 white-list 允許「Player.Wallet → UnredeemedEntitlement」，惡意 / 漏洞 application 可寫入「Player.Wallet.A → UnredeemedEntitlement.B」之分錄 — 形式上 balanced、INV-6 white-list 也通過（目的地 account kind 合法），但實質是 wallet-to-wallet 跨會員轉點之偽裝，違反 Q-10。INV-7 把 user_id 同人綁定下沉到 DB 層強制，三層保護（CI / SDK / DB）對齊 INV-6 之安全強度。

6. KYC / AML 銜接

  • Tier 門檻：v1 預設所有 SKU 開放給 Tier 1（已驗證 email）；單筆兌換 ≥ 50,000 銅幣或單日累計 ≥ 200,000 銅幣之 SKU 標 requires_tier ≥ 2，由 SPEC-005 既有 KYC tier check 攔截。
  • SPEC-010 偵測 hook：在 redemption_purchase commit 後發出 redemption.committed 事件供 SPEC-010 anti-fraud pipeline 消費；目標偵測「短時間高頻兌換 → 暗示帳號被盜 / 點數來源異常」、「結合 SPEC-022 登入裝置異常之高風險兌換」。
  • 禁止濫用路徑：兌換流程不得提供「為他人下單 / gift link」介面；任何「分享」功能僅能分享商品頁網址，不可附帶預填收件人 user_id。

7. 退款 / 過期政策

  • 取消窗口：committed 之後、fulfilled 之前，會員可自助取消並全額退點；窗口長度由 SKU cancel_window_seconds 決定，預設 300 秒。
  • fulfilled 後不可自助退：須走 SPEC-012 客服流程；核准門檻： manager + admin 4-eye；退點來源為 Revenue.VirtualGoodsSales.{kind} 之 contra（負向 entry）， 並另寫補償 cs_compensation 分錄補回會員銅幣（與 redemption_refund 分離以利稽核）。
  • 過期 sweep：daily cron 掃 issued 狀態超過 entitlement_ttl_days 之 entitlement，寫入 entitlement_expiry 交易。
  • breakage 揭露：Revenue.EntitlementBreakage 為獨立子科目，年度財報必須單獨揭露，避免與正常銷貨收入混同。
