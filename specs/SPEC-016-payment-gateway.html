1. Objective

定義玩家儲值（fiat → 站內點數）的端到端支付通路：通路選型、收款主體、webhook 簽章、退款 / chargeback、跨幣別匯率鎖定、PCI 範圍劃線、多通路備援、結帳 UX。本 SPEC 補齊 SPEC-002（資金安全 / 帳本）與實際支付路徑之間的銜接議題。

5. Webhook 處理

5.1 必含驗證

項目 規則
HMAC 簽章 各通路規範各異；簽章驗證失敗直接 401，禁止記日誌
Replay 防護 Webhook 必含 timestamp，視窗 5 分鐘外的事件拒收
Idempotency 以通路 transaction_id 為 key，呼應 SPEC-002 §6.1
TLS 接收 endpoint 強制 TLS 1.3
IP 白名單 各通路公告之 IP range；命中之外 → drop

回應： - 200 OK：處理成功（含「已處理過」case） - 4xx：簽章 / 格式錯誤；通路會 retry，需審查 - 5xx：系統錯誤；通路 retry

5.3 Retry 規範

通路 retry 行為各異，後端必須假設： - 同一 transaction_id 至少送達 1 次，最多送達 N 次 - N 次 retry 都應產生同一筆 ledger transaction（idempotent） - 通路規範之最終 retry 截止前未回 200 → 通路標記為「pending」並由運維介入

5.4 失敗對帳

每日 T+1： - 對比平台 ledger 之該日 deposit transaction 數量 vs 通路後台對帳檔 - 差異 > 0 自動寫入 Suspense.Reconciliation（SPEC-002 §7.2）+ P0 告警

5.5 通路 Webhook Payload 對映表

各通路 webhook payload schema 不一致。本節定義從通路原生格式到後端統一 ProviderWebhookEnvelope（見 packages/proto/v1/payment.proto）的對映規則。每個通路在 services/payment-service/internal/providers/{provider}/ 內實作 driver-specific verifier。

5.5.3 Phase 1 換算規則

SPEC-016 §7.1 規定 Phase 1 ledger 僅有 Bank.TrustAccount.TWD。對非 TWD 通路（PayMongo / MoMo / VNPay 等）：

  • Driver decode 時取通路提供的 fx_rate（若無則拒絕，要求業主與通路重簽合約包含 FX 透明欄位）
  • settled_twd = original.amount × fx_rate，存入 ProviderWebhookEnvelope.settled_twd
  • 主流程僅 deposit settled_twd 到 Bank.TrustAccount.TWD，原幣別僅作 audit 紀錄
  • fx_rate 字串保留小數精度（如 "31.5"），不轉 float

觸發 處置

6.3 退款限制

  • 退款只能原路返回（信用卡退原卡、ATM 退原帳戶）
  • 部分退款最低粒度 = 1 點 = TWD 1（依計價單位）
  • 退款金額不得超過原始儲值
  • 退款超過 90 天則拒絕（通路普遍時限）

7. 跨幣別與匯率

Phase 1 — 永遠單幣別 TWD（呼應 SPEC-002 §3.1 已 Resolved 之 1 點 = TWD 1）。ledger 僅維持 Bank.TrustAccount.TWD 一個資產帳戶；國際玩家以非 TWD 法幣儲值時，由通路在 webhook 中換算為 TWD 後入帳，平台 ledger 永遠以 TWD 計價，任何幣別皆於通路端完成換算。

Phase 2（多幣別）保留設計但目前無啟用計畫。Q-3 已 Resolved 為 TWD 1:1，Phase 2 不再被 Q-3 阻塞；觸發條件改為業務驅動：(a) Op Co. 開立非 TWD 計價之國際版本（例如 USD ledger）、或 (b) 平台需主動承擔 FX 對沖（例如向 DMM 結算非 TWD 點數）。在無上述業務需求前，§7.4 之多幣別 schema 不實作。

Phase 1 平台不承擔 FX 風險（換算發生於通路端）。通路收取的 FX spread 視為玩家成本。

7.3 玩家 UI 對 FX 的呈現

  • 結帳前顯示原幣別金額 + 預估 TWD 點數，並標注「最終點數依通路結算匯率為準，可能微幅變動」
  • 入帳完成後，玩家錢包與儲值紀錄統一以 TWD 點數呈現
  • 退款比照 §6.3 「原路返回」原則，TWD 對原幣金額之精算差額由通路端處理

8. PCI DSS 範圍劃線

8.1 PCI 範圍最小化

平台永遠不直接接觸卡片號碼。所有卡資料透過通路 SDK / 跳轉至通路頁面收集。

元件 PCI 範圍
Web 前端 out-of-scope（卡資料以 iframe / redirect 至通路頁面收集）
API Gateway out-of-scope
Backend 服務 out-of-scope
Webhook receiver out-of-scope（通路只送 token / last 4 digits）

8.2 不可儲存的資料

  • ❌ 完整 PAN（卡號）
  • ❌ CVV / CVC（任何時刻）
  • ❌ Track 1/2 magstripe data
  • ❌ PIN

8.3 可儲存（受限）

  • ✅ Token（通路產生）
  • ✅ 卡號末 4 碼（顯示用）
  • ✅ Issuer / 國家 / 卡別（風控用）
  • ✅ Holder name（受限，僅 Tier 2/3 KYC 留存）

8.4 自評每年一次

  • SAQ A 等級即可（純 redirect / iframe 模型）
  • 由通路提供 Attestation of Compliance (AoC)
  • Compliance 每年更新自評

13. 安全要求

  • Webhook endpoint 走 Cloudflare WAF + IP 白名單
  • 通路 API 金鑰存於 Vault，依各通路最小權限
  • 退款 API 內部呼叫需 4-eye 簽核（T3 客服 + Compliance）

15. Open Questions

跨檔決策已收斂至 SPEC-000 §5 中央追蹤表。本節僅保留 SPEC-016 自身範圍內議題。

  1. 通路 chargeback rate 是否須在合約中爭取 < 0.5%（業界標準）？
  2. 玩家通路偏好是否要加密儲存（避免被推測使用習慣）？
  3. 跨境匯率 hedge 是否在 Op Co. 規模達一定門檻後啟動（如 Wise 之 forward contract）？
  4. 越南 / 菲律賓本地通路（Momo / PayMongo）是否需要設第二家 Op Co. 才能合規收款？
  5. 退款是否提供「退至錢包點數」之選項（玩家未真的轉錯）？— 法律風險：點數無回兌原則之邊界
