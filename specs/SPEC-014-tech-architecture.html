為何全 Rust 而非「Rust hot path + Go 其餘」混搭： - 單語言內部 RPC 與 SDK：12 個 service 之間共用 crates/sdk/（observability / errors / proto-gen / ledger client）；混語言要寫兩套 SDK + 兩套 OTel 對接，維運成本高於語言收益。 - 編譯時間可接受：sccache + Cargo workspace incremental build，CI 暖快取下單服務 < 90s；Distroless FROM rust AS builder + cargo-chef 分層快取使 image build < 5 min。 - 學習曲線：CRUD-style service（user / kyc / notification）用 axum + sqlx 程式量與 Go 相當，借助 ? 運算子甚至更短；borrow checker 對非熱點服務之主要成本為前 2 週適應期。

3.2.1 Cloudflare Pages Edge runtime 限制（T-10，公開 Beta 前 PoC）

Status (2026-05-08): ❌ live verification blocked before preview deploy. apps/web production next build passes, but @cloudflare/next-on-pages v1.13.16 failed to generate .vercel/output/static on the Windows host while probing pnpm --version; a shim retry timed out after 240s. prophetica-web-poc Pages project exists, but no preview deployment was produced. Rerun PoC-B on Linux/CI or a fixed Windows toolchain before deciding Edge runtime vs Node.js runtime.

Public Beta blocker：PoC-B live verification 未完成、且未接受 fallback ADR 前，apps/web 不得以 Cloudflare Pages Edge runtime 作為公開 Beta 生產部署模式。允許內部開發繼續，但公開 Beta 前必須在 PRE-FLIGHT-POCS §4.4 回填 pass / fail 證據；若失敗，需明確採 Node.js runtime 或 K8s BFF fallback。

apps/web 透過 @cloudflare/next-on-pages 部署至 Cloudflare Pages（Workers runtime）。Edge runtime 與標準 Node.js runtime 行為差異會在以下場景踩坑，公開 Beta 前需完成 E2E PoC 驗證（詳細 PoC plan 見 PRE-FLIGHT-POCS §4）：

場景 已知限制 PoC 驗證項
KYC iframe 嵌入（SumSub Web SDK） Edge runtime 對 Buffer / crypto Node API 有限制；SumSub iframe 內部 postMessage 需 server-side relay 時必須走 Web Crypto API iframe 載入 → 證件拍攝 → liveness → webhook → 通知前端流程端到端通過
WebSocket fan-out（撮合事件即時推播） Cloudflare Workers 之 WebSocket 為「pair」模式（client ↔ Worker durable object），單一 connection 不可在多個 Worker 之間 share state；訂單簿 WS 推播實際上由 ws-gateway（K8s 上的 axum service）處理，apps/web 自身不啟用 Workers WebSocket apps/web 連線至 ws-gateway 之 wss:// endpoint 跨 Cloudflare proxy 通過；reconnect / gap detection 行為符合 SPEC-003 §10.3
Server Actions / RSC（Next.js 15 App Router） Edge runtime 不支援部分 Node.js APIs（fs、net、tls、vm）；某些 npm package 在 import 時即失敗 server actions 中呼叫後端 gRPC（透過 fetch + tonic-web 或經 api-gateway REST proxy）通過 build + runtime
fetch 行為差異 Edge runtime fetch 不支援 keepalive: false；AbortController 行為與 Node 略異 TanStack Query 之 retry / cancel / abort 在 Edge runtime 下行為一致
環境變數注入 Cloudflare Pages 之 env binding 與 Next.js process.env 在 Edge runtime 行為不同；secret binding 走 env.SECRET_NAME .env.local → wrangler.toml 之 [vars] 之 mapping 通過 build；secret 不誤入 client bundle

若 PoC 任一項無法滿足 → 退路選擇：(a) apps/web 改部署至 Cloudflare Pages 之 Node.js runtime（性能略降但相容性好）；(b) 該功能拆 server-only API endpoint 落在 K8s 上由 api-gateway / bff-service 處理，apps/web 僅做 SSR + 純前端互動。退路選擇需開新 ADR。

4.1 MVP 合併部署 advisory（T-1，建議性，非強制）

動機：12 service × 各自 sqlx migrations / OTel instrumentation / Helm chart / Argo CD application = 重複工程量 + onboarding 摩擦；下單熱路徑跨 5+ service hop 累計 P99 也容易超 SPEC-007 §6.4 latency budget。

建議：MVP / 公開 Beta 階段先合併部署為 7 個 binary，service crate 結構（services/*/）保持本表 12 個分離（Cargo workspace 不變）但 build / deploy 為合併 binary。當 DAU > 5,000 或某 service 內部複雜度顯著（例如 KYC SaaS 整合需獨立 scaling）時再拆分。

MVP binary 合併之 service crate 拆分時機
core-api api-gateway + user-service + market-service + position-service + referral-service DAU > 5k / referral 規模化（簽 B2B 業務 ≥ 10 家）
realtime-gateway ws-gateway 一直獨立（WS 連線數 scaling 與 HTTP 不同）
wallet-ledger-service 保留獨立 帳本服務永遠獨立（attack surface + leader election）
matching-engine-{hot,cold} 保留獨立（兩 binary） SPEC-003 §17.3 已落地分流
settlement-worker 保留獨立（active / standby 模式） —
kyc-service 保留獨立（SaaS 整合 + webhook 安全邊界） —
notification-and-risk notification-service + risk-antifraud-service risk 邏輯 ML 化 / 第三方整合複雜化

合併部署的好處： - 部署 hop 與 service discovery surface 減少；core-api 內 user / market / position / referral 可同 process 承載，wallet-ledger / matching-engine 仍保留獨立安全與 latency 邊界 - 12 個 Helm chart → 7 個（onboarding 摩擦 -40%） - CI 編譯時間 -30%（fewer link units，shared dependencies）

合併部署的代價： - 個別 service 之 scaling 不獨立（如 user-service 無法獨立 scale up） - attack surface 略增（合併 binary 內部隔離靠 module + workspace lints，不靠 process boundary）

Codex PR #1 落地建議：採合併部署。services/*/ crate 保留本表 12 個結構（lib crate）+ services/_binaries/{core-api,realtime-gateway,...}/main.rs 之 7 個 binary crate 引用對應 lib。SPEC-017 §11.2 acceptance check 應反映此拓撲選擇。

本 §4.1 原為 advisory；截至 2026-05-09，MVP 合併部署已落地為目前實作形態。SDD 紀律：spec 應反映現況。

4.1.1 目前實作狀態（2026-05-09，MVP 合併部署落地）

現況：採 MVP 合併部署拓撲。12 個 services/*/ crate 保留 service 邊界與測試面，但不再各自暴露 standalone src/main.rs service binary；deployable entrypoints 集中於 services/_binaries/*。

當前實作選擇：

  • services/*/ 保留為 lib crate，維持 domain / API / test 邊界；未來拆回 12-binary 時不需重建模組邊界
  • services/_binaries/core-api 承載 api-gateway + user-service + market-service + position-service + referral-service
  • services/_binaries/realtime-gateway 承載 ws-gateway，因 WS 連線數 scaling 與 HTTP 不同而維持獨立 deployable
  • services/_binaries/wallet-ledger-service、settlement-worker、kyc-service 維持獨立 deployable，保留帳本安全邊界、active / standby 模式與 KYC webhook 邊界
  • services/_binaries/matching-engine-hot 使用 current-thread runtime + LocalSet + core_affinity；matching-engine-cold 使用 multi-thread runtime，對齊 SPEC-003 §17.3
  • services/_binaries/notification-and-risk 承載 notification-service + risk-antifraud-service，待 risk ML 化或第三方整合複雜化後再拆分
  • 新增 crates/sdk/tests/service_topology.rs 作為 topology regression test，防止 service crate 重新長出 standalone src/main.rs
4.1.1.1 拆回 12-binary 之觸發條件（將來）

下列任一成立時，啟動拆回 12-binary 拓撲之 PR / ADR：

  1. DAU > 5,000 或單一 service scaling 明顯分歧：例如 user / market / referral 其中一者需要獨立 HPA 或資源上限
  2. service 內部複雜度溢出：KYC SaaS、risk ML、referral B2B 或 notification provider 整合需要獨立 release cadence
  3. 安全或合規邊界升級：Compliance Officer / Tech Lead 要求特定 service 以 process / deployment boundary 隔離
  4. observability 或 incident response 摩擦：合併 binary 造成 log / trace owner 判讀、rollback、on-call routing 成本高於拆分成本

拆分流程（簡述，詳細待轉換時開新 ADR）：

  • 將目標 service 從 services/_binaries/* 抽回獨立 binary entrypoint
  • 保留現有 lib crate API，新增最小 src/main.rs 或對應 deployable package
  • Helm chart / Argo CD application / CI deploy step 由 MVP 合併形態拆分為目標 service 形態
  • 更新 SPEC-014 §4.1.1 與 topology regression test，確保 spec / code / deployment 三者一致

DMM API：binary protobuf over TLS（呼應 SPEC-009）

6.1.1 Gateway REST proxy 錯誤透傳

api-gateway 對 admin / internal REST proxy 經路（把後台請求轉發給內部 service 的 REST endpoint），收到 upstream service 的非 2xx 回應時：

  • 必須透傳 upstream 的 HTTP 狀態碼。upstream 回 404 → gateway 回 404；409 → 409，依此類推。
  • 必須透傳 upstream 回應主體中的 error code（例：ERROR_CODE_MEMBER_NOT_FOUND），不得替換成 ERROR_CODE_INTERNAL。
  • 禁止把可辨識的 upstream 4xx 一律壓成 500 ERROR_CODE_INTERNAL。500 僅保留給 gateway 自身的未預期失敗。
  • 僅當 gateway 取不到 upstream 回應時（連線拒絕、逾時、DNS 失敗等傳輸層失敗），才回 502 Bad Gateway 配合服務專屬的 unavailable error code（例：ERROR_CODE_KYC_SERVICE_UNAVAILABLE）。
  • gateway 自身的前置處理失敗（請求格式錯誤、權限不足）仍由 gateway 直接回對應狀態碼，與本規則無關。

理由：upstream service（如 user-service）已對 domain 錯誤回正確的狀態碼與 error code（會員不存在 → 404 ERROR_CODE_MEMBER_NOT_FOUND）。gateway 作為 proxy 把這些壓成 500 會讓後台無法分辨「會員不存在」與「系統故障」，並汙染告警與監控訊號。

6.1.2 Gateway 認證與 principal 傳遞契約

api-gateway 在本檔 §4 服務表中即明列職責為「邊緣 API、認證、路由」。對外（玩家 REST）入口，gateway 必須自行驗證 caller 的 session token 並衍生出 authenticated principal，不得直接信任 client 傳入的身份。

  • token 來源：session token 由 user-service 簽發（密碼 / LIFF / WebAuthn 登入流程，呼應 SPEC-022）。gateway 不簽發 token。
  • 驗證方式：gateway 必須在轉發前驗證 token——以 user-service 公布的 JWKS（/.well-known/jwks.json）驗章加過期檢查，或經 user-service 的 session introspection endpoint 驗證。驗證失敗一律不得轉發至下游。
  • principal 注入：驗證成功後，gateway 對內部 upstream service 注入 principal header（如 x-user-id、x-principal-type、x-principal-id）。這些 header 是 gateway 信任邊界內側的產物，語義為「已由 gateway 驗證過的身份」。
  • header 剝除：gateway 必須在入口剝除（strip）任何由外部 client 傳入的同名 principal header，再注入自己驗證得出的值。禁止讓 client 自帶 x-user-id 等 header 穿透到下游——該行為等同身份偽造。
  • 狀態碼：缺少 token、token 無效或過期 → 401 配合認證類 error code；token 有效但該 principal 無權限執行此操作 → 403。此兩者屬 gateway 自身的前置處理失敗，依 §6.1.1 由 gateway 直接回應，與 upstream 錯誤透傳規則無關。
  • 下游信任模型：內部 service 信任 gateway 注入的 principal header，其前提是這些 service 僅在私網、不可由外部直接路由；internal / service-to-service endpoint 不得對公網開放。

理由：現行 api-gateway 的 AuthContext extractor 直接讀取 x-user-id header 而未驗證任何 token，隱含假設「上游有一個會驗 JWT 再注入 header 的 proxy」。該假設未被任何 SPEC 定版，且該 proxy 不存在於現行合併部署拓撲（§4.1.1）。本節把 §4「api-gateway 負責認證」具體化為可實作契約：驗證發生在 gateway、principal header 為 gateway 內部產物、外部同名 header 一律剝除。SPEC-022 §15 對「登入由哪個 service 作為唯一寫入點」「principal_id 來源」之 open question，其認證側由本節收斂。SPEC-023 §4.2 / §7 的旅程認證接縫亦以本節為權威。

6.1.2.1 現況與遷移路徑（Transitional state, 2026-05-19）

本節 §6.1.2 描述的是目標態。截至 2026-05-19 spike 結果，現行 apps/web BFF 並未送 Authorization: Bearer 至 api-gateway，而是在 BFF 側自驗 HMAC cookie（proph_session，由 apps/web 自己用 SHA-256 HMAC 簽）後，直接以 x-user-id header 送至 gateway；gateway 目前對該 header 不做驗章。upstream 的 user-service session token 則被 apps/web 額外存於 proph_user_service_session cookie（SameSite=Strict），但目前並未在呼叫 gateway 時被轉送出去。即現況為 BFF-trust transitional state，§6.1.2 之 caller token 驗章機制尚未上線。

遷移路徑由 SPEC-023 玩家旅程實作計畫 §5.0 Phase 0 規範。粗略分為三個階段（任務級分解見計畫）：

  1. Caller credential migration：所有 caller（apps/web BFF 與其他內部呼叫者）從送裸 x-user-id 改為送 Authorization: Bearer <user-service token>；無法或不該走玩家 token 的 caller 改走明確 internal-service auth 或時限 allowlist。apps/web 的 proph_session 自此退守為單純 UI session 識別，proph_user_service_session 為 gateway caller credential 來源。
  2. Gateway JWT validation online：gateway 啟用 §6.1.2 規範之 JWT 驗章 middleware（user-service JWKS），驗過的 principal 注入 request extensions。過渡期間可暫時並存 Bearer 與 x-user-id 兩條路徑作為遷移橋接，但 x-user-id 路徑只供向後相容、不得擴張至新 caller，並以 metric 追蹤使用比例直至歸零。
  3. Cutover + 攻擊面驗證：所有 caller 完成階段 1 後，AuthContext 切換為僅讀 verified principal，gateway 開始 strip 外部 x-user-id / x-principal-* header。執行直接攻擊面測試（偽造 x-user-id 無 Bearer → 401；合法 Bearer + 偽造 x-user-id → 以 token user 為準）。通過後 transition flag 移除，§6.1.2 全面生效，本 §6.1.2.1 可標記為 historical 或刪除。

關鍵順序不變式：階段 3 的 x-user-id strip 必須在所有 caller 完成階段 1 之後啟用，否則仍以裸 x-user-id 呼叫 gateway 的 caller 將立即 401。實作計畫以 feature flag 或明確 task dependency 保證此順序。
