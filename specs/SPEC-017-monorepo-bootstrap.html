1. Objective

定義 prophetica 從「git clone 到 make dev 啟動本地全套服務」的最小可重現流程。本 SPEC 是「可實施規格」中唯一不對應某個業務 service 的 meta-SPEC，目的是讓 Codex / 新進工程師在第一個 PR 之前有明確的 bootstrap 步驟，避免每位實作者各自詮釋 SPEC-014 §5 的目錄結構。

1.1 In-scope

  • Repository 骨架（Turborepo + pnpm workspaces + Cargo workspace）
  • Docker Compose 本地開發環境
  • Makefile / pnpm script 統一入口
  • 各 service / app 之最小 hello-world stub
  • CI bootstrap（GitHub Actions 最小可運行 workflow）
  • 開發者首次設定流程

1.2 Out-of-scope

  • 業務邏輯（由各 SPEC 定義）
  • Production K8s / Helm / Terraform（由 SPEC-013 / SPEC-008 定義）
  • protobuf message 內容（見 §4.3，schema 細節在 packages/proto/v1/）

2. 目錄結構（與 SPEC-014 §5 一致）

SPEC-014 §5 為規範來源，本節為實際 bootstrap 後的 file tree 對應。任一不一致以 SPEC-014 為準並更新本節。

3.4 Windows 開發者特別說明

prophetica 主要開發機之一為 Windows + PowerShell。為避免每位開發者自行設定：

  • 所有 make 目標必須能在 WSL2 Ubuntu 22.04 上跑通
  • docker-compose.local.yaml 不依賴 host network mode（Windows Docker Desktop 不支援）
  • 路徑分隔符不用反斜線（一律 /）

12. Open Questions

  1. ~~packages/proto/gen/ 是否 commit 進 git？~~ ✅ Resolved 2026-05-05：commit 進 git（含 Rust + TS 雙語言）。理由：(a) 跨機器（macOS / Windows / Linux CI）import path 一致，rust-analyzer / IDE 立即可解析；(b) 新人首次 clone 即可 cargo build，不必先跑 buf generate；(c) PR diff 會明確顯示 schema 變更對 stub 的影響，作為 schema 評審輔證；(d) CI 跑 git diff --exit-code crates/proto/src/gen packages/proto/gen/ts 確保 .proto 與 gen/ 同步（不一致則 CI fail）。落地動作：兩個目錄皆不加入 .gitignore；新增 make proto target 規範 regenerate 流程。注意：Rust 慣例為 build.rs runtime codegen，本決策刻意偏離以對齊 monorepo 全語言一致性策略。
  2. ~~.env 配置注入採 direnv vs docker-compose env_file vs dotenv-cli？~~ ✅ Resolved 2026-05-05：採 docker-compose env_file 為主，理由與落地： - direnv 在 PowerShell / Windows 原生支援差，本團隊 macOS + Windows 雙平台 → 排除 - dotenv-cli 多一層 npm wrapper，Rust service 仍要自己讀 env，價值有限 → 排除 - docker-compose env_file: .env 為事實標準、跨平台、與 §5 docker stack 天然契合 → 採用 - 直接跑 cargo run -p <service> 之開發者：Rust side 統一用 dotenvy（dotenvy::dotenv().ok(); 於 main 起始）；Next.js side 走內建 .env.local（apps/web/） - 範本檔：repo 根 .env.example（已知 key + 註解 + 安全預設值），make bootstrap 首次執行時 copy 為 .env 若不存在 - 嚴格禁止 將 .env commit 進 git（已加入 .gitignore）；secrets 載入 prod 走 SPEC-010 §6 secret manager
  3. ~~mock servers（tools/mocks/sumsub / payment）是否獨立 repo 或同 monorepo？~~ ✅ Resolved 2026-05-05：同 monorepo（路徑 tools/mocks/{sumsub,payment}/）。理由： - 版本同步零成本：mock 必須與 SPEC-005 KYC webhook payload schema、SPEC-016 §5.5 6 家通路 webhook 對映表、packages/proto/v1/kyc.proto / payment.proto 同步演化。獨立 repo 會造成 schema drift，CI 無法在同一 PR 跨 repo 驗證。 - 新人 onboarding 簡化：make dev 一次拉起含 mocks 的完整 stack，不必額外 clone repo / 設 token。 - CI 共享 cache：Rust workspace 與 protobuf stub 已在 monorepo 編譯，mocks 共用 sccache / cargo target cache。 - 嚴格隔離：mocks 僅在 make dev / make test 啟用；tools/mocks/ 透過 .dockerignore 與 Cargo feature flag（[features] mock = []，僅 mocks crate 自身依賴）確保絕無進入 production binary 之路徑；§8 CI 加 grep gate：services/ 與 crates/sdk/ 之 Cargo.toml 不得依賴 tools/mocks/* crate。
  4. Windows 主機之 host networking 限制如何處理 hostNetwork 撮合引擎部署？本地 dev 不啟用 hostNetwork（僅 prod K8s 啟用），由 SPEC-008 §3 監督。
  5. ~~CI matrix（macOS / Linux / Windows）是否啟用？~~ ✅ Resolved 2026-05-05：採 「Linux 主 gate + macOS nightly + 不跑 Windows runner」 三層策略： - PR gate（每次 push）：ubuntu-latest only — lint / test / build / sentinel-scan / buf generate --check。生產環境為 Linux，主 gate 必須與 prod 一致。 - Nightly（cron）：macos-latest 跑全套 unit test + make doctor。理由：團隊有 macOS 開發者，需早期捕捉路徑分隔符 / 檔名大小寫敏感性 / Apple Silicon (aarch64) 之 Rust cross-compile 差異（rdkafka 之 librdkafka native 綁定常見差異點）。Nightly 失敗發 Slack alert 但不阻塞 PR merge（單列 issue tracking）。 - 不跑 Windows runner：Windows 開發者統一走 WSL2 + Docker Desktop（執行時等同 Linux），CI 加 Windows runner 成本高（GitHub Actions Windows runner 計價 2x、Docker-in-Docker 困難、librdkafka MSVC build 時常爆），ROI 低。 - 開發者本機行為：macOS / WSL2 直接 make dev；Windows 原生（非 WSL2）僅支援 make dev-host（純 cargo run 啟動，不含 docker stack），明列於 §9 setup 文件。
