1. Objective

定義 prophetica 從「git clone 到 make dev 啟動本地全套服務」的最小可重現流程。本 SPEC 是「可實施規格」中唯一不對應某個業務 service 的 meta-SPEC，目的是讓 Codex / 新進工程師在第一個 PR 之前有明確的 bootstrap 步驟，避免每位實作者各自詮釋 SPEC-014 §5 的目錄結構。

1.1 In-scope

  • Repository 骨架（Turborepo + pnpm workspaces + Cargo workspace）
  • Docker Compose 本地開發環境
  • Makefile / pnpm script 統一入口
  • 各 service / app 之最小 hello-world stub
  • CI bootstrap（GitHub Actions 最小可運行 workflow）
  • 開發者首次設定流程

1.2 Out-of-scope

  • 業務邏輯（由各 SPEC 定義）
  • Production K8s / Helm / Terraform（由 SPEC-013 / SPEC-008 定義）
  • protobuf message 內容（見 §4.3，schema 細節在 packages/proto/v1/）

2. 目錄結構（與 SPEC-014 §5 一致）

SPEC-014 §5 為規範來源，本節為實際 bootstrap 後的 file tree 對應。任一不一致以 SPEC-014 為準並更新本節。

v0.2.3 erratum（2026-05-05）：先前版本錯誤假設 Kumo 由 Cloudflare 私有 registry 發佈，並要求 KUMO_NPM_TOKEN。實際上 @cloudflare/kumo 經 github.com/cloudflare/kumo README 與 pnpm add 雙重驗證，發佈於公開 npm registry（與 @cloudflare/workers-types 等其他 @cloudflare/* 套件一致）。本節重寫以反映正確真相。

@cloudflare/kumo 為 Cloudflare 維護的 React 元件庫（建立於 Base UI），發佈於公開 npm registry，不需要特殊 .npmrc registry 配置或 auth token。安裝指令與一般 npm 套件無異：

3.4 Windows 開發者特別說明

prophetica 主要開發機之一為 Windows + PowerShell。為避免每位開發者自行設定：

  • 所有 make 目標必須能在 WSL2 Ubuntu 22.04 上跑通
  • docker-compose.local.yaml 不依賴 host network mode（Windows Docker Desktop 不支援）
  • 路徑分隔符不用反斜線（一律 /）

6.3 admin / liff app 認證與角色（amended 2026-05-10）

變更摘要：原條文要求 apps/admin/ 顯示「登入佔位」，本次修訂改為實際 login UI 與應用層 session，並引入 RBAC 三角色（admin / manager / affiliate）。Cloudflare Access 仍維持為 ingress 殼，但僅針對內部角色路徑生效；affiliate 路徑（/me/affiliate/*）與 /login 走 Access bypass，由應用層 session cookie 自驗。

  • app/page.tsx — 角色 redirect：admin / manager 進入操作入口，affiliate redirect 至 /me/affiliate
  • app/me/affiliate/{page,payouts,sub-tree}.tsx — affiliate 自助門戶，僅顯示 viewer 自己的代理資料（脫敏）

6.3.1.1 補償 domain 工作流規則（新增 2026-05-23）

§6.3.1 矩陣定義 /compensation 之路由層級 RBAC；本節補述跨路由的領域工作流契約。實作層次決定（狀態機、reconcile 演算法、入帳冪等規則、failure 分類、cancel 狀態 reserved 等）不入 spec，集中於 docs/implementation-plans/2026-05-19-compensation-review-chain-plan.md。

  • 兩步流程：補償走「提案 → 審核」二步；同一筆提案的提案者 user_id 不得等於審核者 user_id（單人核准下的職責分離保證；handler 守門 + 測試覆蓋，跨表 DB CHECK 不可行）。
  • 提案者類別（proposer_kind，gateway 由 signed call 之 actor_role 推導）：
    • admin / manager：經 admin app /compensation 表單提案，亦在同頁面審核他人提案。
    • cs_system：客服系統經 gateway compensation API 提案（machine-to-machine signed internal call）。
    • affiliate：v1 為 scoped API only；admin app UI 由獨立 v1.1 plan 接入 /me/affiliate 子頁。affiliate 不進 /compensation，故矩陣維持 403。
  • 審核者類別：限 admin 或 manager，單人核准即可（取代原 SPEC-012 §11 「4-eye T3 + Compliance」設計；T3/Compliance 非 admin app 角色，且職責分離已由 proposer ≠ approver 保證）。
  • Affiliate 提案守門（gateway 強制，三道俱足才得提案）：
    • 金額上限：超過 env AFFILIATE_COMPENSATION_MAX_MINOR_UNITS 即拒（422 ERROR_CODE_COMPENSATION_AMOUNT_OVER_LIMIT）。
    • Subject-scope check：subject 必須與該 affiliate 有 direct referral 關係，呼叫 referral-service 內部端點 GET /internal/referrals/affiliates/{aff_id}/subjects/{subj_id}/scope 驗證（cross-ref SPEC-011 flat-list 推薦模型；v1 僅認 direct，不預留多層語意）。
    • Fail closed：referral-service 不可達 / 5xx → gateway 回 502 ERROR_CODE_REFERRAL_SCOPE_UNAVAILABLE，不放行未驗證的 affiliate 提案。
  • 不存在 member 的回應分流（防止補償提案端點被當作 member 枚舉工具）：
    • admin / manager / cs_system 提案 → 404 ERROR_CODE_MEMBER_NOT_FOUND（語意明確，配合 SPEC-017 §6.3.4 錯誤呈現規則）。
    • affiliate 提案 → 403 ERROR_CODE_COMPENSATION_SUBJECT_OUT_OF_SCOPE（與 out-of-scope 同碼，不洩漏「member 存在 vs 不存在」之差別）。
  • 稽核必含：每筆 compensation audit event 必含 proposer_kind；affiliate 案另含 referral-service 回傳之 relationship。referral-service /scope 端點每次呼叫亦寫一筆內部 audit log（service-level，與 compensation audit 分離）。對齊 SPEC-018 evidence lookup（compensation.proposals.by_ticket）。

6.3.4 Admin app 後端錯誤呈現（新增 2026-05-18）

Admin app 對後端（經 api-gateway，錯誤契約見 SPEC-014 §6.1.1）的非 2xx 回應，必須依 HTTP 狀態碼與回應主體的 error code 呈現可辨識的使用者訊息，不得一律顯示籠統錯誤。最低要求：

  • 404：呈現「查無資料」語意的狀態（如會員查詢的「查無此會員」），而非錯誤橫幅或 toast。
  • 502 / 503：呈現「服務暫時無法使用，請稍後再試」，並允許重試。
  • 5xx（gateway 自身未預期失敗）：呈現籠統錯誤訊息；此為最後手段，不得作為 4xx 的預設呈現。
  • BFF 層（apps/admin/lib/*-bff.ts）必須透傳 gateway 的 HTTP 狀態碼與 error code，不得重新對映或壓平——否則前端無從辨識。

首個落地對象：KYC 審核會員查詢（/members/kyc-review）。gateway 對不存在會員回 404 ERROR_CODE_MEMBER_NOT_FOUND（SPEC-014 §6.1.1），admin app 必須顯示「查無此會員」而非一般錯誤。實作見 apps/admin/app/members/kyc-review/ 與 apps/admin/lib/member-management-bff.ts。

6.3.5 角色帳號生命週期管理（分權 CRUD）（新增 2026-05-22）

意圖與邊界。本節定義自上而下的帳號管理鏈：admin → manager → affiliate（代理）。此為「行政管理權委派」（誰能對誰的帳號做增刪改查），不是 SPEC-011 §2.1 明文禁止的「總代 → 代理 → 業務」多層抽佣下線金字塔。兩者語意必須分離：本節的管理歸屬不產生任何分潤、不沿管理鏈逐層抽成；分潤仍依 SPEC-011 之單層推薦規則，與此處的 managing_manager_id 無因果關係。§6.3.1 為路由層 RBAC，本節為其下的資料列層（row-level）授權，兩者並存、皆以 server-side 為唯一真實來源，UI 僅作呈現過濾。

6.3.5.1 管理權矩陣。「✅ 增刪改查」中之「刪」一律為軟刪除（停用／封存，狀態轉為 disabled／archived），不得物理刪除帳號或其稽核軌跡（SPEC-018）。

操作對象adminmanageraffiliate
manager 帳號✅ 增刪改查（全部 manager）403（不得管理任何 manager，含自身角色提權）403
affiliate 帳號✅ 增刪改查（全部 affiliate）；可指派／重指派 managing_manager_id✅ 增刪改查，僅限 managing_manager_id = 本人之 affiliate403（代理門戶為自助，非帳號管理）
自身 profile（非角色／非歸屬欄位）✅✅✅（既有 /me/affiliate 自助）

6.3.5.2 歸屬模型。affiliate_profiles 新增 managing_manager_id TEXT NULL，存「管理該代理之 manager 的 user_id」，並建索引。其與既有 owner_sponsor_id（推薦人／掛靠來源，屬 SPEC-011 推薦語意）語意分離、不得互相覆寫。歸屬規則：

  • manager 建立 affiliate 時，managing_manager_id 由 server 強制寫入該 manager 的 user_id，呼叫端不可指定他人。
  • admin 建立 affiliate 時，可指派任一存在且未停用的 manager 或留空（NULL = 「admin 池」，僅 admin 可管）。因 affiliate_profiles 位於 referral-service、manager 帳號位於 user-service，managing_manager_id 不做跨服務 foreign key；有效性由 api-gateway 在建立與重指派前查 user-service 驗證。
  • managing_manager_id 的重指派（移交歸屬）僅限 admin；manager 不得修改任一 affiliate 的歸屬（含不得將他人代理改掛己身）。具體執法採 deny-by-presence：manager 之 PATCH payload 只要出現 managing_manager_id 欄位即 403，不比對與現值是否相同——避免「同值送進」的潛在繞道與時序競態。BFF（admin app）在 manager 視角必須於邊界 strip 此欄位（見 apps/admin/lib/affiliate-management-bff.ts 之 stripManagingManagerIdForManager），以免 manager 編輯表單回填唯讀歸屬欄位造成誤拒；admin 視角保留欄位以支援重指派。

唯一事實來源。managing_manager_id 僅由 referral-service 持有並執行範圍判斷；user-service 不得複製此欄位或自行判斷 affiliate 是否屬於某 manager。user-service 僅負責 login credential、role 與停用狀態；任何需要 affiliate 管理歸屬的流程都必須透過 referral-service 查驗，避免雙重事實來源漂移。

6.3.5.3 範圍強制（row-level）。當 actor 為 manager，所有對 affiliate 的讀取與寫入（list / get / create / update / soft-delete）一律於 server 端附加 WHERE managing_manager_id = :actor_user_id 條件；落在範圍外之目標一律回 403（或對清單查詢即不可見），不得僅靠前端隱藏 CTA。actor 為 admin 時無此範圍限制。

6.3.5.4 反向與橫向禁制（紅線）。下列一律 server-side 拒絕，並寫稽核：

  • affiliate 對任何帳號的管理操作 → 403（呼應 SPEC-002 §4.4.5「不得代表 admin/manager 操作」）。
  • manager 對 admin 或其他 manager 帳號之任何 CRUD → 403。
  • manager 對範圍外 affiliate 之任何 CRUD → 403。
  • 提權禁制：建立／更新帳號時，manager 可設定之 role 僅能為 affiliate；任何試圖寫入 admin／manager 角色或修改自身 role 之請求 → 403。角色指派為 admin 專屬。
  • 承 §6.3.5.2，manager 之 PATCH payload 中出現 managing_manager_id 欄位（無論值是否變動）→ 403（deny-by-presence）。BFF 在 manager 視角須 strip 此欄位。
  • 上述拒絕事件皆須留下 denied audit（actor、target、action、reason / error code），不得只回 403 而無稽核軌跡。denied create 可能尚無 affiliate_id，不得寫入要求 affiliate_id NOT NULL REFERENCES affiliate_profiles 的既有成功 mutation audit 表；須使用 nullable target 的 denied-operation audit sink，或同等可存 attempted payload 的獨立表。歸屬／範圍／費率等 affiliate domain 拒絕由 referral-service 寫本地 denied audit；gateway 粗篩或 saga 編排拒絕由 api-gateway 寫 gateway denied audit。

6.3.5.4.1 manager 範圍內可寫欄位（含抽佣費率）。manager 對自己旗下（範圍內）affiliate 的可寫欄位包含 profile 與 commission_rate_bps（抽佣費率）：經理可調整自己旗下代理的佣金率，此為既有且預期行為（程式碼 lib.rs:1982 之 manager 限制僅涵蓋信用控制 credit_*，不含 commission_rate_bps）。此處調整的是單層佣金率（代理本身的抽佣），不沿管理鏈逐層分潤，不構成 SPEC-011 §2.1 禁止的多層下線分潤。manager 仍不得修改：credit_* 信用控制、role（§6.3.5.4 提權禁制）、managing_manager_id（§6.3.5.2 歸屬重指派限 admin）。每次費率變更須寫入 affiliate_rate_changes（含 changed_by / reason）與 operation audit。

6.3.5.5 帳號 API 與既有缺口。本節對應之 server 介面與目前實作落差（補完於 implementation plan）：

  • user-service 之 /v1/internal/admin/members*（建立／更新／刪除）目前 handler 無 actor 角色閘且建帳號 role 寫死 player。本節要求：(1) 由 api-gateway 注入可信 actor（user_id + role），(2) manager 帳號 CRUD（建立／編輯／停用 manager）閘定為 admin 專屬，(3) affiliate 帳號 CRUD 可由 admin 或經 referral-service 驗證為範圍內的 manager 執行，建立時 login credential role 固定為 affiliate，並建立／更新 referral-service 的 affiliate_profiles 管理歸屬，(4) 建帳號需可指派 manager／affiliate 角色（受 §6.3.5.4 提權禁制約束）。
  • referral-service 之 affiliate mutation 已有 admin|manager 角色閘與「manager 不得改信用控制」限制（既有），但缺 §6.3.5.3 的 managing_manager_id 範圍強制，須補上。
  • 每筆 mutation 與 denied mutation 必須寫稽核（actor user_id／role、目標、動作、reason、authorization_basis 或拒絕原因），沿用既有 affiliate admin CRUD 稽核表式樣並擴及 manager 帳號操作（SPEC-018）。

6.3.5.5.1 Affiliate 帳號建立編排。建立 affiliate 是跨服務流程：user-service 建立 login credential / role，referral-service 建立 affiliate_profiles / managing_manager_id。不得以兩個無關同步寫入直接提交。api-gateway 必須作為 orchestrator，要求 client 提供或 server 產生穩定 Idempotency-Key，並以 saga / outbox 記錄階段狀態與補償動作。admin app 建立 affiliate 帳號時必須呼叫此 saga endpoint；既有 referral-service affiliate create 只可作為 saga 內部 profile-create step 或 profile-only 維護 API，不得由 UI/BFF 直接當成帳號建立入口。若 user-service 已成功但 referral-service 失敗，流程必須進入可重試或補償狀態（例如停用或標記 pending 的 credential，直到 profile 建立成功），不得對外回報完整成功；若 referral-service 已成功但 credential 失敗，也必須能以同一 idempotency key 重試或封存 profile。完成條件是兩邊皆存在且可登入／可管理，否則必須可查詢、可告警、可人工修復。

6.3.5.6 刪除與孤兒處理。停用（軟刪除）一個 manager 前，admin 必須先將其旗下 affiliate 重指派給其他 manager 或移入 admin 池（managing_manager_id = NULL）；不得留下指向已停用 manager 的 affiliate。affiliate 軟刪除不影響其歷史分潤與撥款紀錄（SPEC-011）。

6.3.5.7 路由銜接。帳號管理 UI 依 §6.3.1 慣例以 server-side RBAC 過濾：manager 帳號管理頁為 admin 專屬（manager／affiliate 403）；代理帳號管理沿用 /affiliate，對 manager 為「範圍內可寫」，其資料與 CTA 範圍依 §6.3.5.3 過濾。涉及高敏感操作（如批次停用）是否納入 SPEC-010 §9.3 multi-sig，列為 OQ 待 §6.3.5 落地時定案。

三個 Next.js app（web / admin / liff）共用 packages/ts-sdk 與 Kumo 元件，由 Turborepo ^build 依賴拓撲連動。

12. Open Questions

  1. ~~packages/proto/gen/ 是否 commit 進 git？~~ ✅ Resolved 2026-05-05：commit 進 git（含 Rust + TS 雙語言）。理由：(a) 跨機器（macOS / Windows / Linux CI）import path 一致，rust-analyzer / IDE 立即可解析；(b) 新人首次 clone 即可 cargo build，不必先跑 buf generate；(c) PR diff 會明確顯示 schema 變更對 stub 的影響，作為 schema 評審輔證；(d) CI 跑 git diff --exit-code crates/proto/src/gen packages/proto/gen/ts 確保 .proto 與 gen/ 同步（不一致則 CI fail）。落地動作：兩個目錄皆不加入 .gitignore；新增 make proto target 規範 regenerate 流程。注意：Rust 慣例為 build.rs runtime codegen，本決策刻意偏離以對齊 monorepo 全語言一致性策略。
  2. ~~.env 配置注入採 direnv vs docker-compose env_file vs dotenv-cli？~~ ✅ Resolved 2026-05-05：採 docker-compose env_file 為主，理由與落地： - direnv 在 PowerShell / Windows 原生支援差，本團隊 macOS + Windows 雙平台 → 排除 - dotenv-cli 多一層 npm wrapper，Rust service 仍要自己讀 env，價值有限 → 排除 - docker-compose env_file: .env 為事實標準、跨平台、與 §5 docker stack 天然契合 → 採用 - 直接跑 cargo run -p <service> 之開發者：Rust side 統一用 dotenvy（dotenvy::dotenv().ok(); 於 main 起始）；Next.js side 走內建 .env.local（apps/web/） - 範本檔：repo 根 .env.example（已知 key + 註解 + 安全預設值），make bootstrap 首次執行時 copy 為 .env 若不存在 - 嚴格禁止 將 .env commit 進 git（已加入 .gitignore）；secrets 載入 prod 走 SPEC-010 §6 secret manager
  3. ~~mock servers（tools/mocks/sumsub / payment）是否獨立 repo 或同 monorepo？~~ ✅ Resolved 2026-05-05：同 monorepo（路徑 tools/mocks/{sumsub,payment}/）。理由： - 版本同步零成本：mock 必須與 SPEC-005 KYC webhook payload schema、SPEC-016 §5.5 6 家通路 webhook 對映表、packages/proto/v1/kyc.proto / payment.proto 同步演化。獨立 repo 會造成 schema drift，CI 無法在同一 PR 跨 repo 驗證。 - 新人 onboarding 簡化：make dev 一次拉起含 mocks 的完整 stack，不必額外 clone repo / 設 token。 - CI 共享 cache：Rust workspace 與 protobuf stub 已在 monorepo 編譯，mocks 共用 sccache / cargo target cache。 - 嚴格隔離：mocks 僅在 make dev / make test 啟用；tools/mocks/ 透過 .dockerignore 與 Cargo feature flag（[features] mock = []，僅 mocks crate 自身依賴）確保絕無進入 production binary 之路徑；§8 CI 加 grep gate：services/ 與 crates/sdk/ 之 Cargo.toml 不得依賴 tools/mocks/* crate。
  4. Windows 主機之 host networking 限制如何處理 hostNetwork 撮合引擎部署？本地 dev 不啟用 hostNetwork（僅 prod K8s 啟用），由 SPEC-008 §3 監督。
  5. ~~CI matrix（macOS / Linux / Windows）是否啟用？~~ ✅ Resolved 2026-05-05：採 「Linux 主 gate + macOS nightly + 不跑 Windows runner」 三層策略： - PR gate（每次 push）：ubuntu-latest only — lint / test / build / sentinel-scan / buf generate --check。生產環境為 Linux，主 gate 必須與 prod 一致。 - Nightly（cron）：macos-latest 跑全套 unit test + make doctor。理由：團隊有 macOS 開發者，需早期捕捉路徑分隔符 / 檔名大小寫敏感性 / Apple Silicon (aarch64) 之 Rust cross-compile 差異（rdkafka 之 librdkafka native 綁定常見差異點）。Nightly 失敗發 Slack alert 但不阻塞 PR merge（單列 issue tracking）。 - 不跑 Windows runner：Windows 開發者統一走 WSL2 + Docker Desktop（執行時等同 Linux），CI 加 Windows runner 成本高（GitHub Actions Windows runner 計價 2x、Docker-in-Docker 困難、librdkafka MSVC build 時常爆），ROI 低。 - 開發者本機行為：macOS / WSL2 直接 make dev；Windows 原生（非 WSL2）僅支援 make dev-host（純 cargo run 啟動，不含 docker stack），明列於 §9 setup 文件。
