## 1. Objective

設計多層代理推薦體系，但**避免觸及多層次傳銷（MLM）法律紅線**，並確保佣金計算可被稽核、稅務可被追蹤。

## 2. 法律邊界（先擺最前面）

### 2.1 MLM 紅線

依台灣公平交易法 §23 與多層次傳銷管理法，**禁止**：

- 主要收入來自介紹下線而非銷售
- 入會費（推薦人從新人入會費抽佣）
- 三層以上的金字塔結構（嚴格說兩層以上即危險）

### 2.2 安全設計

> 採用「**單層介紹費 + 銷售佣金**」設計，不做傳統意義上的多層代理。

| 設計 | 內涵 |
|------|------|
| **介紹獎勵**（一次性）| 介紹人在被推薦人首次儲值達閾值時獲得固定獎勵點數，僅一層 |
| **交易佣金**（持續）| 介紹人從被推薦人的**交易手續費**中抽取百分比，僅一層 |
| **不存在「下線的下線」** | 推薦關係**只有一層**，不形成樹狀結構 |
| **介紹獎勵以點數發放** | 不是現金，符合「站內虛擬道具」性質 |

> 原 PRD「總代 → 代理 → 業務」的多層架構**不採用**。技術實作上仍可記錄推薦樹用於分析，但**不據此計算佣金**。

### 2.3 「業務」角色（B2B 簽約推廣）

對於希望以「業務」身份大規模推廣的合作方：

- 必須**簽訂正式 B2B 合約**（與 Operating Co.）
- 業務以**個人名義開立發票**（自由業）或**公司對公司結款**
- 業務的「推薦獎勵」歸入**廣告 / 行銷費用**會計科目
- 與一般玩家推薦走**完全分開**的計算與發放路徑

## 3. 推薦關係模型

### 3.1 資料結構

```sql
CREATE TABLE referrals (
    id              BIGSERIAL PRIMARY KEY,
    referrer_id     BIGINT NOT NULL,            -- 推薦人
    referred_id     BIGINT NOT NULL UNIQUE,     -- 被推薦人，每人只能被一人介紹
    referral_code   VARCHAR(32) NOT NULL,
    referred_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    qualified_at   TIMESTAMPTZ,                 -- 達標（首次儲值或 KYC 完成）時點
    status          VARCHAR(32) NOT NULL,       -- pending/qualified/disqualified
    metadata        JSONB NOT NULL DEFAULT '{}'
);
CREATE INDEX idx_referrals_referrer ON referrals(referrer_id);
```

### 3.2 推薦碼生成

每位玩家自動分配唯一推薦碼：

```
{username_hash}_{random_alnum_4}
e.g., 'abc123_X9pK'
```

- 不公開玩家原名
- URL 形式：`https://proph.net/?ref=abc123_X9pK`
- 註冊頁自動填入 `referral_code`

### 3.3 推薦關係建立規則

- 每位玩家**最多被一人**介紹（first-touch attribution）
- 推薦關係於玩家**註冊時**鎖定，不可後續更改
- 推薦碼**不可由親屬之間使用**（後台偵測 KYC 證件地址、姓氏 → 標記疑似）

## 4. 佣金計算

### 4.1 介紹獎勵（一次性）

被推薦人達標條件：

- 首次儲值 ≥ TWD 500
- 完成 KYC Tier 1
- 註冊後 30 日內成交至少 5 筆訂單（防只儲值不交易）

達標後：

```
推薦人獲得：固定 100 點數（內部成本約 TWD 100）
被推薦人獲得：50 點數註冊獎金
```

> 預算邏輯：行銷成本 ≈ TWD 150 / acquired user，視市場 CAC 調整

### 4.2 交易佣金（持續）

被推薦人每筆成交產生的**手續費**中：

```
maker_fee × 10% → referrer
taker_fee × 10% → referrer
```

單位為點數，每日結算批次寫入 referrer 錢包。

### 4.3 佣金期限

交易佣金**僅持續被推薦人註冊後 12 個月**，之後不再計算。

> 設計目的：防止「躺賺」，鼓勵推薦人持續推廣新人

### 4.4 反作弊規則

- referrer 與 referred 為同 IP / 同 device fingerprint / 同 KYC 證件 → **不發放**
- referred 沒有真實交易（僅儲值不交易）→ **不發放**
- referrer 帳戶被標記異常 → 凍結佣金至釐清
- referred 退款 / chargeback → 對應佣金反沖

### 4.5 帳本記錄

呼應 SPEC-002，佣金為平台費用：

```
Txn: affiliate_commission

  Entry 1: Expense.AffiliateCommission   +X
  Entry 2: Player.Wallet.{referrer}      -X
```

## 5. 推薦人後台

### 5.1 自助介面

每位玩家都可在個人頁查看：

- 已成功介紹人數
- 累計獲得獎勵
- 過去 30 天 / 12 個月歷史
- 推薦樹結構（**僅一層**：你介紹的人）

### 5.2 業務專屬後台（B2B 簽約）

針對簽約業務的進階介面：

- 細項 dashboard：每位被推薦人的活動、儲值、交易量、佣金
- 月度報表 PDF 下載
- 提現申請（業務從推薦獎勵點數提現走 B2B 合約走流程，**不**經玩家錢包出口）
- 稅務文件：發票上傳、扣繳憑單下載

## 6. 業務 / 大型推廣方支付路徑

> 這個區段**不**走玩家點數系統，**走 Operating Co. 應付帳款**。

```
業務簽合約：每月行銷費 / 績效獎金 → Operating Co. 開立 BVI 法律下的 B2B 應付
業務每月開立發票 / invoice
Operating Co. 從營運帳戶（非託管帳戶）支付
業務自行報稅（境外收入或本地收入依其所在國法律）
```

業務帳戶可選擇將點數獎勵轉為 B2B 合約應付：

- 玩家身份 → 業務身份升級需正式簽約
- 點數轉應付：1 點 = TWD 1 等值，計入應付帳款
- 此**不違反**玩家無出金原則，因業務的法律地位是「推廣服務商」非玩家

## 7. 稅務處理

### 7.1 玩家層級

- 玩家獲得的點數獎勵**不是現金所得**，依台灣稅法不需報稅
- 但**B2B 業務**獲得的 B2B 收入須報稅
- 玩家若達一定收入規模（每年介紹超過 X 人 / 收入超過 X 點）→ 系統提醒，建議升級為業務

### 7.2 平台層級

- 介紹獎勵與交易佣金記入 `Expense.AffiliateCommission`
- 月結提供財務 / 會計 / 稅務團隊
- 跨境支付（業務在不同國家）依執照地稅法處理

### 7.3 扣繳義務

- B2B 業務若為台灣居民，依所得稅法扣繳 10%
- 跨境支付依雙邊租稅協定處理
- 系統需自動產生扣繳憑單

## 8. 監管揭露

執照地監管可能要求揭露：

- 推薦獎勵總額（月 / 季）
- B2B 業務名單（執照地律師審閱）
- 大額推薦獎勵個案（單月 > USD 5,000 等值）

## 10. Open Questions

2. 12 個月佣金期限是否合適？業界多為 lifetime 但風險高
3. 「業務」升級門檻？月介紹 ≥ X 人 / 累計收入 ≥ X？
4. 業務 B2B 合約是否要求最低推廣承諾？
5. 業務違反條款（如假帳號刷量）的清退與已付佣金回收條款？
