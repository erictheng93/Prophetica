SPEC-023 — 玩家入門與首次下單旅程（Player Onboarding & First-Trade Journey）

優先級：P1
版本：v0.1.0 · 最後更新：2026-05-19
依賴：SPEC-003, SPEC-005, SPEC-005a, SPEC-014, SPEC-015, SPEC-016, SPEC-021, SPEC-022
被依賴：前端 onboarding 實作、轉換漏斗與 SPEC-020 分析、未來 native app / LIFF 內嵌產品面

v0.1.0 變更

新增玩家入門與首次下單旅程規格。將原本分散於 SPEC-021（landing）、SPEC-022（登入）、SPEC-005 / SPEC-005a（KYC）、SPEC-016（支付）、SPEC-015（市場）、SPEC-003（撮合）的零件，編排為單一條「落地頁 → 註冊 / 登入 → KYC 門檻 → 錢包儲值 → 市場探索 → 首次下單」旅程：定義旅程階段與狀態機、跨頁重導向契約、門檻攔截規則與進場入口交接。本 SPEC 為編排層，不重寫各零件 SPEC 的內部機制。

1. Objective

在 SPEC-023 之前，玩家從 landing page 進入、登入、通過 KYC 與儲值、進場下注的完整旅程，沒有任何單一 SPEC 負責。每個零件都有規格——landing 變體在 SPEC-021、登入事件在 SPEC-022、KYC 在 SPEC-005 / SPEC-005a、支付在 SPEC-016、市場生命週期在 SPEC-015、撮合在 SPEC-003——但「這些零件如何串成一條使用者旅程、誰是這條旅程的 owner、各階段之間如何銜接與重導向」沒有規範來源。實務上旅程真正斷掉的地方，正是這些零件之間的銜接縫。

本 SPEC 是這條旅程的編排層（orchestration spec）與唯一 owner。它定義旅程的階段與狀態機、階段之間的跨頁重導向契約、各下單前置門檻的攔截與導向規則，以及進場入口的交接邊界。本 SPEC 不重寫各零件 SPEC 的內部機制——KYC 分層機制以 SPEC-005 為權威、支付機制以 SPEC-016 為權威、撮合與訂單機制以 SPEC-003 為權威——只規範它們在旅程中如何被觸發、如何銜接、未滿足時把使用者導去哪裡。

旅程的「完成」定義為：一名新訪客在 apps/web 成功送出第一筆被撮合引擎接受的訂單（SPEC-003 訂單下單成功回應）。

2. Scope

2.1 In Scope

  • apps/web（玩家前台）由 landing page 至首次下單的端到端旅程。
  • 旅程階段定義與狀態機（§3、§4）。
  • 跨頁重導向契約：return_to 語義、深連結保存、登入後導向、open redirect 防護（§5）。
  • 進場入口交接：landing 變體與 LIFF 如何把使用者交付到旅程起點（§6）。
  • 下單前置門檻的攔截與導向規則：未登入、KYC tier 不足、錢包餘額不足時的系統行為（§7）。
  • 旅程狀態判定的權威來源（server session、KYC tier、錢包餘額），以及不得依賴 client 端狀態的要求。

2.2 Out of Scope

  • KYC 分層機制、SumSub 整合、tier 升級觸發條件——以 SPEC-005 / SPEC-005a 為權威，本 SPEC 僅引用。
  • 支付通路、入金 / 出金機制——以 SPEC-016 為權威；MVP 真實入金前的調點路徑以 SPEC-002 manual_points_adjustment 為權威。
  • 市場生命週期、撮合與訂單撮合邏輯——以 SPEC-015 / SPEC-003 為權威。
  • 登入事件記錄、IP / 裝置情報——以 SPEC-022 為權威。
  • landing 變體 lifecycle、region × product matrix、合規檢核——以 SPEC-021 為權威。
  • session token 簽發與 gateway 驗證機制——以 SPEC-014 §6.1.2 與 SPEC-022 為權威。
  • LIFF 內嵌產品面（在 LINE 內瀏覽市場、儲值、下單）。目前 LIFF 僅負責把使用者帶到 landing page（見 §6.2）；LINE 內嵌產品旅程為未來 SPEC 或版本範圍。
  • 轉換漏斗指標定義與報表——以 SPEC-020 為權威，本 SPEC 僅提供階段切點。

3. 旅程階段與狀態機

旅程由 7 個階段組成。S0–S2 為線性序列；S3（KYC 門檻）與 S4（錢包儲值）為兩道順序無關的閘門，使用者可以任意先後完成，兩者皆滿足且 session 有效時才達到可下單狀態。S5 市場探索在登入後即可進行，不需先完成 S3 / S4。

S0 落地        S1 註冊        S2 登入
[landing] ──CTA──> [/auth/sign-in?mode=signup] ──> [authenticated]
                          │（已有帳號）
                          └──> [/auth/sign-in] ──> [authenticated]
                                                        │
                                   ┌────────────────────┼────────────────────┐
                                   ▼                    ▼                    ▼
                            S5 市場探索           S3 KYC 門檻           S4 錢包儲值
                            [/markets]            [/kyc/*]              [/topup]
                                   │                    │（達下單最低 tier）  │（餘額 ≥ 成本）
                                   ▼                    └────────┬───────────┘
                            S6 首次下單  ◀───── trade_ready（S2 + S3 + S4 同時成立）
                            [/markets/:id]

旅程狀態以下列受控值表示。狀態是 server 端推導結果，不是 client 持有的旗標（見 §8）：

狀態意義判定來源
visitor未登入訪客，可唯讀瀏覽 landing 與公開市場頁。無有效 session。
registered帳號已建立，可能尚未完成 email 驗證（見 §13 OQ）。user-service 帳號存在。
authenticated持有有效 session，可進入需登入頁面。gateway 驗證通過的 session（SPEC-014 §6.1.2）。

funded錢包銅幣餘額足以支應目標訂單成本。wallet-ledger 可動用餘額。
trade_readyauthenticated + kyc_cleared + funded 同時成立，可實際送出訂單。上述三者之合取。

4. 階段詳述

4.1 S0 — 落地（Landing）

  • 使用者抵達某個 apps/landing-* 變體（SPEC-021）。landing page 為純行銷面，不持有 session cookie（SPEC-021 §5.3）。
  • landing 的主要 CTA（「立即註冊」/「開始體驗」等）必須跳轉至 apps/web 的 /auth/sign-in?mode=signup；次要「登入」連結跳至 /auth/sign-in。
  • CTA 點擊可附帶來源歸因參數（landing variant、行銷來源）。歸因參數的格式與保存以 SPEC-021 / SPEC-020 為權威；本 SPEC 僅要求歸因不得阻塞旅程、且不得被當成身份。
  • 離開條件：使用者點擊 CTA 進入 apps/web 的認證頁。

4.2 S1 / S2 — 註冊與登入（Sign-up & Login）

  • 認證面為 apps/web 的 /auth/sign-in；?mode=signup 顯示註冊、無參數顯示登入。
  • 註冊成功建立 registered 帳號；登入成功建立 session，進入 authenticated。
  • session token 由 user-service 簽發、由 api-gateway 驗證——機制以 SPEC-014 §6.1.2 與 SPEC-022 為權威。本 SPEC 不規範 token 格式。
  • 每次登入成功 / 失敗都必須產生 login event（SPEC-022）；本 SPEC 不重述其欄位。
  • 登入完成後的導向遵循 §5 重導向契約：有 return_to 則導回，否則導向 /portfolio。
  • 離開條件：session 建立完成。

4.3 S3 — KYC 門檻（KYC Gating）

  • 下單所需的最低 KYC tier 由 SPEC-005 §2 定義（見 §13 OQ-1，需與 SPEC-005 對齊確認）。
  • 觸發方式有二：(a) 使用者嘗試一個需要該 tier 的動作（如下單）而 tier 不足，被 §7 攔截導向 /kyc/*；(b) 使用者主動發起 KYC 升級。
  • KYC 流程本身（Tier 1 OTP、Tier 2 SumSub iframe 等）以 SPEC-005 / SPEC-005a 為權威。本 SPEC 僅要求：因下單被攔截而進入 KYC 時，完成後必須依 §5 導回原本的下單意圖頁。
  • 離開條件：KYC tier 達到下單所需最低值（kyc_cleared）。

4.4 S4 — 錢包儲值（Wallet Funding）

  • 送出訂單前，可動用銅幣餘額必須足以支應該訂單成本（含 SPEC-003 定義的下單鎖定額）。
  • 觸發方式有二：(a) 使用者嘗試下單但餘額不足，被 §7 攔截導向 /topup；(b) 使用者主動儲值。
  • 資金來源依階段不同：
    • MVP（真實入金前，SPEC-000 Launch Gate LG-2 未通過）：銅幣由 SPEC-002 manual_points_adjustment 之授權調點路徑提供。此階段 /topup 不得呈現會誤導為真實金流已開通的 UI。
    • 真實入金開放後（LG-2 通過）：依 SPEC-016 支付通路儲值。
  • 儲值機制以 SPEC-016 / SPEC-002 為權威。本 SPEC 僅要求：因下單被攔截而進入儲值時，完成後必須依 §5 導回原本的下單意圖頁。
  • 離開條件：餘額 ≥ 目標訂單成本（funded）。

4.5 S5 — 市場探索（Market Discovery）

  • 市場列表 /markets 與市場詳情 /markets/:id 顯示 SPEC-015 定義的市場。公開市場列表預設允許 visitor 唯讀瀏覽（見 §13 OQ-3）。
  • 市場資料、訂單簿、近期成交以 SPEC-015 / SPEC-003 為權威。
  • 離開條件：使用者於市場詳情頁發起下單。

4.6 S6 — 首次下單（First Order）

  • 使用者於 /markets/:id 透過下單面板選擇結果腿（YES / NO）、價格與數量送出訂單。
  • 送出前，前端與後端都必須確認旅程狀態為 trade_ready。任一門檻未滿足，依 §7 攔截；不得在前端先行宣稱已下單。
  • 訂單撮合、pre-trade 檢查、回應契約以 SPEC-003 為權威。
  • 旅程完成條件：撮合引擎回傳訂單已被接受（SPEC-003 下單成功回應）。

5. 跨頁重導向契約

旅程跨越 apps/landing-* 與 apps/web 多個頁面，重導向必須有一致契約，否則使用者會在被攔截後迷失意圖。

  • landing 不持有 session：landing 變體不得設定或讀取 session cookie；認證態僅存在於 apps/web（呼應 SPEC-021 §5.3）。
  • return_to 參數：當使用者因門檻被攔截導向認證 / KYC / 儲值頁時，系統必須以 return_to query 參數保留原始意圖頁的完整路徑（含 query string）。例如未登入使用者深連結到 /markets/abc?side=yes 嘗試下單，被導向 /auth/sign-in?return_to=%2Fmarkets%2Fabc%3Fside%3Dyes。
  • open redirect 防護：return_to 必須只接受 same-origin 的相對路徑。絕對 URL、協定相對 URL（//host）、跨網域目標一律拒絕並 fallback 至預設導向。此規則由 apps/web 中介層強制（見 §13 OQ-4）。
  • 門檻完成後導回：使用者完成被攔截的門檻（登入 / KYC / 儲值）後，若 return_to 存在且合法，必須導回該頁；否則導向預設頁 /portfolio。
  • 導向單跳：每次攔截導向必須在單次 request 完成，不得讓使用者經過多層中介跳轉。
  • 多重門檻：使用者下單同時缺 KYC 與餘額時，系統一次只導向一個門檻；該門檻完成後導回原市場頁，由 §7 規則重新評估、必要時再導向下一個門檻。每一步的 return_to 都必須指回最初的下單意圖頁。

6. 進場入口交接

6.1 Landing 變體

各 apps/landing-* 變體是旅程的主要進場入口。變體的 region × product matrix、合規檢核與上線 / 退役以 SPEC-021 為權威。對本 SPEC 而言，所有變體的交接契約一致：landing CTA 把使用者交付到 apps/web 的認證頁（§4.1），旅程自 S1 起一致。

6.2 LIFF

目前 LIFF（LINE）入口在本 SPEC 旅程中僅負責把使用者帶到 landing page。使用者一旦自 LINE 進入 landing，即走與一般 web 訪客完全相同的標準旅程（S0 起）。

  • 本版本 LIFF 不在 LINE 內承載註冊、登入、KYC、儲值或下單。
  • LIFF 內嵌產品面（在 LINE 內完成旅程、使用 LINE 身份登入）為未來 SPEC 或版本範圍，屆時需擴充本 SPEC §6 或另開銜接 SPEC。
  • 因此本 SPEC 的旅程階段（§3、§4）與門檻規則（§7）只針對 apps/web 撰寫。

7. 門檻與攔截規則

下表為旅程的規範性攔截規則。前端與後端對「使用者嘗試的動作」評估所需狀態；未滿足時，系統必須執行對應導向，並依 §5 保留 return_to。

嘗試的動作所需狀態未滿足時的系統行為
瀏覽 landing / 公開市場列表 / 市場詳情（唯讀） visitor 即可 允許。不得攔截唯讀瀏覽。
進入需登入頁（/portfolio、/topup、/kyc/*、/account/*） authenticated 導向 /auth/sign-in?return_to=<原路徑>；登入後導回。
送出訂單（下單） authenticated 導向 /auth/sign-in?return_to=<市場頁>；登入後導回市場頁，重新評估。
kyc_cleared（達下單最低 tier） 導向 /kyc/* 對應 tier；完成後導回市場頁，重新評估。
funded（餘額 ≥ 訂單成本） 導向 /topup；完成後導回市場頁，重新評估。
提領 / 出金 依 SPEC-016 / SPEC-005 超出本 SPEC 範圍，引用對應 SPEC。

規則要點：

  • 後端為最終權威：前端門檻檢查只為改善體驗，不可取代後端強制。即使前端被繞過，api-gateway 與下游 service 仍必須拒絕不符旅程狀態的下單（SPEC-003 pre-trade 檢查、SPEC-014 §6.1.2 認證）。
  • 攔截不得靜默失敗：被攔截時必須給出明確、可操作的下一步導向；不得只回一個無導向的錯誤。
  • 門檻順序無關：KYC 與儲值兩道閘門可任意先後完成；§7 在每次導回市場頁後重新評估剩餘缺口。

8. Non-Functional Requirements

項目要求
狀態權威旅程狀態判定必須以 server session、KYC tier、錢包餘額為準，不得依賴 client 端可竄改的旗標或 localStorage。
意圖保存被攔截導向後完成門檻，必須導回原始意圖頁；深連結（含 query）必須完整保留。
導向延遲每次攔截導向在單次 request 完成；不得多層中介跳轉。
降級行為市場資料、錢包餘額等下游查詢失敗時，旅程頁可顯示降級狀態，但不得以 mock 資料誘導使用者送出無法成立的訂單。
安全return_to 僅接受 same-origin 相對路徑；landing 不持有 session。

10. Testing Strategy

  • E2E journey tests：覆蓋 happy path——新訪客自 landing CTA → 註冊 → 登入 → /portfolio → /markets → 市場詳情 → 首次下單成功。
  • 攔截導向 tests：未登入嘗試下單 → 導向 /auth/sign-in → 登入後導回市場頁；KYC tier 不足下單 → 導向 /kyc/* → 完成後導回；餘額不足下單 → 導向 /topup → 完成後導回。
  • 多重門檻 tests：同時缺 KYC 與餘額時，逐道閘門導向、每步 return_to 都指回原市場頁。
  • 深連結 tests：未登入深連結到帶 query 的市場頁並嘗試下單，登入後完整導回（含 query）。
  • 安全 tests：return_to 帶絕對 URL / 跨網域 / 協定相對 URL 時被拒絕並 fallback 至預設頁。
  • 後端強制 tests：繞過前端、直接對 api-gateway 送出不符旅程狀態的下單，必須被拒絕（未認證 → 401、KYC / 餘額不足 → 對應錯誤）。
  • Manual QA：以桌面與手機瀏覽器走完整旅程，確認每個攔截點都給出明確下一步。

11. Success Criteria

  • 存在單一規範來源（本 SPEC）描述 landing → 首次下單的完整旅程，且每階段都標明權威零件 SPEC。
  • 新訪客可在 apps/web 走完 happy path 並成功送出第一筆被撮合引擎接受的訂單。
  • 所有下單前置門檻（登入、KYC、餘額）未滿足時，使用者被導向唯一明確、可解鎖的下一步，完成後導回原意圖頁。
  • 旅程狀態完全由 server 端推導；繞過前端的不合法下單被後端拒絕。
  • return_to 僅接受 same-origin 相對路徑，跨網域目標被拒絕。
  • landing 變體與 LIFF 入口都把使用者一致交付到旅程起點。
  • 測試覆蓋 happy path、各攔截導向、多重門檻、深連結保存、open redirect 防護與後端強制。

12. Boundaries

12.1 Always

  • 旅程每個攔截點都把使用者導向唯一明確、可解鎖的下一步。
  • 完成被攔截的門檻後，導回原始意圖頁並保留深連結。
  • 以 server session、KYC tier、錢包餘額作為旅程狀態的唯一權威。
  • 後端對下單獨立強制旅程門檻，不信任前端檢查結果。
  • 各零件機制一律引用權威 SPEC（SPEC-003 / 005 / 015 / 016 / 021 / 022），不在本 SPEC 重寫。

12.2 Ask First

  • 變更下單前置門檻的組合（例如取消 KYC 門檻、開放未驗證下單、調整下單所需最低 tier）。
  • 新增進場入口或改變既有入口的交接方式（native app、LIFF 內嵌下單、第三方嵌入）。
  • 變更登入後的預設導向頁。
  • 在真實入金開放（LG-2）前於 /topup 呈現真實金流 UI。

12.3 Never

  • 在前端宣稱訂單已送出，而後端尚未回傳成功。
  • 信任 client 傳入的身份，或允許繞過 KYC / 餘額門檻送出訂單。
  • 讓 return_to 接受跨網域絕對 URL（open redirect）。
  • 把 landing page 變成持有 session 的登入態頁。
  • 以 mock / fallback 資料誘導使用者送出無法成立的訂單。
  • 攔截使用者後只回無導向的錯誤、不指出下一步。
