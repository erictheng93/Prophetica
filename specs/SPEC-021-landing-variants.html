1. 範圍與目標

1.1 為什麼需要這份 SPEC

產品方針確定採 multi-landing 架構：不同地區市場與不同產品線對應獨立 apps/landing-* Next.js 應用，但共用同一組 Rust 後端 services + 同一個 apps/admin 後台。為避免 landing 增生造成：

  • 合規元件被各 landing 自行重寫（KYC entry、責任博弈 modal 不一致）
  • API 契約偏離 packages/proto 造成後端報表斷裂
  • 觀測事件命名各自為政造成 SPEC-007 / SPEC-020 報表無法跨 variant 聚合
  • 視覺風格碎片化失控

本 SPEC 規範 landing variant 的 lifecycle 與強制檢核清單。

1.2 範圍

  • 每個 apps/landing-* 的目錄骨架與必載入的共用元件清單
  • Region × Product matrix 的宣告格式
  • 上線前合規檢核 gate
  • 部署拓樸（Cloudflare Pages 多 project + 域名策略）
  • Variant 退役流程

1.3 非範圍

  • landing 的視覺設計細節（屬於 design/ 與 packages/design-tokens 的領域）
  • 後端 services 的修改（multi-landing 不應造成後端 schema 變動）
  • Geo-block / IP 地區阻擋 —— 已於 2026-05-15 全域移除（見 SPEC-000 v0.1.5 changelog）

2. Variant Matrix

每個 landing variant 必須在其 package.json 之 prophetica.variant 欄位宣告：

{
  "name": "@prophetica/landing-sports",
  "prophetica": {
    "variant": {
      "id": "sports",
      "regions": ["TW", "JP", "KR", "VN", "MY", "PH"],
      "product_lines": ["sports"],
      "design_theme": "apple",
      "deployment": {
        "domain": "sports.prophetica.example",
        "path_prefix": "/"
      },
      "owner": "marketing",
      "launched_at": "2026-06-01",
      "retired_at": null
    }
  }
}
欄位強制說明
id✅kebab-case，全域唯一；用於 observability dimension variant_id
regions✅ISO 3166-1 alpha-2 陣列；可包含多個
product_lines✅必須是 packages/proto 中已定義的 product enum 子集
design_theme✅packages/design-tokens 中 registered theme，或 variant-local override
deployment.domain✅Cloudflare Pages project 對應的對外域名
deployment.path_prefix可選預設 /，多個 variant 共用同域名時必填且不可重疊
owner✅內部 team 名稱，用於 PR review routing
launched_at✅ISO 8601 日期；未上線可暫設未來日期
retired_at可選null = 仍在線

2.1 命名規範

目錄名為 apps/landing-{slug}/，{slug} 為人類可讀識別字（kebab-case）。slug 不強制編碼 region / product —— 真正的 region × product matrix 由 §2 的 manifest 欄位宣告，目錄名只需易讀且全域唯一。

apps/landing-{slug}/          ← directory
@prophetica/landing-{slug}    ← package name
variant.id === {slug}

範例：
  apps/landing-sports/      → id "sports"，product_lines ["sports"]，regions 多國
  apps/landing-tw/          → id "tw"，regions ["TW"]，product_lines 多條
  apps/landing-jp-casino/   → id "jp-casino"，region + product 皆專一

3. 強制共用（不可偏離）

共用對象來源強制理由
API 契約packages/protoSPEC-014 §6 single source of truth；landing 不准自定義新欄位
HTTP / gRPC clientpackages/ts-sdksession、idempotency key、tracing header 一致
合規元件packages/ui/compliance/*見 §3.1
Observability eventspackages/ts-sdk/analyticsevent name 與 dimension key 統一，SPEC-007 §3 / SPEC-020
版本SPEC-017 §3 鎖定的 Next.js / React / @cloudflare/kumo多 variant 不能版本漂移，避免 monorepo build 矩陣爆炸
TypeScript / ESLint config各 app tsconfig 對齊 apps/web baselinePR 自審門檻一致

3.1 合規元件清單（packages/ui/compliance/*）

下列元件必須從 packages/ui/compliance 引入，不准在 variant 內 fork 或重寫：

Component對應 SPEC用途
<KycEntryButton />SPEC-005註冊 / 升級 Tier 2 CTA
<ResponsibleGamingBanner />SPEC-006 §3站台底部強制顯示
<ResponsibleGamingModal />SPEC-006 §4自我排除 / 限額 / 冷靜期 entry
<AgeConfirmationGate />SPEC-006 §2首訪 ≥18 確認
<NeutralPlatformDisclosure />SPEC-009 §1「中立撮合，平台不下場」聲明
<AnalyticsBoundary />SPEC-007 §3 / SPEC-020統一事件 emitter wrapper

如果某個 variant 的視覺設計需要客製這些元件的外觀，只能透過 props / theme tokens 改外觀，不能 fork 邏輯。若 props 不夠用，回頭擴 packages/ui/compliance，不是在 variant 內另起爐灶。

實作狀態（2026-05-16）：packages/ui/compliance/* 尚未實作。在這些元件落地前，新 variant 應以 inline 內容滿足合規可見性要求（age gate、RG 通知、平台中立聲明），並於該處標註 SPEC-021 §3.1 TODO，待元件 ship 後替換。apps/landing-sports 即為此過渡模式範例。

4. 可分歧層面（自由發揮）

對象可分歧備註
Hero / Marketing copy✅i18n 與 brand tone 完全自治
字體 / 配色 / 動效✅透過 packages/design-tokens 的 theme override
Layout / Page composition✅但 §3.1 合規元件必須出現在 viewport 上
Product surface✅在 variant 宣告的 product_lines 範圍內
Onboarding flow 視覺✅但 KYC / RG 邏輯走共用元件

4.1 視覺方向之 prior art

design/ 目錄已有三份視覺探索可供 variant 設計起點：

  • design/landing-apple.html + design/DESIGN-apple.md — Apple 風格（精簡、留白、產品攝影）
  • design/landing-airbnb.html + design/DESIGN-airbnb.md — Airbnb 風格（社群感、溫暖配色、cards）
  • design/landing-lamborghini.html + design/DESIGN-lamborghini.md — Lamborghini 風格（高反差、賽車美學）

這三份是非 production 視覺探索，新 variant 可挑一個方向延伸或新創。新方向之 theme tokens 須補進 packages/design-tokens 並於 PR 描述引用 design/DESIGN.md 設計系統章節。

5. 部署拓樸

5.1 Cloudflare Pages 多 project

每個 variant 對應一個獨立 Cloudflare Pages project：

apps/landing-sports/wrangler.toml    → CF Pages: prophetica-landing-sports
apps/landing-jp-casino/wrangler.toml → CF Pages: prophetica-landing-jp-casino

CI 部署條件：只有該 variant 的目錄或其依賴的 packages/* 變動時才觸發。turbo.json 的 task（build / lint / typecheck / test / dev）為 workspace-generic，新 variant 由 pnpm-workspace.yaml 的 apps/* glob 自動納入，無需修改 turbo.json。

5.2 域名策略

兩種策略可並存：

A. 不同子域（推薦給「不同地區市場」）

tw.prophetica.example  → apps/landing-tw
jp.prophetica.example  → apps/landing-jp-casino
kr.prophetica.example  → apps/landing-kr-events

B. 同域不同 path（推薦給「不同產品線」）

prophetica.example/sports  → apps/landing-sports
prophetica.example/casino  → apps/landing-casino
prophetica.example/events  → apps/landing-events

混合：地區走子域、產品線走 path：

tw.prophetica.example/sports
tw.prophetica.example/casino
jp.prophetica.example/sports

5.3 Cookie / Session 邊界（與 SPEC-010 §2 對齊）

  • 預設：landing 不持有 session cookie；「立即註冊」CTA 跳轉到 apps/web 之 /auth/signup，登入後 redirect 回原 landing 之指定 path
  • 跨子域共享 session：若需要 landing 顯示「已登入」狀態，cookie domain 設為 .prophetica.example（apex），所有子域共用
  • 產品線 path 切分：同 apex 下不同 path 自動共用 cookie，無需特殊設定

SameSite=Lax、Secure、HttpOnly 強制，無例外（SPEC-010 §2）。

6. 新 landing 上線檢核清單（PR Gate）

新增 apps/landing-* 的 PR 必須在 description 勾選下列項目，缺一則 reject：

## SPEC-021 New Landing Variant Checklist

### 宣告
- [ ] package.json 之 prophetica.variant 完整填寫（§2 全欄位）
- [ ] variant.id 全域唯一（CI script 掃描所有 apps/landing-*/package.json
      之 prophetica.variant.id 驗證）

### 強制共用
- [ ] 引用 packages/proto 與 packages/ts-sdk，無自定 API 呼叫
- [ ] 引用 packages/ui/compliance/* 列出之全部元件，未 fork
      （元件未 ship 前以 inline 內容過渡，標註 §3.1 TODO）
- [ ] Analytics 透過 <AnalyticsBoundary />，event name 對齊 SPEC-020 dictionary
- [ ] Next.js / React / Kumo 版本對齊 SPEC-017 §3 lock file

### 合規可見性
- [ ] <AgeConfirmationGate /> 在首訪流程出現
- [ ] <ResponsibleGamingBanner /> 出現在 viewport（首屏可不出但 footer 必到）
- [ ] <NeutralPlatformDisclosure /> 在 footer 或 about 頁
- [ ] KYC CTA 文案經 legal 過審
- [ ] 無「保證」「穩賺」「平台對沖」「平台造市」等違反 SPEC-009 §1 的字眼

### 部署
- [ ] wrangler.toml 指向獨立 Cloudflare Pages project
- [ ] 域名 / path_prefix 與既有 variant 無衝突

### 觀測
- [ ] variant_id 已加入 SPEC-007 §3 metric / log 標籤
- [ ] Lighthouse CI（Performance / Accessibility / SEO）≥ 90

6.1 4-eye review 要求

  • 必須 Tech Lead + 該 variant owner 雙簽
  • 若 variant 含新地區（regions 出現未曾上線的國家代碼）→ 加要求 legal 審 marketing copy

[ proposal ] → [ design review ] → [ implementation ] → [ §6 PR gate ] → [ launched ]

                                                                              ▼
                                                                       [ monitoring ]
                                                                              │
                                                          ┌───────────────────┤
                                                          ▼                   ▼
                                                    [ retiring ]         [ active ]
                                                          │
                                                          ▼
                                                    [ retired ]
                                                    （保留 6 個月供 SEO / 直連流量 redirect）

7.1 退役流程

  1. package.json 之 prophetica.variant.retired_at 填上日期
  2. variant 域名加 301 redirect 到指定的存活 variant
  3. 該 variant 的 Cloudflare Pages project 標記 inactive，6 個月後刪除
  4. SPEC-000 changelog 補一筆退役紀錄
  5. observability dashboard 之 variant_id filter 加入退役標記，歷史資料仍可查

7.2 A/B 測試

A/B 不算新 variant，由單一 variant 內部以 feature flag 處理（SPEC-013 或對應 flag 服務）。禁止為 A/B 而新增 apps/landing-* 目錄。

8. Anti-patterns（不要做）

  • ❌ landing 內直接 fetch(API_URL)：必須走 packages/ts-sdk
  • ❌ landing 內定義新的 analytics event name：必須在 SPEC-020 dictionary 補定義後共用
  • ❌ landing 內 fork 合規元件：擴 props 或在 packages/ui 加新 variant
  • ❌ 為了視覺需求調整 Next.js / React 版本：違反 SPEC-017 §3
  • ❌ 用環境變數開關決定「要不要顯示 KYC entry」：合規元件強制存在，不可條件性
  • ❌ 把產品線判斷邏輯寫在 landing：產品線由 prophetica.variant.product_lines 宣告，後端 service 與 admin 直接讀此 metadata

9. Open Questions

  • A/B variant 的 traffic split 機制（Cloudflare Workers edge split vs Next.js middleware vs 第三方 LaunchDarkly / GrowthBook）
  • 多 variant 共用 cookie 時的 RG self-exclusion 跨 variant 一致性（SPEC-006 §4 是否需要中央 service 取代 cookie）
  • design tokens override 的版本控管：variant 鎖 token 版本 vs 隨主版滾動
