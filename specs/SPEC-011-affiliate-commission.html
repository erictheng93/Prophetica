1. Objective

在遵守法律與合規原則下，建立可被稽核、可被追蹤的推薦傭金體系。現階段僅啟用「第一層推薦」作為營運主線；同時保留後續經治理程序展開分層/多層機制的制度空間。

2. 法律邊界（先擺最前面）

2.1 MLM 紅線

依台灣公平交易法 §23 與多層次傳銷管理法，禁止：

  • 主要收入來自介紹下線而非銷售
  • 入會費（推薦人從新人入會費抽佣）
  • 三層以上的金字塔結構（嚴格說兩層以上即危險）

2.2 安全設計

採用「單層介紹費 + 銷售佣金」設計，不做傳統意義上的多層代理。

本規格第一期以「單層」作為實際執行設定。是否啟動分層（多層）模式，需另行進行法務與合規稽核並由治理決策批准後，才可納入後續版本。

2.4 可擴展分層原則（治理條件）

  • 保留「未來可擴展」是為了避免重構阻礙營運；現階段不新增分層計算權益。
  • 啟用新一層前，必須先完成三方確認：產品、法務、合規。
  • 新版本必須先定義分層觸發條件、補償邊界、責任歸屬與追溯規則，並更新 SPEC-000 的交叉決策紀錄。
設計 內涵
介紹獎勵（一次性） 介紹人在被推薦人首次儲值達閾值時獲得固定獎勵點數，僅一層
交易佣金（持續） 介紹人從被推薦人的交易手續費中抽取百分比，僅一層
不存在「下線的下線」 推薦關係只有一層，不形成樹狀結構
介紹獎勵以點數發放 不是現金，符合「站內虛擬道具」性質

原 PRD「總代 → 代理 → 業務」的多層架構不採用。技術實作上仍可記錄推薦樹用於分析，但不據此計算佣金。

2.3 「業務」角色（B2B 簽約推廣）

對於希望以「業務」身份大規模推廣的合作方：

  • 必須簽訂正式 B2B 合約（與 Operating Co.）
  • 業務以個人名義開立發票（自由業）或公司對公司結款
  • 業務的「推薦獎勵」歸入廣告 / 行銷費用會計科目
  • 與一般玩家推薦走完全分開的計算與發放路徑

3. 推薦關係模型

3.1 資料結構

本節只保留行為規則：每位玩家只能被一位介紹人綁定，且綁定點在註冊時落定且不可更改（first-touch）。

具體欄位、索引與遷移流程請參考 implementation plan。

3.2 推薦碼生成

每位玩家於註冊成功後同 transaction 內自動分配唯一推薦碼。

3.2.1 演算法（G-1 釘死）

推薦碼需兼顧唯一性、不可推回原始使用者、且不影響註冊流程，完整運算規則與碰撞處理（重試與告警）放在 implementation plan。

推薦連結格式持續維持可點擊分享形式，註冊頁僅採用首次出現的 referral code。

3.3 推薦關係建立規則

  • 每位玩家最多被一人介紹（first-touch attribution）
  • 推薦關係於玩家註冊時鎖定，不可後續更改
  • 推薦碼不可由親屬 / 同連結帳號之間使用 — 由 SPEC-010 §4.2.1 user_link_score 之子規則 affiliate_kinship_link 偵測，G-2 細化如下：

3.3.1 親屬偵測子規則 affiliate_kinship_link（G-2）

親屬/可疑關聯行為列為防濫用防線。具體特徵欄位、權重模型與執行時序移至 implementation plan，由 SPEC-010 的規則與 Compliance 流程做聯動。

實作需保留本規格提到的狀態轉換（如 pending_review / disqualified）並能與人工複核結果保持一致。

4. 佣金計算

4.1 介紹獎勵（一次性，延遲 30 天發放，G-3）

4.1.1 達標條件（觀察期內須全部滿足）

被推薦人於註冊後 30 天觀察期內須累計滿足：

  • 首次儲值 ≥ TWD 500
  • 完成 KYC Tier 1
  • 觀察期內成交至少 5 筆訂單（防只儲值不交易）
  • 觀察期內無 chargeback（呼應 SPEC-016 §6.1，chargeback ≥ 1 觸發永久封號則直接 disqualify）
  • 觀察期結束時無 §3.3.1 親屬偵測 pending_review 未裁決狀態
  • 觀察期結束時 referrer 帳號自身正常（未凍結 / 未封號）

4.1.2 獎勵時點（delayed-issue 模型）

設計維持 延遲發放，避免介紹人未達條件後需回收已發放金額，且便於對應 INV-6 的出入帳原則。

觀察期結束批次裁決與入帳時點的實作節奏（含排程時間、狀態更新時機）由 implementation plan 定義。

  • referred 進入觀察期後滿足條件才可 qualified 並觸發介紹獎勵。
  • 介紹獎勵為固定 100 點數；被推薦人註冊獎金 50 點數。

4.2 交易佣金（持續，獨立每日批次 txn，G-4）

被推薦人每筆成交產生的手續費中：

  • 平台預設以「佣金百分比（%）」計算 referrer 可得比例。
  • 平台官方管理員可隨時調整該百分比，並保有全域或代理別設定的營運權限。
maker_fee × 佣金百分比 → referrer
taker_fee × 佣金百分比 → referrer

4.2.1 帳本流（與 trade transaction 嚴格分離）

G-4 釘死：交易佣金與 trade hot path 帳本分離，交易主帳本仍維持既有規則，commission 僅以每日批次方式入帳。

實作細節（Kafka topic、worker、每日批次、idempotency key、去重策略）放在 implementation plan。

4.2.2 Staging 表

commission_accruals 作為交易佣金前置暫存，欄位、索引、唯一鍵（trade_id）與 paid_out 流程詳見 implementation plan。

4.3 佣金期限

交易佣金僅持續被推薦人註冊後 12 個月，之後不再計算。

設計目的：防止「躺賺」，鼓勵推薦人持續推廣新人

4.4 反作弊規則

  • referrer 與 referred 為同 IP / 同 device fingerprint / 同 KYC 證件 → 由 §3.3.1 affiliate_kinship_link 偵測標記 pending_review，30 天觀察期到期未通過裁決則 disqualified，從未發放（呼應 G-2）
  • referred 沒有真實交易（僅儲值不交易）→ §4.1.1 「成交至少 5 筆」未達 → disqualified，從未發放
  • referrer 帳戶被標記異常（凍結 / 封號 / EDD pending） → 觀察期到期時若仍異常 → 介紹獎勵跳過本帳號永不發放（不留 pending dangling），交易佣金亦自停止
  • referred 退款 / chargeback（G-5 細化，呼應 SPEC-016 §6.1 chargeback ≥ 1 永久封號）：
    • 介紹獎勵：依 §4.1.2 延遲發放模型，觀察期內 referred chargeback → disqualified，referrer 從未收到 → 不需 clawback、不破 INV-6
    • 交易佣金（已過觀察期之 referred）：referred 一旦 chargeback ≥ 1 → SPEC-016 §6.1 永久封號 → 後續無交易 → 持續佣金自然停止
    • chargeback 之前已支付給 referrer 的交易佣金：不追回。理由：(a) referrer 為善意第三方，無從預知 referred chargeback；(b) 追回會破 INV-6 outflow 白名單，需新增 carve-out 反 R-1 紅線設計意圖；(c) 單筆 referred 之累計 commission 通常 ≪ 100 TWD，業務上可吸收為 marketing acquisition cost。本決策對應 SPEC-002 v0.1.8 INV-6 chargeback carve-out 不擴及 affiliate；wallet-ledger-service migration 之 trigger 維持原 SPEC-002 §5 INV-6 名單即可

4.5 帳本記錄

呼應 SPEC-002 §4.3 direction 規則（G-6 補 sign convention 說明）：

  • direction = +1 ≡ 借方（debit）：對 Expense / Asset / Player.Locked 表示金額增加；對 Liability / Revenue 表示減少
  • direction = -1 ≡ 貸方（credit）：對 Expense / Asset / Player.Locked 表示減少；對 Liability / Revenue 表示增加

Player.Wallet.* 為 liability 類別 → direction = -1 表示玩家錢包點數增加（平台對玩家負債增加）。

4.5.1 介紹獎勵（一次性，§4.1.2 達標 batch 觸發）

帳本方向及 Entry 結構定義移到 implementation plan，規格保留借貸正負與科目方向意圖，不直接展開欄位明細。

4.5.2 交易佣金（持續，§4.2.1 每日 batch）

交易佣金入帳帳本方向與約束檢查方式，請依 implementation plan 實作。規格層維持「發放方向為 referral player inflow」的行為規則即可。

5. 推薦人後台

5.1 自助介面

每位玩家都可在個人頁查看：

  • 已成功介紹人數（status = 'qualified' 之 referrals 計數）
  • 累計獲得獎勵（介紹獎勵 + 交易佣金分項顯示）
  • 過去 30 天 / 12 個月歷史（時間序列圖表）
  • 推薦清單（flat list，僅一層）：你介紹的人 — 列出每位 referred 之 username（僅顯示前 3 字 + 後 1 字、其餘以 * 遮蔽，避免 PII 揭露）、註冊時點、status（pending / qualified / disqualified / pending_review / pending_eddreview）、累計貢獻佣金（G-7：原「推薦樹結構」用詞改為「推薦清單」，避免暗示 MLM 樹狀結構，呼應 §2.2「推薦關係只有一層，不形成樹狀結構」）

5.2 業務專屬後台（B2B 簽約）

針對簽約業務的進階介面：

  • 細項 dashboard：每位被推薦人的活動、儲值、交易量、佣金
  • 月度報表 PDF 下載
  • B2B 酬勞月結（業務 invoice + Operating Co. 應付帳款流程，現金支付至業務指定銀行帳戶；完全與玩家錢包點數無關 — 詳見 §6）
  • 稅務文件：發票上傳、扣繳憑單下載

紅線提醒：本後台不提供任何「玩家錢包點數 → 現金」轉換功能。業務若同時是平台玩家身份，其玩家錢包點數仍不可回兌（呼應 §6.2）。

6. 操作與交易留痕（全體操作者）

本節不列技術欄位；僅規格層面定義「誰做了什麼要留在場域可查」。

  • 交易留痕：所有傭金、點數、補償、調整、退款、回滾、註銷等交易類動作，無論由系統自動或人工觸發，都必須形成可追溯交易紀錄。
  • 管理員留痕：平台營運、客服、風控、合規、技術、法務的資料變更、權限調整、批准/否決、配額變更、提現授權等，皆需保留可稽核操作紀錄。
  • 代理留痕：代理端發起的推薦名單維護、資源申請、活動名額、額度申請與調整、審核回覆，都需一併紀錄；同一動作可由後續管理層覆核，但不得刪除或覆寫先前紀錄。
  • 抽佣率調整留痕：官方管理員調整代理抽佣 % 數，需留存前後值、調整人、調整時點、適用範圍與授權依據，且可回溯。
  • 紀錄原則：任何歷史記錄不得刪除，需更正者以新增紀錄補記，並保留前後狀態與授權鏈。
  • 合規衔接：與管理權限簽核有關之留痕，應可直接對應本規格或既有治理規格中的審核流程（例如 multi-sig 與 4-eye 類需求）。

與本規格不符的留痕實作細節、欄位定義、保存年限、資料庫實作，請放在 implementation plan 或執行書完成。

7. 業務 / 大型推廣方支付路徑

核心原則（R-1 紅線）：業務 B2B 路徑與玩家點數系統完全分離，永遠不透過任何技術路徑將「玩家錢包點數」轉換為「法人應付帳款」或「現金」。此限制為 zero tolerance，無任何例外（含 B2B 合約包裝、業務身份升級、自願捐贈等）。對應 SPEC-000 §5 R-1。

6.1 業務簽約模型（獨立法律關係）

業務 B2B 為全新獨立之法律關係，非「玩家身份升級」：

業務（自然人個人 / 公司法人）── 簽訂 B2B 合約 ──→ Operating Co.
                                                    │
                                                    ▼
業務每月依合約 KPI 提交 invoice（介紹合格玩家數 × 單價 + 帶量階梯獎金等）
                                                    │
                                                    ▼
Operating Co. 從**營運帳戶**（非託管帳戶）以**現金**支付至業務指定銀行帳戶
                                                    │
                                                    ▼
業務自行報稅（境外收入或本地收入依其所在國法律）

關鍵特徵：

  • 業務酬勞不基於該業務「玩家錢包」內任何點數餘額
  • 業務酬勞不從任何玩家錢包出口
  • 業務酬勞為獨立 KPI 計算結果，於 §6.4 之 Expense.AffiliatePartnerFee 會計科目記錄
  • 業務 B2B 合約由 Operating Co. 律師起草，明示「不含任何玩家點數轉換條款」

6.2 雙身份隔離（業務同時是平台玩家）

若同一自然人同時為「業務」與「平台玩家」：

維度 玩家身份 業務身份
user_id 例：user_42 例：partner_007（獨立 id）
帳本軌跡 Player.Wallet.42 點數 Liability.AccountsPayable.partner_007 應付帳款
收入性質 點數遊戲獎勵（不可回兌） 現金 KPI 酬勞
支付通路 站內錢包（永不出口） 銀行 API 匯款（營運帳戶）
稅務 玩家獎勵不需報稅（虛擬道具） 業務酬勞須報稅

執行要求：

  • 兩個身份在系統內為完全獨立之 user_id 與帳本軌跡，不可共用同一 wallet
  • 玩家身份之錢包點數遵守「不可回兌」原則 — 即便該人為簽約業務，也不能將其玩家錢包點數轉為現金 / 應付帳款 / 任何形式之兌換
  • 後台需強制 KYC 證件對照偵測「業務 partner_id」與「玩家 user_id」之自然人關聯，並於業務 KPI 計算 query 中排除「業務本人作為玩家」之自我介紹（防止套自身行為，呼應 §4.4 反作弊）

6.3 帳本層強制執行（呼應 SPEC-002 §5 INV-6）

本節不提供實作欄位與 SQL；重點保留為產品規格：Player.Wallet 對 outflow 的目的地為法規白名單，凡涉及玩家點數轉入現金或業務應付皆禁止。

INV-6 的檢查條件、資料庫約束實作與 sentinel-scan 規格，詳見 implementation plan。

6.4 業務酬勞會計科目（與玩家獎勵嚴格分離）

業務 B2B 酬勞與玩家獎勵在帳本層完全分離：

費用（Expenses）
  ├─ Expense.AffiliateCommission       玩家介紹獎勵 / 交易佣金
  │                                    └─→ 對手方為 Player.Wallet.{referrer}
  │                                        （仍是點數，不可回兌；呼應 §4.5）
  │
  └─ Expense.AffiliatePartnerFee       業務 B2B 合約酬勞
                                       └─→ 對手方為 Liability.AccountsPayable.{partner_id}
                                           （現金應付，與玩家錢包零交集；呼應 §6.1）

兩者永遠不相互轉換、相互抵銷、相互沖銷。月結時各自獨立揭露。SPEC-002 §4.2 Chart of Accounts 將同步補上 Expense.AffiliatePartnerFee 與 Liability.AccountsPayable.* 子科目。

8. 稅務處理

7.1 玩家層級

  • 玩家獲得的點數獎勵不是現金所得，依台灣稅法不需報稅
  • 但B2B 業務獲得的 B2B 收入須報稅
  • 玩家若達一定推廣規模（每年介紹超過 X 人）→ 系統提醒可另外簽約 B2B 業務獲得現金 KPI 酬勞；此業務簽約不會將玩家現有錢包點數轉為現金（玩家錢包點數永遠不可回兌），業務酬勞為新起算之 B2B 合約收入（§6.1），與玩家身份的點數歷史完全分離

7.2 平台層級

  • 介紹獎勵與交易佣金記入 Expense.AffiliateCommission
  • 月結提供財務 / 會計 / 稅務團隊
  • 跨境支付（業務在不同國家）依執照地稅法處理

7.3 扣繳義務

  • B2B 業務若為台灣居民，依所得稅法扣繳 10%
  • 跨境支付依雙邊租稅協定處理
  • 系統需自動產生扣繳憑單

9. 監管揭露

執照地監管可能要求揭露：

  • 推薦獎勵總額（月 / 季）
  • B2B 業務名單（執照地律師審閱）
  • 大額推薦獎勵個案（單月 > USD 5,000 等值）

10. 驗收條件

9.1 後端（Codex owner）

  • 玩家可在第一層規則下完成推薦關係建立、保留狀態、上限觸發與人工回審流程
  • 介紹獎勵完成 30 天觀察期裁決後發放；不符合條件不發放
  • 交易佣金持續計提可見且可回溯，且可在達上限時暫停新增佣金
  • 介紹 code / 狀態轉換與親屬複核不影響被推薦人註冊有效性
  • 任何「玩家點數 -> 現金 / 應付帳款」路徑在產品行為上不得發生
  • 達標上限與異常回溯提示可被用戶與客服查證
  • 本節工程實作細節已落到對應 implementation plan 與執行書
