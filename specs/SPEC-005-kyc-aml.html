1. Objective

建立分層的客戶身份驗證（KYC）與反洗錢（AML）系統，以最低摩擦、最高合規覆蓋的方式處理玩家入場、儲值、交易、結算過程的身份與風險審查。不自建 KYC 流程，採用業界 SaaS 整合節省成本與法律風險。

2. KYC 分層（Tiered KYC）

2.1 三層設計

層級 觸發 驗證內容 月收入申報 限制
Tier 0 訪客 未註冊 / 未儲值 無 — 僅瀏覽公開市場、看歷史結算
Tier 1 基礎 完成註冊 + 首次儲值 Email、手機 OTP、生日（≥18）、首發國對應證件驗證（見 §2.4） 不申報（保留 NULL） 累計儲值 < 金幣 30,000 / 月、單筆 < 金幣 5,000
Tier 2 標準 累計儲值達 Tier 1 上限或自願升級 證件 OCR + 自拍人臉比對 + Liveness Detection + 地址證明 可選申報（鼓勵以解鎖更高上限） 累計儲值 < 金幣 300,000 / 月（已申報）；金幣 100,000 / 月（未申報）
Tier 3 強化（EDD） Tier 2 上限 / 高風險訊號 / 平台主動觸發 收入來源證明、銀行對帳單、視訊驗證、PEP/Sanctions 篩查 必填並核對證明文件 個案核定（依執照地法規）

2.1.3 peer_transfer 准入規則

本節定義會員 → 會員轉點 / 贈點（SPEC-002 §4.4.7 peer_transfer_*）之 KYC 准入閘門與 tier 階梯上限。產品定位提醒：平台僅提供儲值入金通道、無任何銅幣兌換 / 贖回 / 退費出口；會員間轉點 / 贈點為唯一的會員間 wallet-to-wallet 主動流通機制（非撮合），因此 KYC + AML 兩道閘門皆收緊。

KYC tier 門檻

角色 最低 tier 說明
發送方（sender） TIER_1 避免 Tier 0 訪客觸發 peer_transfer 製造 fake wallet 來源；Tier 1 已含手機 OTP + 證件驗證 + 18 歲 gate
接收方（recipient） TIER_1 避免 Tier 0 / 殭屍帳號被當 layering 終點；接收方為 Tier 0 → 平台回 recipient_kyc_tier_insufficient，UI 引導對方先升級 Tier 1 再領取

任一方未達 TIER_1 → SPEC-002 §4.4.7.1 之准入檢查回 kyc_tier_insufficient，不寫入帳本。

單日 / 單月轉出上限（依發送方 KYC tier 階梯）

發送方 tier 單日 peer_transfer 轉出累計上限 單月 peer_transfer 轉出累計上限 備註
TIER_0 — — 禁止使用（見上表）
TIER_1 金幣 1,000 金幣 10,000 對齊 Tier 1 之儲值上限（單筆 < 金幣 5,000 / 累計儲值 < 金幣 30,000）之安全比例（單日 ≈ 20%、單月 ≈ 33% 儲值上限）
TIER_2 未申報 金幣 10,000 金幣 50,000 對齊 Tier 2（未申報）之 金幣 100,000 / 月儲值上限的 50%
TIER_2 已申報 金幣 30,000 金幣 150,000 對齊 Tier 2（已申報）之 金幣 300,000 / 月儲值上限的 50%
TIER_3 個案核定 個案核定 由 Compliance + admin console 設定個別玩家上限
  • 累計口徑：以 peer_transfer_send 已 commit 之 amount（不含手續費）為準；自動退回（24h timeout）與接收方主動拒收已退回之金額不計入累計上限（手續費仍計入平台收入，與本表無關）。
  • 滑動窗口：「單日」= 過去 24 小時 rolling window；「單月」= 過去 30 天 rolling window；非自然日 / 自然月切分，避免月底 / 跨日繞過。
  • 超額處置：超過上限 → SPEC-002 §4.4.7.1 之准入檢查回 peer_transfer_limit_exceeded，提示玩家升級 tier 或等待窗口刷新。
  • 接收方上限：v1 不對接收方設累計上限（接收為被動行為），但 SPEC-010 §4.2.5 PT-1 / PT-2 / PT-3 之 post-transfer 偵測仍會抓異常入帳模式。

KYC 中途降級 / 凍結之既存 PendingTransfer 處置

  • 發送方於 PendingTransfer 期間進入 Player.Frozen.* 或 KYC tier 被人工降至 TIER_0 → 既有 pending 等待原 24h 自動退回路徑（peer_transfer_refund），不提前強制退回（避免 race 與重複 entry）；新 peer_transfer_send 直接拒絕。
  • 接收方於 PendingTransfer 期間進入 Player.Frozen.* 或 KYC tier 被人工降至 TIER_0 → 既有 pending 立即觸發 peer_transfer_refund（refund_reason = 'compliance_block'，呼應 SPEC-002 §4.4.7.3 Phase 2b）。
  • 雙方同時凍結 → 接收方優先規則勝出（強制 refund）。

2.4 Tier 1 多市場身份證件驗證

5. 證件儲存與隱私

5.1 儲存策略

  • 不將證件影像存於應用 DB
  • KYC provider 提供之證件影像 URL 透過後端代理 + 短期 token 取用
  • 內部歸檔副本：每日批次下載至 R2（EU region）+ Object Lock，AES-256 at-rest 加密
  • 加密金鑰由 Vault 託管，最小權限存取（僅合規審計人員）

5.2 個資去識別化

  • 證件號碼不明文存 DB，僅存 SHA256(salt + ID number)
  • 比對時：對輸入 ID 計算同樣 hash 後比對 hash
  • 鹽值由 Vault 管理，每年輪換（換鹽後舊資料保留供稽核）

5.3 即時取圖代理

KYC 審核人員需於後台查看 KYC provider 收集的會員證件影像（ID 正反面、自拍、Liveness 截圖）。影像不直接由前端向 KYC provider 取用，而是透過以下代理鏈路，確保金鑰不洩漏至瀏覽器： 

Admin 瀏覽器 → api-gateway → kyc-service → KYC provider API

5.3.1 端點定義

端點 說明
GET /v1/internal/admin/kyc/members/{user_id}/documents 列出該會員所有已上傳文件的元資料（doc_id、類型、上傳時間）；不含影像 bytes
GET /v1/internal/admin/kyc/members/{user_id}/documents/{doc_id} 代理回傳單張影像 bytes；Content-Type 依 KYC provider 原始回應透傳

5.3.2 Binding Invariants

  • user_id → applicant_id 解析僅在 kyc-service 內部完成。api-gateway 與 Admin 前端只知 user_id；applicant_id 永遠不出現在公開或內部 admin API 的 URL / 回應中。
  • doc_id 為 kyc-service 的 opaque 識別符。kyc-service 在資料庫中維護 (user_id, doc_id) 的綁定；任何 doc_id 若未綁定至請求中的 user_id，一律回傳統一 404 Not Found，回應體不得揭示「doc 存在但屬於其他 user」或「doc 根本不存在」的差異（防止存在性洩漏）。
  • 影像 bytes 不得緩衝於任何中間節點。api-gateway 與 kyc-service 均以串流（streaming）方式轉發；不得將影像存於記憶體快取、磁碟或任何非 KYC provider 的持久層（R2 歸檔由 §5.4 的日批次負責，非即時代理路徑）。
  • 存取限制：呼叫此端點須持有 kyc_review 權限。MVP 階段此權限映射至 admin 與 manager 角色；affiliate 角色明確排除。

5.3.3 內部簽名機制（「短期 token」語意澄清）

§5.1 提及「後端代理 + 短期 token 取用」。此「短期 token」指的是 admin server route 向 api-gateway 發起的伺服器對伺服器簽名呼叫，並非任何可送達瀏覽器的 token。瀏覽器端僅使用 admin session cookie。具體機制如下：

  • 簽名演算法：HMAC-SHA256，涵蓋 method、path、body-hash（空 body 為空字串 hash）、timestamp（Unix 秒）、actor（操作人員 ID）、role（操作人員角色）。
  • 簽名金鑰（ADMIN_INTERNAL_CALL_SECRET）由 Vault 管理，admin server route 與 api-gateway 各持 shared secret，不寫入任何前端 bundle 或 Cookie。
  • api-gateway 驗證簽名後才轉發至 kyc-service；timestamp 偏差超過 300 秒即拒絕（防重放）。api-gateway → kyc-service 為獨立內部跳，轉發 actor / role / request-id header 供 kyc-service 稽核。
  • KYC provider API key 僅存於 kyc-service 環境變數（由 Vault 注入），不向 api-gateway 或前端透出。

5.4 R2 歸檔

為滿足監管要求的長期留存，採日批次將 KYC provider 影像下載至 Cloudflare R2：

5.4.1 存儲配置

Bucket 用途
kyc-documents 證件影像（ID 正反面、地址證明等）
kyc-liveness 自拍 / Liveness 影像與視訊截圖
  • Object Lock 保留期：7 年（WORM 模式），初始狀態標記為「待合規簽核」；合規審計人員核簽後可更新 metadata 標記，但物件本體不可刪除。
  • 加密：SSE-AES256（Cloudflare R2 服務端加密）；加密金鑰由 Cloudflare 管理，Vault 記錄存取審計軌跡。
  • 批次時間：每日 UTC 03:00（避開制裁篩查批次 UTC 02:00），由排程服務驅動（Worker Cron Trigger 或內部 cron job）。
  • 每筆物件的 key 格式：{user_id}/{doc_type}/{provider_doc_id}/{timestamp}.{ext}，確保按會員可查詢。

5.4.2 既有 wrangler.toml R2 binding 說明

apps/admin/wrangler.toml 與 apps/web/wrangler.toml 目前存有 R2 bucket binding 配置，屬歷史配置 / 待拆遷項。前端 Next.js Worker 不應擁有 KYC 影像歸檔的 R2 binding——這會使 admin / web bundle 持有不必要的 R2 存取能力，違反最小權限原則。

正確架構：R2 binding 應移至專屬的歸檔 Worker 或 kyc-service 部署配置。既有 apps/admin/wrangler.toml / apps/web/wrangler.toml 中的 KYC R2 binding 應在拆遷工作中移除，待 §5.3 取圖代理與 §5.4 歸檔批次均實作完成後統一清理。

7.2 SAR（Suspicious Activity Report）流程

可疑案件由 Compliance Officer 評估：

  1. 系統自動產生 SAR draft
  2. Compliance 補充訊息、做出判斷
  3. 確認可疑 → 提交至執照地金融情報單位（FIU）
  4. 玩家通常不通知（依當地法規，多數國家禁止 tipping off）
  5. 帳戶處置：凍結 / 限制 / 持續監控（依個案）

7.3 強制觸發 SAR 的情境

  • 單筆儲值 > 銀幣 10,000
  • 30 日累計儲值 > 銀幣 30,000
  • 不尋常下注模式（極大單筆、極端勝率玩家集中下注）
  • 玩家拒絕 KYC 升級且帳戶留有大量銅幣

8. 玩家 UX

8.1 KYC 流程設計原則

設計準則 實作
最少摩擦 Tier 1 只需 OTP + 生日，10 秒完成
進度可見 進度條 + 預估完成時間
失敗友善 失敗原因白話翻譯（不是 KYC provider 原始錯誤碼）

8.2 失敗重試

  • 同一玩家 24 小時內最多 5 次嘗試
  • 5 次後鎖定 24 小時
  • 連續鎖定 3 次 → 強制人工 review

9. 整合驗收測試

9.1 Happy Path

  • 新玩家 Tier 0 → Tier 1 註冊流程 < 60 秒
  • Tier 1 → Tier 2 升級（含 KYC SaaS 流程）端到端 < 5 分鐘
  • Tier 2 → Tier 3 升級流程含視訊驗證

9.2 失敗情境

  • KYC provider webhook HMAC 驗證失敗 → 401
  • webhook 重複送達 → 冪等
  • 制裁名單命中 → 自動凍結 + 推送 Compliance Slack
  • 玩家 KYC 失敗 → 帳戶凍結但持倉保留至結算

9.3 邊界

  • 證件過期 → 提前 30 天提醒、過期後限制儲值
  • 玩家修改個資（姓名、生日）→ 強制重新 KYC

11. 驗收條件

  • KYC provider 整合通過 Sandbox 測試（模擬 GREEN/RED/PENDING）
  • webhook HMAC + idempotency 驗證測試通過
  • 制裁名單每日 batch 篩查腳本可在 30 分鐘內掃描 1M 用戶
  • KYC 證件影像加密儲存通過 OWASP 檢核
  • PII 去識別化（hash + salt）驗證通過
  • AML 規則引擎可被 Compliance Officer 自助配置（不需工程介入）
