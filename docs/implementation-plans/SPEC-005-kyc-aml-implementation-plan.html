0. 實作狀態與 Launch Gate

  • Backend 已完成（PR #1 之前）：in-memory contract、API trait、mock provider、基本 migration、secret hardening 校準。
  • Backend P0 sprint（Codex 範圍，可立即啟動）：Postgres provider wiring、SQLx offline metadata 對齊最終 queries、SumSub / Onfido sandbox secret fallback hardening。
  • Frontend 主路徑已落地（PR #2 merged 2026-05-09）：KycIdentityProvider 抽象、Tier 2/3 state machine、Tier 3 polling fail-soft（SPEC-005a §6.1）、CSP（§8）、5 個 KYC telemetry metrics（§7.3）、Tier 3 SumSub → iProov adapter chain 骨架（§11.2）；acceptance gates 3 / 6 / 9 / 11 closed。Tier 3 stage 2 iProov real adapter 仍為 not_implemented stub。
  • Frontend 剩餘工作（blocked on SPEC-000 §5 Q-9 採購）：等 SumSub sandbox credentials 到位後（a）執行 mock → real provider 替換、（b）iProov real adapter 寫入並退掉 not_implemented stub、（c）Tier 2 SumSub iframe 真實 mount E2E 驗證、（d）webhook HMAC + GREEN/RED/PENDING replay sandbox E2E 通過。在 sandbox credentials 到位前無法啟動，且這同時是 LG-3 evidence 回填條件。
  • Public Beta blocker：真實入金 / 真實下單前，Tier 2 SumSub iframe、webhook HMAC、GREEN / RED / PENDING replay、RED→Frozen、PEP / sanctions rescan 必須 sandbox E2E 通過並回填 SPEC-000 LG-3 evidence；採購進度追蹤於 SPEC-000 §5 Q-9。

1. 實作目標

  • 完成分層 KYC（Tier 0/1/2/3）與升級流程。
  • 實作 SumSub webhook 風險事件寫入與 idempotent 保證。
  • 上線 AML 檔案、制裁名單與 SAR 觸發流程。
  • 固定 KYC / AML 風控事件與告警輸出，對齊 observability 規格。

2. 範圍與邊界

包含：kyc-service、user-service、mock-sumsub、packages/ts-sdk、apps/web 之 KYC 路徑、PostgreSQL schema、審核排程。

不含：支付、資安基底架構、客訴人員流程介面（由其他 SPEC 負責）。

3. 不變式（Invariants）

ID描述
INV-KYC-1Tier 值固定為 TIER_0 / TIER_1 / TIER_2 / TIER_3，不得出現 LEVEL_* 或 tier1/tier2 等混用字面。
INV-KYC-2user_kyc_records 不得存證件原號；僅存 hash、provider 元資料、狀態與時間軸。
INV-KYC-3同一位使用者在同一狀態轉移上不得同時存在重複未關閉 pending 記錄。
INV-KYC-4SumSub webhook 必須以 SHA256(raw_payload) 做 idempotency key；若 payload 重送不得改寫既有結果。
INV-KYC-5RED / 制裁命中為必停：不得只停留 pending，需更新為凍結或阻擋狀態。
INV-KYC-6刷新 token 中的 KYC tier 後 15 分鐘內前端可讀取到新權限（現有 access token 可容許短暫陳舊）。

4. 資料模型（PostgreSQL）

重點表（建議最小集合）：

  • user_kyc_records：tier、status、provider、applicant、document hash、review payload、sanction/pep 命中欄位。
  • kyc_webhook_events：raw_payload_sha256、review_answer、signature、processed_at、idempotent state。
  • kyc_audit_events：tier 升降與審核結果追蹤（給 compliance 查核）。
  • kyc_screening_jobs：日批次制裁篩查（status、offset、cursor、rows、runtime_s）。
  • user_declaration_history：declared_monthly_income 申報值變更與 stale 標記。

實際索引建議：user_id,status、tier,updated_at、raw_payload_sha256 unique。

5. 流程與 API 契約

5.1 Tier 1 自驗流程

  • 輸入欄位：姓名、生日、國家、文件號。
  • 執行 country rule 驗證、年齡檢查、重複 hash 檢查、自排除名單命中。
  • 驗證通過：寫入 user_kyc_records，狀態 passed，tier_1。

5.2 升級 API

  • POST /api/v1/kyc/users/{user_id}/upgrades：建立 upgrade request，回 sdk_token、target_tier、provider_applicant_id、可選 chain。
  • 可重放策略：idempotency key 由 server side 重建，避免 client 端可偽造。
  • 重複請求回傳同一 token（已存在未完成的 pending request）。

5.3 Webhook 入口

  • POST /api/internal/webhooks/sumsub：驗證 HMAC-SHA256（或供應商指定 hash），失敗 401。
  • 狀態映射：GREEN→passed；YELLOW→pending；RED→frozen。
  • 制裁/PEP 命中覆蓋 review_result。
  • 事件發布：kyc.events 至 user-service 與審計通道。

5.4 查詢 API

  • GET /api/v1/kyc/users/{user_id}/overview：回傳有效 KYC 狀態、tier、sanction flag、申報收入。
  • GET /api/v1/kyc/users/{user_id}/events：顯示最近審核歷程。

6. 前置規則（跨模組）

  • SPEC-006 會讀取 declared_monthly_income：未申報時回傳 NULL。
  • SPEC-005a 會使用同一個 start_upgrade token contract。
  • SPEC-007 需要監控 webhook queue lag、kyc failure ratio、idempotent retry 次數。

7. 排程與作業

  • 每日 UTC 02:00：制裁名單 batch 篩查 Tier 2+ 全部用戶，超過門檻自動標記 frozen。
  • 每月 1 次：monthly KYC report 產檔並上傳到監管/稽核 bucket。
  • 每日夜間：declared_monthly_income stale 標記更新。
  • 異常告警：webhook 60 分鐘內無法處理 > N 筆則告警。

8. 安全與 PII

  • 證件號、不完整日誌不得寫 log。
  • PII hash 僅可於 hash 欄位與 audit 中保留少量 metadata。
  • KYC secret（sumsub webhook secret、SALT、JWT 相關）統一由 Vault 管理，不可硬編碼於 env file。

9. 驗收清單

  • SumSub webhook 重播 5 次，僅第一筆生效。
  • 重複 upgrade click 不產生第二筆 pending request。
  • Tier 1 自驗可在 1 分鐘內完成（模擬環境）。
  • RED / sanction 命中能封鎖下單與儲值。
  • AML daily scan 在 30 分鐘內完成並有對帳報告。
