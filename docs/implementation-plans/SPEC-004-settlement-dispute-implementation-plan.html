SPEC-004-settlement-dispute implementation plan

版本： v0.1.2
對應規格：SPEC-004-settlement-dispute.html
範圍：Oracle 提交與驗證、爭議裁決、結算批次、取消/平局處理、公告推播、監控告警

1. 目標與非目標

  • 提供可落地的結算/爭議系統實作序列：OPEN/CLOSED/PENDING/DISPUTED/SETTLING/SETTLED/CANCELLED 全流程。
  • 確保任一市場在一個結算窗口內只產生一次最終結算結果，避免重複發放。
  • 非目標：交易撮合、帳本資產服務核心入帳邏輯（仍依 SPEC-002/SPEC-003 既定規格實作）。

2. 核心資料模型與欄位

  • 使用 oracle_submissions、dispute_resolutions 及既有市場/持倉/帳本相關資料源。
  • 結算結果狀態欄位至少包含：market_id、status、state_version、settles_at、dispute_deadline、updated_by、updated_at。
  • 需保存 Oracle 證據與決策鏈 Hash：原始證據 URI、證據清單、提交者、提交時間、簽名摘要、決策結果、投票意見。

2.1 Invariants（必須成立）

ID不變式
INV-SET-1 任一市場在同一時刻只能有一個結算階段有效（狀態欄位唯一且具線性可追溯版本）。
INV-SET-2 一旦進入 SETTLING，該市場在結算完成前不得再次進入 PENDING。
INV-SET-3 同一市場同一結算輪次的結算交易僅可提交一次（防重複 payout）。
INV-SET-4 DISPUTED 需保留可驗證決策證據與投票紀錄，且結果可追溯至 2-of-N 前置簽核。
INV-SET-5 取消（CANCELLED）後不得再進入 SETTLING。

3. 狀態機實作

  1. OPEN → CLOSED：市場關閉時立即停止可成交行為，清理未成交訂單。
  2. CLOSED → PENDING：接收至少兩位 Oracle 的一致初判結果後進入。
  3. PENDING → SETTLING：無申訴或申訴結果駁回。
  4. PENDING → DISPUTED：申訴條件達標（持倉比例門檻、金額門檻或人工提報）或 Oracle 不一致。
  5. DISPUTED → SETTLING：合議/審核結果確定且可計算。
  6. DISPUTED → CANCELLED：可歸檔為無法裁決、或行政取消。
  7. SETTLING → SETTLED：付款與帳務一致性核對通過。

所有 transition 都需寫入 transition log，包含操作人、原因代碼、前序/後序版本與冪等鍵。

4. Oracle 提交流程（4.2）

  • 兩位以上 Oracle 遞交結果時需做一致性校驗，不一致則直接轉入 DISPUTED。
  • 每筆提交附 evidence refs 與 evidence hash，並產生不可變更的提交記錄。
  • 簽名驗證：驗證提交者身份、時間窗、來源域名、附件完整性。
  • 在前置驗證通過後，才可觸發 PENDING 公告。

5. 證據保存與稽核（4.3 / 6.3）

  • 證據採「內容＋路徑＋hash 清單」三元模型保存，支持離線核對與爭議期間再取閱。
  • 每筆裁決寫入決策摘要，含投票明細、反對意見、最終簽核者。
  • 保存層需保留 5 年，且不可被覆寫，僅能新增新版本。
  • 審核 Hash = votes JSON + decision + 版本號 + 時戳的串接雜湊。

6. 申訴入口與判定條件（5.1 / 5.2 / 5.3）

  • 申訴權限：每位持倉玩家每市場一次，需提交理由與佐證。
  • PENDING 保持到人工決定，未結算期間不得進入帳務變更。
  • 申訴門檻：固定 5%（可參數化）或大戶資產觸發的補充條件。
  • REST 介面需回傳 dispute_id、階段、處理期限、狀態。

7. 取樣與裁決（6）

  • Dispute Adjudicator 三人以上獨立裁決，2 票以上可通過。
  • 裁決結果支持：維持、轉向、作廢市場、延展審核。
  • 3-way split 時升級 compliance review，需可追溯審核原因。
  • 裁決紀錄必須可重算，對外展示最終結果與公開檢視摘要。

8. 結算執行（7）

8.1 結算前凍結

  • 進入 SETTLING 前鎖定持倉可動作；禁止並發轉移、賣出、手動干預。
  • 維持「持倉快照版本」供重試與補償使用。

8.2 結算計算

  • 以市場結果將每位持倉映射到 payout，保持與 SPEC-004 條款一致。
  • 平局/取消市場依原市場規則退還金額（保留小數規則、四捨五入策略）。
  • 所有賠付寫入帳本時先做對帳預估，再入帳。

8.3 大型批次與失敗恢復

  • 每批次處理持倉時保留批次序號與窗口 checksum，用於比對「預期總和」與「實際入帳總和」。
  • 單批失敗則回滾該批，保留已完成批次結果不變。
  • 重試節奏（次數與間隔）需參數化，並有最大重試上限與人工升級開關。

8.4 排程與 off-peak

  • 預設於 UTC 18:00~22:00（台北 02:00~06:00）排程；例外市場可延遲到下一可用窗口。
  • scheduler 層需可配置「市場鎖定」、可觀測「等待至下一窗口」的原因。

9. 取消與退還（8）

  • CANCELLED 僅允許退還原持倉價值，不能新增風險曝險。
  • 退還計算需使用持倉加權成本與小數精度，避免「整除」導致差異。
  • 手續費保留原則：一般不退，但系統故障造成錯誤取消可走例外補償流程。

10. 特殊情境與風控（9）

  • 市場關閉前撤單：持倉凍結回補到錢包（遵守 idempotent）並通知玩家。
  • Oracle 超時：公告延遲、告警、允許自動延展、超時後轉入取消。
  • 高額 payout 與異常結算需啟動 EDD 流程。
  • 平局相關：首發版維持二元市場；若已存量違規事件，交由作廢與人工流程收斂。

11. API 與推播（10）

  • 對外 API 提供:
    • 結算查詢（公開）
    • 申訴建立/查詢
    • 市場結算狀態訂閱（WS）
  • WS 訊息需支援重連後差異重放，依序列號補齊缺失事件。
  • 公開清單不包含玩家 PII，並保留不可變更的結算結果快照。

12. 監控、SLO 與告警（12）

  • 監控核心指標：Oracle 提交到 PENDING、申訴 API P99、結算完成時間、重試次數、DLQ/手動介入次數。
  • 告警等級：
    • P1：Oracle 遲滯、重試超標、單批失敗率異常
    • P0：結算結果不一致、重複入帳、不可重建的狀態轉換
  • 每次人工 resume 前必須確認「未入帳批次 checksum」與「市場版本一致」。

13. 實作檢核清單

  • 狀態機遷移測試（含非法轉換）
  • Oracle 雙簽驗證與衝突處理
  • 申訴 API 走一條龍與重放
  • 批次結算成功/失敗/重試/中斷恢復場景
  • CANCELLED 退還與手續費例外分支
  • WS gap 重連與公開 API 跨批一致性

14. 開發順序建議

  1. 先完成狀態機、資料模型版本控制與 transition log。
  2. 接 Oracle 提交、爭議裁決、DECISION 簽核。
  3. 完成結算批次執行器與批次恢復。
  4. 落地 API / WS / 告警，補上測試與演練。
