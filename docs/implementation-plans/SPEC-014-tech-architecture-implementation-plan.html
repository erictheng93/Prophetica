SPEC-014 tech architecture implementation plan

版本: v0.2.6
更新日: 2026-05-09
對應規格: SPEC-014
目標: 落實 Rust-first 架構、服務拓撲與 ADR 決議

1. 目的與邊界

  • 把架構決策（服務、執行環境、資料層、通訊）轉為可執行的實施項目。
  • 未重複描述產品行為，僅保留部署、組件、依賴與拓撲規格。

2. 技術棧硬性設定

  • 後端：Rust stable（edition 2024），Rustls 為預設，rDKafka 作 OpenSSL 例外。
  • 前端：Next.js 15 / React，Cloudflare Kumo 元件系統。
  • DB：PostgreSQL 16；Cache/Session：Redis；訊息：Kafka。
  • Observability：OTLP/OpenTelemetry，保留告警、tracing、metrics。
補充：若前端邊界跨 edge runtime，需先檢視 Node API 相容表再決定分流。

3. 服務拓撲（實作）

apps/web (Next.js SSR/RSC) ─┬─> API Gateway (axum)
                          └─> ws-gateway (wss)
API Gateway ──> auth | kyc | matching | ledger | payment | risk | settlement
所有 service 共用 PostgreSQL event/command bus / Redis / Kafka
  • 12 service crate 保留抽象邊界；deployable entrypoints 由 services/_binaries/* 承載 MVP 合併部署。
  • gRPC for internal RPC，HTTP for client-facing paths。

4. 工具鏈與 SDK

  • Cargo workspace + Rust edition 2024，`[workspace.lints]` 全域規範。
  • `forbid(unsafe_code)` + cargo-geiger gate；允許明確列白名單後例外。
  • SQL 檢核透過 sqlx prepare/check，`.sqlx` 目錄入版。
  • `crates/proto/` 統一管理 protobuf，移除舊 Go SDK 路徑。

5. 不變式

  • 所有服務間溝通遵循版本化 schema，任何 producer/consumer 變更需兼容。
  • 帳本關鍵路徑（撮合、ledger）禁止 dynamic schema fallback。
  • Rust 服務除經授權例外不得引入 unsafe。

6. 實施清單與里程碑

  1. 更新 Cargo workspace / toolchain / lints。
  2. 完成服務 container image 與 probe 設定。
  3. 完成 service 接口驗證（ADR + integration tests）。
  4. 完成可重現部署流程與 rollback runbook。
  5. 在 OQ 清單中記錄 MVP 合併部署拆回 12-binary 的切換條件與回退條件。
