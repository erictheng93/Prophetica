SPEC-022 — 登入事件情報實作計畫

版本: v0.1.2
更新日: 2026-05-17
對應規格: SPEC-022-login-event-intelligence.html v0.1.3
目標: 將登入 IP、IP 推估地點、登入裝置、登入主體覆蓋與查詢權限轉成可執行工程任務

0. 變更紀錄

  • v0.1.2：對齊 SPEC v0.1.3：新增 login_surface、principal_external_id、account_identifier_hash_key_version 與失敗登入 identifier CHECK；明確禁止把 affiliate id 塞入 risk_flags；收斂 outbox fail-open 語意。
  • v0.1.1：修正 user_id CHECK 約束，避免不可識別帳號的失敗登入無法寫入；補上 X-Real-IP 解析路徑、§5 outbox / queue 補寫要求、NFR 100ms 驗收項、UI「未知」顯示，並對齊 SPEC §15 Open Questions。
  • v0.1.0：初版實作計畫。

1. 實作邊界

  • 主要落點：services/user-service，登入成功 / 失敗事件由認證服務集中產生。
  • 入口覆蓋：apps/web、apps/admin、apps/liff 與 affiliate 後台路徑都必須接到同一份 login event contract。
  • 資料範圍：IP、可信 header 來源、IP geolocation、User-Agent 解析、principal identity、session 關聯、失敗原因與 MVP risk flags。
  • 查詢範圍：使用者安全頁最近登入紀錄、客服 / 管理員後台查詢、完整 IP 查詢 audit trail。
  • 不實作：自動封鎖、新裝置通知、完整風控分數、GPS 定位與瀏覽器 fingerprinting。

2. 核心不變式

  • INV-LOGIN-1：每個互動式登入入口都必須產生同一格式的 login_events。
  • INV-LOGIN-2：成功登入事件必須包含 principal_type 與 principal_id；一般玩家額外包含 user_id。
  • INV-LOGIN-3：登入失敗事件不得保存密碼、OTP、access token、refresh token、session secret。
  • INV-LOGIN-4：client IP 只能來自可信 proxy allowlist 或 remote address fallback。
  • INV-LOGIN-5：geolocation 與 User-Agent 解析失敗不得阻塞登入。
  • INV-LOGIN-6：完整 IP / User-Agent 查詢必須受 RBAC 控制，且需要寫入 SPEC-018 audit trail。
  • INV-LOGIN-7：UI 不得把 IP geolocation 顯示為精準位置。

3.2 login_events

CREATE TABLE login_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  login_surface TEXT NOT NULL,
  principal_type login_principal_type NOT NULL,
  principal_id UUID,
  user_id UUID,
  principal_external_id TEXT,
  account_identifier_hash TEXT,
  account_identifier_hash_key_version TEXT,
  event_type login_event_type NOT NULL,
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  ip_address INET NOT NULL,
  ip_source TEXT NOT NULL,
  geo_country TEXT,
  geo_region TEXT,
  geo_city TEXT,
  geo_latitude NUMERIC(9, 6),
  geo_longitude NUMERIC(9, 6),
  geo_source TEXT,
  geo_accuracy login_geo_accuracy NOT NULL DEFAULT 'unknown',
  asn TEXT,
  isp TEXT,
  user_agent_raw TEXT NOT NULL DEFAULT '',
  browser_name TEXT,
  browser_version TEXT,
  os_name TEXT,
  os_version TEXT,
  device_type login_device_type NOT NULL DEFAULT 'unknown',
  device_vendor TEXT,
  device_model TEXT,
  session_id UUID,
  auth_method TEXT NOT NULL,
  failure_reason TEXT,
  risk_flags JSONB NOT NULL DEFAULT '[]'::jsonb,
  request_id TEXT,
  correlation_id UUID,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  CONSTRAINT login_events_user_id_scope
    CHECK (user_id IS NULL OR principal_type = 'user'),
  CONSTRAINT login_events_success_requires_identity
    CHECK (
      event_type <> 'login_success'
      OR (
        principal_id IS NOT NULL
        AND (principal_type <> 'user' OR user_id IS NOT NULL)
      )
    ),
  CONSTRAINT login_events_failure_has_identifier
    CHECK (
      event_type <> 'login_failure'
      OR principal_id IS NOT NULL
      OR account_identifier_hash IS NOT NULL
      OR failure_reason = 'invalid_identifier'
    ),
  CONSTRAINT login_events_identifier_hash_key_version_pair
    CHECK (
      (account_identifier_hash IS NULL AND account_identifier_hash_key_version IS NULL)
      OR (account_identifier_hash IS NOT NULL AND account_identifier_hash_key_version IS NOT NULL)
    ),
  CONSTRAINT login_events_geo_source_required
    CHECK (geo_accuracy <> 'approximate' OR geo_source IS NOT NULL)
);

約束說明：

  • login_events_user_id_scope 只允許 principal_type = user 的事件帶 user_id，避免以 user_id 覆蓋 admin / manager / affiliate（SPEC §3）。
  • login_events_success_requires_identity 僅對 login_success 要求 principal_id，且玩家成功登入額外要求 user_id。失敗登入（含玩家端點輸入不存在帳號）允許 principal_id 與 user_id 為 null，改以 account_identifier_hash 關聯，對應 SPEC §2.1 / §3。
  • login_surface 由入口 / BFF 傳入，例如 user_web、admin_console、affiliate_portal、liff。未知帳號的失敗登入由此推導 attempted principal_type，避免 user-service 在無帳號 role 時全部誤歸類為 user。
  • principal_external_id 保存 affiliate account id 等非 user 業務識別；不得塞入 risk_flags。若後續需要多種外部識別，再升級為受控 metadata schema。
  • login_events_failure_has_identifier 要求 login_failure 至少能以已識別 principal 或 identifier HMAC 關聯；只有 identifier 無法標準化時才允許兩者皆空，並以 failure_reason = invalid_identifier 標記。
  • account_identifier_hash_key_version 必須與 account_identifier_hash 成對出現，支援 HMAC key rotation 與後續暴力嘗試偵測。
  • geo_accuracy 欄位 DEFAULT 'unknown' 與 SPEC §3 / login_events_geo_source_required 一致；writer 取得 provider 結果時必須明確設為 approximate 並填入 geo_source。

3.4 Retention

  • MVP 預設保留 180 天完整事件。
  • 超過保留期後，執行刪除或匿名化 job；是否匿名化需由合規決定。
  • 若事件已被 SPEC-018 evidence pack 引用，刪除前需確認 evidence retention policy。

5. Login Event Contract

pub struct LoginEventInput {
    pub login_surface: LoginSurface,
    pub principal_type: LoginPrincipalType,
    pub principal_id: Option<Uuid>,
    pub user_id: Option<Uuid>,
    pub principal_external_id: Option<String>,
    pub account_identifier_hash: Option<String>,
    pub account_identifier_hash_key_version: Option<String>,
    pub event_type: LoginEventType,
    pub ip: ClientIp,
    pub user_agent: ParsedUserAgent,
    pub geo: GeoLookupResult,
    pub session_id: Option<Uuid>,
    pub auth_method: AuthMethod,
    pub failure_reason: Option<LoginFailureReason>,
    pub risk_flags: Vec<RiskFlag>,
    pub request_id: Option<String>,
    pub correlation_id: Option<Uuid>,
}
  • login_surface 由玩家 web、admin BFF、affiliate portal、LIFF BFF 等入口明確傳入；user-service 不得在未知帳號失敗登入時只靠 credential role 推斷入口。
  • principal_type 成功登入由帳號 role 映射；未知帳號失敗登入由 login_surface 推導 attempted type。
  • affiliate 登入需以 principal_external_id 保存 affiliate account id；risk_flags 只保存風險標記，不保存 identity。
  • 登入失敗且帳號不存在時，principal_id 可為 null，但 account_identifier_hash 應填入標準化 identifier 的 HMAC，並填入 HMAC key version。HMAC key 來自 Vault / secret manager，支援 rotation；normalization 必須共用登入 identifier canonicalization。
  • identifier 無法標準化時，account_identifier_hash 可為 null，但 failure_reason 必須是 invalid_identifier。
  • writer 必須吞掉 enrichment failure，但資料庫 / outbox 寫入 failure 需打 metrics 與 error log，只記 event summary，不寫完整登入情報。

6. IP 解析實作

  1. 新增設定：USER_SERVICE_TRUSTED_PROXY_CIDRS、USER_SERVICE_IP_HEADER_MODE。
  2. 若 remote address 不在 trusted proxy CIDR，忽略 CF-Connecting-IP、X-Forwarded-For、X-Real-IP。
  3. Cloudflare mode 下優先採 CF-Connecting-IP，並記錄 ip_source = cf_connecting_ip。
  4. Proxy mode 下解析 X-Forwarded-For chain，取第一個不屬於 trusted proxy 的 IP；記錄 ip_source = x_forwarded_for。
  5. 若 reverse proxy 改寫的是 X-Real-IP（無 XFF chain），且來源在 trusted proxy CIDR 內，採用 X-Real-IP 並記錄 ip_source = x_real_ip（SPEC §4 優先序第 3）。
  6. 所有解析失敗 fallback 至 TCP remote address，記錄 ip_source = remote_addr；若仍不可得，拒絕寫入完整事件並打內部錯誤 metrics。

7. Geolocation 與 User-Agent Enrichment

7.1 Geolocation

  • MVP provider 優先順序：Cloudflare headers → MaxMind local DB → disabled fallback。
  • 外部 API provider 必須另行審核，因為會把 IP 傳給第三方。
  • Provider timeout 建議 50ms；超時後寫入 geo_accuracy = unknown。
  • 登入 hot path 如需更低延遲，可先寫入 base event，再由 async worker 補齊 geolocation。

7.2 User-Agent

  • Rust 端使用輕量 parser crate 或內部 adapter；新增依賴前需評估維護度與 license。
  • 解析失敗時保存 raw User-Agent，並將 browser / OS / device 欄位設為 unknown / null。
  • 不得基於 User-Agent 產生唯一裝置指紋。

8. 登入入口接線

入口現況線索實作要求
玩家 password loginservices/user-service/src/auth.rs 的 /api/auth/login、/v1/auth/login成功與失敗都呼叫 login event writer；入口傳入或預設 login_surface = user_web，未知帳號失敗登入映射為 attempted user。
Admin / manager / affiliate loginapps/admin/app/api/auth/login/route.ts 代理到 user-service；user-service credential 內已有 role / affiliate_idadmin app 必須轉發原始 request headers 並傳入 login_surface = admin_console 或 affiliate_portal；成功登入由 user-service 根據 role 寫入 admin、manager、affiliate，未知帳號失敗登入由 surface 推導 attempted type。
Passkey assertion/v1/auth/webauthn/assert/finish成功 assertion 產生 login_success，auth_method = passkey，並沿用同一 request 的 login_surface。
LIFFapps/liff 觸發 LINE login 後取得 identity若最後仍由 user-service 換取 session，由 user-service 記錄 login_surface = liff；若不是，需新增同 contract 的 BFF event write。
Session refresh可選若實作 refresh rotation，可寫 session_refresh；不作為 MVP blocker。

最終一致性（SPEC §5）：若某入口因架構限制無法在登入交易內同步寫入 login_events（例如 LIFF 由 BFF 換取 session），必須在同一個 durable transaction 內 enqueue transactional outbox，或透過 message queue 等價機制補寫，並保證最終可查詢；不得因 app 分離而漏記 admin / manager / affiliate 登入。outbox 補寫的事件需與同步路徑共用同一份 contract。若 login_events 與 outbox / queue 都不可用，登入流程可 fail-open，但必須記錄不含完整登入情報的 error summary、累加 login_events_write_failed_total、觸發告警，且不得標記該事件已持久化。

9. 查詢 API 與後台

9.1 API

  • GET /v1/internal/admin/login-events：管理員 / 授權客服查詢，支援 principal type、principal id、user id、IP、event type、時間窗。
  • GET /v1/users/me/login-events：一般使用者查詢自己的最近登入紀錄，只回傳遮罩 IP 與約略位置。
  • GET /v1/internal/admin/login-events/:id：完整事件詳情，需更高 RBAC，且寫入 SPEC-018 audit event。

9.2 Response policy

  • 一般使用者：遮罩 IP、約略地點、裝置類型、瀏覽器、登入時間。
  • 客服：預設遮罩 IP；必要角色才可看完整 IP。
  • 管理員 / Compliance：可看完整 IP 與 raw User-Agent，但查詢必須留痕。
  • 所有 location label 使用「根據 IP 推估」或「約略位置」。

10. 觀測與告警

  • Metrics：login_events_written_total、login_events_write_failed_total、login_geo_lookup_duration_ms、login_geo_lookup_failed_total、login_ip_spoof_header_ignored_total。
  • Structured log：僅記錄 event id、principal type、event type、ip_source、geo_source、failure class；不得寫完整 IP 與 raw User-Agent 到一般 log。
  • Alert：連續 5 分鐘事件寫入失敗率 > 1% 或 geolocation provider timeout 大幅上升。

11. 實作順序

  1. 建立 migration：enum、login_events、indexes、retention metadata。
  2. 建立 Rust domain model 與 repository，使用 sqlx::query! / query_as!，並定義 identifier normalization / HMAC key version contract。
  3. 實作 client IP resolver，先以測試鎖住 trusted proxy / spoofing 行為。
  4. 實作 User-Agent parser adapter 與 geolocation provider interface。
  5. 接入 password login success / failure，確認 user/admin/manager/affiliate role mapping、未知帳號的 login_surface 映射，以及 affiliate principal_external_id。
  6. 接入 passkey assertion success；視現有 refresh token scope 決定是否加入 session_refresh。
  7. 新增 admin/internal query API、RBAC、完整事件查詢 audit trail。
  8. 新增 web/admin UI 顯示最近登入紀錄與查詢列表。
  9. 新增 retention job 或排程任務。
  10. 補齊 metrics、alert、runbook note。

13. 任務拆分

  • Task 1 — Schema：新增 login_events migration、enum、indexes、CHECK 約束。Verify：migration test 覆蓋 login_surface 必填、失敗登入 identifier 條件、HMAC key version 成對出現、affiliate external id 欄位。
  • Task 2 — IP resolver：實作 trusted proxy allowlist 與 header parser。Verify：單元測試覆蓋 Cloudflare、XFF chain、spoofed header、remote fallback。
  • Task 3 — Enrichment：實作 UA parser 與 geolocation provider interface。Verify：parser fallback、provider timeout、disabled provider 測試。
  • Task 4 — Event writer：新增 repository / service，保證 secret 不入庫，identifier 只存 HMAC + key version。Verify：integration test 寫入成功 / 失敗事件、invalid identifier fallback、outbox / fail-open metrics。
  • Task 5 — Auth integration：接入 password / passkey login，覆蓋 user/admin/manager/affiliate。Verify：四種 role 的成功 / 失敗登入測試、未知帳號依 surface 分類、affiliate id 寫入 principal_external_id。
  • Task 6 — Query API：新增 admin 與 self query API，落實 RBAC 與 masking。Verify：authorization tests。
  • Task 7 — UI：新增使用者最近登入紀錄與後台查詢頁；地點或裝置解析失敗時顯示「未知」而非空白或錯誤（SPEC §9）。Verify：Playwright 或既有前端測試，確認約略位置文案與「未知」fallback 顯示。
  • Task 8 — Retention / observability：新增 retention job、metrics、alert。Verify：job dry-run、metrics snapshot、告警規則檢查。

14. 驗收

  1. user、admin、manager、affiliate 成功登入各產生一筆 login_success。
  2. 錯誤密碼、未知帳號、MFA / passkey 失敗會產生 login_failure，且不含 secret。
  3. 未知帳號失敗登入會保留 login_surface、attempted principal_type 與可用的 identifier HMAC / key version；identifier 無法標準化時以 failure_reason = invalid_identifier 標記。
  4. affiliate 登入事件將 affiliate account id 寫入 principal_external_id，不得寫入 risk_flags。
  5. login_events 與 outbox / queue 都不可用時，登入 fail-open 會產生 write-failure metric / alert，且不標記事件已持久化。
  6. spoofed X-Forwarded-For 在非 trusted proxy 來源下被忽略。
  7. Cloudflare header / proxy header / remote address fallback 均有測試。
  8. Geolocation provider timeout 不阻塞登入，事件仍可查詢。
  9. 完整 IP 與 raw User-Agent 只有授權角色可見，且查詢寫入 audit trail。
  10. 一般使用者頁面只顯示遮罩 IP 與「根據 IP 推估」地點。
  11. 登入事件保留期 job 可 dry-run 與實際執行，且不破壞 evidence pack 需求。
  12. 事件寫入與 geolocation 不使登入 P95 額外增加超過 100ms（SPEC §10）；第三方查詢走非同步 enrichment 時，以 base event 寫入延遲量測。
