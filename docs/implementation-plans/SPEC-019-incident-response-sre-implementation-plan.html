SPEC-019 Incident Response & SRE implementation plan

版本: v0.1.0
更新日: 2026-05-09
對應規格: SPEC-019
目標: 將事故管理與 SRE 流程落地為可執行 runbook 與交付機制

1. 事故管理基礎建設

  • 建立事故分級與處理矩陣（S0~S3）為系統共用常量。
  • 在運維入口提供事故建立 API：incident_id、severity、impact_scope、owner、eta。
  • 事故生命週期欄位：triggered、investigating、mitigating、recovered、verified、postmortem。
  • 公告內容來源使用統一模板，保證文案一致性與不可遺漏欄位。

2. 告警到工單轉接

  • 指定核心告警到事故建立器的條件：
  • 核心交易錯誤率突增。
  • 登入/下單延遲超過 95% p95 閥值。
  • 支付回傳錯誤率超門檻。
  • 不可用事件需 5 分鐘未回應自動升級。

2.1 事件抑制

  • 同源告警在 10 分鐘內降噪成 1 張事故，避免同一事件形成風暴。
  • 故障修復後 5 分鐘內自動解除靜音規則，重新進入監控。

3. 用戶公告與狀態頁實作

  • 建立通用狀態元件：站內 banner、status page、客服工單關聯。
  • 每次更新保存 immutable 狀態歷史（incident_status_history），包含最後更新時間和更新者。
  • S0/S1 事故每 15 分鐘更新一次，S2/S3 事故每 30 分鐘。
  • 事故結束後保留 24 小時可見，但不可手動刪除。

4. 應急運行手冊（Runbook）

  • 依據服務建立 4 套 runbook：交易、金流、客服、可用性。
  • 每份 runbook 包含三段流程：隔離、旁路、恢復。
  • 每段流程綁定回歸驗證（例如健康檢查、關鍵 API、DB lock 狀態）。
  • 所有 runbook 步驟引用對應 playbook checklist，並將異常直接寫入事故附件。
incident.runbook:
  id
  incident_id
  step_code
  owner
  started_at
  finished_at
  pass boolean

5. 事後復盤機制

  • 事故關閉 72 小時內必須完成 postmortem 草稿。
  • 必填欄位：根因、影響時間、影響範圍、修復時間、預防動作、回歸測試。
  • postmortem 草稿必須關聯 incident_id、告警紀錄、變更紀錄。
  • 產生 PMD（post-incident action）清單並排入下一個 sprint。

6. 交叉整合

  • 與 SPEC-007 對接指標、trace 與 alert 規則。
  • 與 SPEC-008 對接故障切換演練與 RTO/RPO。
  • 與 SPEC-013 對接 deploy rollback 與熱修補丁流程。
  • 與客服系統對接事故標籤，避免用戶重複提報同一事件。

7. 驗收清單

  1. S0 事件可 5 分鐘內建立、公告、指派。
  2. 事故更新間隔與公告欄位符合規範。
  3. runbook 可按步驟執行並回填 pass/fail。
  4. 72 小時內 postmortem 自動提醒且可提交。
  5. 事故歷史可稽核且不可被修改。
  6. 演練紀錄每季至少一次。
