SPEC-007 — 可觀測性與監控實作計畫

規格參照：SPEC-007-observability.html · 版本：v0.1.0

1. 實作目標

  • 完成 Metrics / Logging / Tracing 三柱並落地 Prometheus、OTel、Grafana 觀測。
  • 把 service-level、業務級、合規級 SLO 都標準化。
  • 定義跨 hop latency budget 與告警邏輯。

2. 不變式

  • 所有服務必有 healthz 三階端點：live/readiness/startup。
  • 所有核心告警都有對應 runbook 並可追溯。
  • 任何 SLO breach 需可自動計算 burn rate 並回報。
  • 跨服務 budget 為契約，不得未經 PR 擴張。

3. Telemetry 規格

  • Metrics：Counter / gauge / histogram，命名採 proph_{domain}_{subject}_{unit}。
  • Logging：JSON 結構化，必含 service, version, level, trace_id, event。
  • Tracing：OTel SDK with W3C traceparent，trace name 與 hop 命名對應 6.4。

4. 熱路徑 Latency Budget（實作對應）

需建立每 hop 對應 OTel attribute（如 latency.budget.order_submit_cf），並輸出實測值供告警比較：

Hop預算（P99）監測器
edge + auth約 6msapi_gateway span
wallet pre-trade約 3mswallet.reserve span
engine match2-3msengine.order.apply span
response serialize1msapi.response.serialize span

5. 告警 / Runbook

  • P0 / P1 / P2 / P3 分層，Slack、PagerDuty、Email 分流。
  • 必建 runbook 索引：ledger imbalance、engine 慢化、kafka lag、對帳失敗、WAF/網關事件。
  • 每季至少一次故障演練。

6. 工程落地清單

  • Rust 服務接入 OTEL + Prometheus registry。
  • Grafana dashboard：API、engine、wallet、settlement、compliance。
  • Prometheus 規則：P99 burn、queue lag、error rate、retry ratio。
  • AlertManager 路由與分群（prod / staging 區分）。

7. 驗收

  • Tracing 能在 1 次 user 下單中穿透主要 services。
  • 各 SLO 指標 30 天穩定可取樣。
  • P0 告警有 100% runbook 連結且可執行。
  • 跨 hop budget 告警不誤報率可接受，且可回歸。
