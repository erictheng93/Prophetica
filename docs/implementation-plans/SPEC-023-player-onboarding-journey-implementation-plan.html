1. 實作邊界

  • 主要落點：services/api-gateway（認證接縫 + 下單前置強制）、apps/web（旅程 middleware + 攔截 UX）。
  • 次要落點：services/user-service（JWKS 暴露與 me endpoint 對齊）、services/market-service（market list 透過 gateway 暴露）、services/wallet-ledger-service（餘額查詢介面確認）。
  • 覆蓋範圍：apps/web 上 landing 抵達後的全旅程；landing 變體本體（apps/landing-sports 等）只負責 CTA 跳轉，但本計畫必須驗證 CTA handoff 是否符合 SPEC-023 §4.1。LIFF 內嵌產品面不在本計畫範圍，但 LIFF → landing handoff 必須納入驗證。
  • 不實作：KYC 流程本體（SPEC-005 / SPEC-005a 已完成或另計畫）、撮合本身（SPEC-003）、真實支付通路（SPEC-016 待 LG-2）、轉換漏斗事件分類（SPEC-020）、LIFF 內嵌下單。

2. 核心不變式

  • INV-JOURNEY-1：旅程狀態（authenticated / kyc_cleared / funded / trade_ready）只能由 server 端推導，前端不得自行宣告狀態跳過攔截。
  • INV-JOURNEY-2：所有需要 caller principal 的對外 /v1/* 端點，其 principal 必須由 api-gateway 驗章後注入；gateway 必須剝除外部傳入的 x-user-id / x-principal-* header。公開唯讀端點（例如 GET /v1/markets）必須明確列入 allowlist，且不得從 client header 建立 principal。
  • INV-JOURNEY-3：下單端點（POST /v1/markets/:id/orders）對 KYC Tier < 1 或可動用餘額 < 訂單成本必須回 4xx 配合結構化錯誤碼，不得只回 500 或靜默成功。
  • INV-JOURNEY-4：return_to 只能是 same-origin 相對路徑；任何消費 return_to 的程式碼導向前必須驗證。
  • INV-JOURNEY-5：被攔截導向後完成門檻，必須導回原始意圖頁（含 query string）；多重門檻必須逐關導向，每關的 return_to 都指回最初的下單意圖頁。
  • INV-JOURNEY-6：MVP 階段（LG-2 未通過）/topup 不得渲染真實支付通路 CTA 或可送出至真實金流的金額表單。
  • INV-JOURNEY-7：visitor 對 /markets / /markets/:id 的唯讀瀏覽不得被攔截（含訂單簿與近期成交）；只有下單等需要狀態的動作觸發 §7 攔截。

3.1 現況拓撲（2026-05-19 spike 收斂）

實作 spike 結果，現行認證接縫並非 §3 描述的目標態，而是 BFF-trust transitional state：

  • apps/web/lib/auth.ts：BFF 接收 user-service 登入回應（session_token），但隨即自簽一個新的 HMAC SHA-256 token，作為 proph_session cookie；payload 只含 userId。
  • apps/web/lib/session.ts:55：upstream user-service session token 另存於 proph_user_service_session cookie（SameSite=Strict），但目前並未在呼叫 gateway 時被轉送出去。
  • apps/web/lib/engine-api.ts:127、affiliate-api.ts:147、responsible-gaming-api.ts:396：對 gateway 的 server-side call 直接送 x-user-id: <userId> header。
  • services/api-gateway/src/lib.rs 之 AuthContext：僅讀 x-user-id header，無任何 token 驗章。

後果：api-gateway 對外（player REST）若可由公網直達，任何 client 都能偽造 x-user-id。即使私網限定，這個 invariant 由 infra 維持，spec 與 code 不能獨立驗證。本 plan §5.0 Phase 0 完成後，現況收斂至 §3 目標態。

5. Phase / Task 拆分

5.0 Phase 0 — Gateway 認證接縫（SPEC-014 §6.1.2）

整條旅程的前置不變式。完成後其他 phase 才能依賴「gateway 已驗過 principal」。Phase 0 也必須先收斂 KYC tier 查詢、訂單成本公式、LG-2 開關與 E2E runner，避免後續 phase 以未定契約實作。

Task 0.0 — 登入路徑與 session / caller credential 契約收斂（spike）

現況 apps/web 同時持有 proph_session（web 自簽 HMAC UI session）與 proph_user_service_session（user-service 回傳 session token）。SPEC-023 / SPEC-014 要求 gateway 驗證 user-service 簽發的 caller credential，因此本任務必須明確決定 gateway 讀取哪個 cookie / header、web 呼叫 gateway 時如何轉送該 credential、以及 proph_session 是否只保留為 web UI session。user-service 目前同時提供 /api/auth/login 與 /v1/auth/login，本任務只需決定正式對外契約與遷移方向。

驗收

  • 決定正式登入 URL prefix：保留 /api/auth/login alias、改以 /v1/auth/login 為唯一外部契約，或以 gateway / reverse proxy 統一；決策需寫入 PR 描述或本計畫後續版本。
  • 決定 gateway caller credential 來源：優先使用 user-service JWT（現況 proph_user_service_session）或明確定義替代 introspection flow；不得把 web 自簽 proph_session 當成 gateway principal 權威。
  • 決定 apps/web server action / API client 對 gateway 的 credential forwarding 規則（Cookie 或 Authorization: Bearer），並列出受影響 helper。
  • 產出一份對齊備註（commit / PR 描述即可），不需新增 SPEC。

依賴: 無　/　規模: XS（單一 spike）　/　檔案: apps/web/lib/auth.ts, apps/web/lib/session.ts, services/user-service/src/auth.rs

Task 0.1 — user-service JWKS 公開穩定 + clock skew tolerance

確認 /.well-known/jwks.json 對 gateway 可用、key rotation 友善；JWT 驗章預留 clock skew tolerance（≤ 60s）。

驗收

  • JWKS endpoint 回傳目前簽章 key + 過去仍有效的 key（grace window）。
  • 單元測試覆蓋 key id 對照、過期 / 未來 token 拒絕、skew 容忍。

依賴: Task 0.0　/　規模: S　/　檔案: services/user-service/src/auth.rs

Task 0.2 — api-gateway 新增 auth middleware（驗 JWT）

在 services/api-gateway/src/lib.rs 新增 tower layer，於需要 principal 的對外路由前驗 caller token（cookie 或 Authorization: Bearer 擇一接受；以 Task 0.0 結論為準）。公開唯讀路由走 explicit allowlist，不建立 principal。驗章失敗回 401 + 認證類 error code。

驗收

  • 缺 token、token 過期、token 簽章錯誤、token key 未知都回 401 + 結構化 error code。
  • 合法 token 通過時放行，並把驗證結果（user_id, principal_type, principal_id, optional affiliate_id）放入 request extensions 供下游處理器使用。
  • GET /v1/markets 等公開唯讀 allowlist 路由可在無 token 時放行，但 request extensions 不得包含 principal。
  • JWKS 暫存 + refresh（避免每次請求都打 user-service）。
  • cargo test -p api-gateway 通過。

依賴: Task 0.1　/　規模: M　/　檔案: services/api-gateway/src/lib.rs, services/api-gateway/src/auth.rs（新檔）

Task 0.3 — Principal header 注入 + 外部同名 header 剝除

把目前 AuthContext 改為從 Task 0.2 注入的 request extension 讀取，不再讀 x-user-id。轉發至下游 service 前注入由 gateway 自己驗過的 x-user-id / x-principal-type / x-principal-id，並先剝除外部 client 傳入的同名 header。

順序注意：本任務的「strip 外部 x-user-id」行為一旦啟用，所有仍以裸 x-user-id 呼叫 gateway 的 caller 立即 401。因此本任務的 cutover 必須在 Task 0.7（apps/web BFF 改送 Bearer）與 Task 0.8（內部 caller transition hardening）完成之後執行，或以 feature flag 控制 strip 行為的啟用時點。

驗收

  • 外部 client 傳入 x-user-id: foo 配合合法 token → 下游收到 gateway 注入的 x-user-id（token 真正的 user id），不是 foo。
  • 合法 token + 無 client header → 下游正確收到 gateway 注入值。
  • AuthContext extractor 仍與既有 handler 簽名相容（不破壞 SPEC-014 §4 既有 handler）。
  • 單元測試覆蓋上述兩種 header 注入情境。

依賴: Task 0.2, 0.7, 0.8（cutover 順序）　/　規模: S　/　檔案: services/api-gateway/src/lib.rs, services/api-gateway/src/auth.rs

Task 0.4 — 401 / 403 結構化錯誤對齊 SPEC-014 §6.1.1

讓 gateway 自身的認證失敗（401）與授權失敗（403）使用結構化 error code（不是 500 ERROR_CODE_INTERNAL），與 §6.1.1 已存在的 REST proxy 錯誤透傳規則並行：upstream 4xx 透傳、gateway 自身前置失敗直接回。

驗收

  • 缺 token → 401 ERROR_CODE_UNAUTHENTICATED（命名可採既有 error code style）。
  • token 有效但 path 不允許該 principal type → 403 ERROR_CODE_FORBIDDEN。
  • error code 與 admin app 既有 mapping（commit 2b139d6）相容，不破壞既有錯誤訊息。

依賴: Task 0.2　/　規模: XS　/　檔案: services/api-gateway/src/lib.rs

Task 0.5 — Gateway 認證接縫整合測試（cutover gate）

新增 services/api-gateway/tests/auth_contract.rs（或同等 integration test），覆蓋：(a) 偽造 x-user-id 被剝除（無 Bearer → 401；合法 Bearer + 偽造 x-user-id → 以 token user 為準）、(b) 過期 token 被拒、(c) 簽錯 token 被拒、(d) JWKS rotation 期間舊 key 與新 key 都能驗章、(e) 不存在的 user_id 在驗章層通過但下游業務驗證可拒絕、(f) 公開唯讀 allowlist 路由可未認證取得，且偽造 principal header 不影響回應。

本任務同時作為 cutover gate：所有測試通過 → 移除 Task 0.7 transition flag → SPEC-014 §6.1.2 全面生效 → SPEC-014 §6.1.2.1 transitional note 可被標記為 historical。

驗收

  • 6 個情境均有測試且通過。
  • cargo nextest run -p api-gateway --locked 通過。
  • cutover 完成後 Task 0.7 的 transition flag 已從 codebase 移除。

依賴: Task 0.3, 0.4, 0.7, 0.8　/　規模: S　/　檔案: services/api-gateway/tests/auth_contract.rs

Task 0.7 — apps/web BFF clients 改送 Authorization: Bearer

把 apps/web 對 gateway 的 server-side calls（lib/engine-api.ts:127、lib/affiliate-api.ts:147、lib/responsible-gaming-api.ts:396 及其他經 grep 確認的呼叫點）從目前送裸 x-user-id header 改為從 proph_user_service_session 取 user-service token，送 Authorization: Bearer <token>。Task 0.0 的 forwarding contract 為依據。

此任務存在的理由：Task 0.3 一旦讓 gateway 開始 strip 外部 x-user-id，apps/web 若仍只送裸 header 而未送 Bearer，玩家所有寫操作立即 401。本任務必須在 Task 0.3 cutover 之前完成。

驗收

  • 三個（以上）BFF API client 改為從 getUpstreamSessionToken()（apps/web/lib/session.ts:66）取 token，送 Bearer；無 token 時短路回 401-equivalent，不再以 placeholder x-user-id 繞過。
  • 過渡期透過環境變數或 feature flag 控制是否同時保留 x-user-id（向後相容）；正式上線後 flag 拆除。
  • 單元 / integration tests 覆蓋：(a) 有 token → 帶 Bearer；(b) 無 token → 短路；(c) flag-on 過渡 → 兩者同送。

依賴: Task 0.0, 0.2　/　規模: M　/　檔案: apps/web/lib/engine-api.ts, apps/web/lib/affiliate-api.ts, apps/web/lib/responsible-gaming-api.ts, 其他經 grep 確認的呼叫點

Task 0.8 — 未遷移內部 caller 的 transition hardening

盤點除 apps/web BFF 以外仍以 x-user-id 呼叫 gateway 的 caller（apps/admin、service-to-service、CI / smoke test scripts、affiliate portal、未來新增之 client 等）。每一個 caller 必須走以下路徑之一：

  • (a) 同樣遷移至 Authorization: Bearer（首選）；或
  • (b) 走明確的 internal-service auth（HMAC-signed header、mTLS、或既有 services/api-gateway/src/internal_call_auth.rs 機制），不走玩家 token 路徑；或
  • (c) 列入時間有限的 allowlist（明確 path + caller + 截止日期），開 issue 追蹤遷移。

遷移完成後，gateway 不留任何「有 x-user-id 就信」的泛用路徑。

驗收

  • 每個既存 caller 都有書面紀錄走 (a)/(b)/(c) 其一。
  • (c) 路徑的 allowlist 與截止日期寫進 internal_call_auth.rs 旁的設定檔或常數，並有 unit test 驗證 allowlist 不被無聲擴張。
  • SPEC-022 §5 對 admin / manager / affiliate 登入事件覆蓋的要求不被本任務破壞。

依賴: Task 0.7　/　規模: M（盤點 + 多 caller 改造）　/　檔案: services/api-gateway/src/internal_call_auth.rs, 各 caller

Task 0.6 — Phase 2 / 3 blocker 決策收斂

在開始下單門檻與 topup UI 前，先把會影響 contract 的待決策收斂為可實作輸入。

驗收

  • 決定 KYC tier 權威端點（user-service 或 kyc-service）與 response shape；Task 2.1 不得同時讀兩個不一致來源。
  • 決定 gateway 前置檢查用的訂單成本保守公式；撮合 / ledger 仍是最終鎖定權威，但 gateway 回應需能穩定提供 required_minor_units。
  • 決定 LG-2 開關機制（環境變數、feature flag 或 release gate），Task 3.1 必須引用同一來源。
  • 決定 web journey E2E runner 與 npm script 名稱；若使用 Playwright，新增或指定實際可執行 script。

依賴: Task 0.0　/　規模: XS（contract decision）　/　檔案: PR 描述、本計畫後續版本，必要時 apps/web/package.json

Checkpoint Phase 0：執行順序為 0.0 → 0.1 → 0.2 → 0.4 → 0.7（apps/web BFF 改送 Bearer） → 0.8（內部 caller transition hardening） → 0.3（cutover strip + inject） → 0.5（attack-surface tests + 移除 transition flag）；Task 0.6 的 blocker 決策可於 Phase 0 任何時點平行收斂。手動以 curl 帶任意 x-user-id 試圖打 POST /v1/markets/:id/orders 不帶 Authorization → 收到 401；帶合法 token + 任意 x-user-id → 以 token user 為準。`cargo clippy -p api-gateway --all-targets --locked -- -D warnings` 與 nextest 全綠。

5.1 Phase 1 — Web 旅程 middleware 與 return_to 契約

Task 1.1 — apps/web middleware：session 讀取與旅程狀態

在 apps/web/middleware.ts 實作 web session cookie 讀取（依 Task 0.0 結論決定是否需要透過 gateway / user-service /v1/auth/me 取得 principal + KYC tier 摘要）；產出一個可在 server component 與 server action 共用的 getJourneyState() helper。middleware 可用 proph_session 改善 UI 導向，但任何下單與 gateway 呼叫仍須使用 Task 0.0 決定的 user-service caller credential。

驗收

  • middleware 對受保護路徑（/portfolio, /topup, /kyc/*, /account/*）在無 session 時導向 /auth/sign-in?return_to=<原路徑+query>。
  • middleware 不攔截公開路徑（/, /markets, /markets/:id, /legal/*, /support/*, /how-it-works, /auth/*）。
  • getJourneyState() 回傳 typed object：{ status: visitor|authenticated, userId?, kycTier?, balanceMinor? }。

依賴: Task 0.0, 0.6　/　規模: M　/　檔案: apps/web/middleware.ts, apps/web/lib/journey-state.ts（新檔）

Task 1.2 — return_to same-origin 強制工具

新增 apps/web/lib/safe-return-to.ts：純函式，輸入 raw query 字串、輸出安全的相對路徑或 fallback。拒絕絕對 URL（http://, https://）、協定相對（//）、跨網域或包含換行 / 控制字元的目標。

驗收

  • 純函式單元測試覆蓋：絕對 URL、protocol-relative、跨網域、CRLF injection、過長字串、合法 deep link with query。
  • pnpm --filter @prophetica/web test 通過。

依賴: 無（可平行於 1.1）　/　規模: XS　/　檔案: apps/web/lib/safe-return-to.ts, apps/web/lib/safe-return-to.test.ts

Task 1.3 — /auth/sign-in：return_to 接收與驗證

讓 apps/web/app/auth/sign-in/page.tsx 在登入 / 註冊成功後使用 Task 1.2 的 helper 解析 return_to；合法則導回該頁，否則導向 /portfolio。

驗收

  • 登入頁 query ?return_to=%2Fmarkets%2Fabc%3Fside%3Dyes → 登入後導回 /markets/abc?side=yes。
  • 登入頁 query ?return_to=https://evil.example/x → 登入後導向 /portfolio（fallback）。
  • 無 query → 登入後導向 /portfolio。

依賴: Task 1.2　/　規模: S　/　檔案: apps/web/app/auth/sign-in/page.tsx

Checkpoint Phase 1：手動深連結到 /portfolio 未登入 → 導向 /auth/sign-in?return_to=%2Fportfolio，登入後回 /portfolio。pnpm --filter @prophetica/web test 全綠。

5.2 Phase 2 — 下單前置門檻（後端強制 + 前端攔截）

Task 2.1 — gateway 下單前置強制：KYC tier ≥ TIER_1

在 POST /v1/markets/:id/orders handler 進入 matching engine 前，先呼叫 user-service / kyc-service 取得該 user 的 KYC tier。tier < TIER_1 → 回 403 ERROR_CODE_KYC_TIER_INSUFFICIENT，回應 body 包含 required_tier 與導向提示。

驗收

  • Tier 0 user 試下單 → 403 + 結構化 body。
  • Tier ≥ 1 user 通過 KYC 檢查。
  • tier 查詢失敗時不得 fail-open；回 503 配合 unavailable error code（依 §6.1.1 transport-layer 處理）。

依賴: Phase 0, Task 0.6　/　規模: M　/　檔案: services/api-gateway/src/lib.rs, 新增 KYC tier client trait + HTTP impl

Task 2.2 — gateway 下單前置強制：可動用餘額 ≥ 訂單成本

在 Task 2.1 之後、撮合引擎之前，呼叫 wallet-ledger 取得餘額，計算訂單成本（price_pts × quantity + 預估手續費上限），不足 → 回 402 ERROR_CODE_INSUFFICIENT_FUNDS。

驗收

  • 餘額不足 → 402 + body 含 available_minor_units, required_minor_units。
  • 足夠 → 通過至撮合引擎。
  • 不得在前置檢查與撮合之間有 race（鎖定額仍由 SPEC-002 ledger order_lock 處理；本步驟只做粗略門檻）。

依賴: Task 2.1, Task 0.6　/　規模: M　/　檔案: services/api-gateway/src/lib.rs

Task 2.3 — gateway 暴露 GET /v1/markets（proxy 至 market-service）

新增 gateway route GET /v1/markets（可選 status / category query），轉發至 market-service 的 /internal/markets。本端點是公開唯讀 allowlist，不需要 principal，也不得從外部 x-user-id / x-principal-* header 建立 principal。錯誤透傳依 SPEC-014 §6.1.1。

驗收

  • 合法 query 透過 gateway 取得市場列表。
  • market-service 503 → gateway 回 502 ERROR_CODE_MARKET_SERVICE_UNAVAILABLE。
  • 本端點允許未認證 caller 讀取（公開市場列表，呼應 INV-JOURNEY-7），且偽造 principal header 不影響轉發內容或下游 auth context。

依賴: Phase 0　/　規模: S　/　檔案: services/api-gateway/src/lib.rs, 新增 MarketServiceClient trait + HTTP impl

Task 2.4 — apps/web：trade panel soft check + 重新評估導向

在 apps/web/components/trade-panel.tsx 的送單 server action：

  • 送單前 soft check journey state（unauth / kyc 不足 / 餘額不足）；soft check 不通過時不打 gateway，直接導向對應頁並帶 return_to=<市場頁完整路徑+query>。
  • 送單後若 gateway 回 401 / 403 / 402，依錯誤碼導向 /auth/sign-in / /kyc/tier-1 / /topup，並帶 return_to。
  • 多重門檻：每關完成後使用者由 return_to 回到市場頁，server action 重新評估、必要時導向下一關。

驗收

  • 未登入嘗試下單 → 導向 /auth/sign-in?return_to=...。
  • Tier 0 已登入嘗試下單 → 導向 /kyc/tier-1?return_to=...。
  • 餘額不足嘗試下單 → 導向 /topup?return_to=...。
  • 同時缺 KYC 與餘額：先導向 KYC，完成後回市場頁，再次嘗試 → 導向 topup。

依賴: Task 2.1, 2.2, 1.2　/　規模: M　/　檔案: apps/web/components/trade-panel.tsx, apps/web/lib/market-api.ts

Task 2.5 — apps/web：fetchOpenMarkets 切換至 /v1/markets

把 apps/web/lib/market-api.ts 的市場列表呼叫從 market-service 直連改為 gateway 路徑。保留現有 fallback mock，但增加環境變數開關以便 E2E 切換。

驗收

  • /markets 頁通過 gateway 取得列表。
  • fallback mock 只在 gateway 不可用時觸發，不在正常路徑誘導使用者送出不存在市場的訂單（呼應 SPEC-023 NFR）。

依賴: Task 2.3　/　規模: S　/　檔案: apps/web/lib/market-api.ts

Checkpoint Phase 2：手動以 curl 直打 gateway 下單（不同身份組合）驗證 401 / 403 / 402 行為；手動於 web app 下單測試三種攔截導向均能完成並回 market 頁。cargo nextest run -p api-gateway、pnpm --filter @prophetica/web test 全綠。

5.4 Phase 4 — E2E 驗證

使用既有 e2e 工具（admin app 已有 gateway mock pattern，可借鑑；web app E2E 工具以 Task 0.6 決策為準）撰寫旅程測試。

Task 4.1 — E2E: happy path

visitor → 點 landing CTA（或直接訪 /auth/sign-in?mode=signup）→ 註冊 → 登入 → /portfolio（mock 餘額 OK + tier 1）→ 進入 /markets/:id → 下單 → 成功訊息含 order id。

驗收：測試通過；通過撮合引擎回應驗證 order_id 非空。

規模: M　/　檔案: apps/web/e2e/journey-happy-path.spec.ts（依實際 e2e 框架命名）

Task 4.2 — E2E: 未登入下單攔截

清除 cookie → 訪 /markets/:id?side=yes&qty=10 → 點下單 → 預期導向 /auth/sign-in?return_to=<完整 URL-encoded 路徑+query> → 登入 → 預期導回原市場頁含 query。

規模: S

Task 4.3 — E2E: KYC 不足攔截

登入為 Tier 0 user → 嘗試下單 → 預期導向 /kyc/tier-1?return_to=... → mock 完成 Tier 1 → 預期導回市場頁並可下單。

規模: S

Task 4.4 — E2E: 餘額不足攔截

登入為 Tier 1 + 餘額 0 user → 嘗試下單 → 預期導向 /topup?return_to=... → mock 餘額注入 → 預期導回市場頁並可下單。

規模: S

Task 4.5 — E2E: 多重門檻順序

登入為 Tier 0 + 餘額 0 → 嘗試下單 → 先導向 KYC → 完成後回市場頁 → 再導向 topup → 完成後回市場頁 → 下單成功。確認每關 return_to 都指回最初市場頁。

規模: S

Task 4.6 — E2E: 訪客唯讀瀏覽

visitor 訪 /markets, /markets/:id → 確認可看市場列表、訂單簿、近期成交、機率圖；下單按鈕點擊觸發 4.2 的攔截。

規模: S

Task 4.7 — Security E2E / 單元：open redirect 拒絕

使用 Task 1.2 helper 單元 + 一條 e2e：/auth/sign-in?return_to=https://evil.example/x → 登入後導向 /portfolio，不導向 evil 網域。再覆蓋 protocol-relative (//evil.example/x) 與 CRLF injection。

規模: XS（單元為主）

Task 4.8 — Security E2E: 後端強制（繞過前端）

直接以 curl 對 gateway 送下單（合法 token 但 KYC tier 0；或 token 缺失 + 偽造 x-user-id）→ 預期 401 / 403，且 matching engine 沒收到該 order。

規模: S　/　檔案: services/api-gateway/tests/journey_enforcement.rs

Task 4.9 — E2E: landing / LIFF handoff

從至少一個 landing 變體點主要 CTA，確認進入 /auth/sign-in?mode=signup；若 LIFF 入口已有可測路由，確認其導向 landing 而不是直接進入 web 產品面。

規模: XS　/　依賴: Task 3.3, Task 0.6

Checkpoint Phase 4：所有 Phase 4 測試通過。cargo nextest run -p api-gateway --locked、pnpm --filter @prophetica/web test、E2E 套件全綠。

7. 觀測與告警

  • Metrics：gateway_auth_validation_failed_total{reason}（缺 token / 過期 / 簽錯 / 未知 key）、gateway_principal_header_stripped_total、order_precheck_rejected_total{reason}（kyc_insufficient / insufficient_funds / unauth）、journey_redirect_total{from,to}。
  • Structured log：gateway 認證失敗只記 reason 與 request_id；不得寫 token 內容；旅程攔截導向只記 from / to / reason，不寫 user_id 之外的 PII。
  • Alert：連續 5 分鐘 gateway_auth_validation_failed_total rate 高於基線 5x（可能 token 簽章配置漂移）；gateway_principal_header_stripped_total > 0 視為潛在身份偽造嘗試，至少做 weekly trend 觀察。

8. 驗收條件

  1. 新訪客可從 /auth/sign-in?mode=signup 註冊 → 登入 → /portfolio，session cookie 設定正確。
  2. 所有需要 principal 的對外 /v1/* 端點都經過 gateway 認證 middleware；公開唯讀 allowlist 端點可未登入讀取，但偽造 x-user-id 不會被下游信任。
  3. 下單端點對 unauth / KYC tier < 1 / 餘額不足分別回 401 / 403 / 402 + 結構化 body。
  4. /markets 公開列表可透過 gateway 取得，未登入也能讀。
  5. apps/web middleware 對受保護路徑導向 /auth/sign-in 並保留 return_to；登入後導回原意圖頁。
  6. return_to same-origin 強制：跨網域、protocol-relative、CRLF 注入均拒絕。
  7. 下單流程的三種攔截（unauth / kyc / funds）E2E 均通過；多重門檻順序攔截 E2E 通過。
  8. MVP /topup 不渲染真實支付 CTA，僅顯示服務協助訊息。
  9. visitor 對 /markets / /markets/:id 唯讀瀏覽不被攔截。
  10. 至少一個 landing 變體 CTA 與 LIFF → landing handoff 已驗證符合 SPEC-023。
  11. 後端強制 E2E：繞過前端直接 curl 送 invalid 下單 → 被拒，撮合引擎未受影響。
  12. 觀測指標可在 dashboard 看到攔截與驗章失敗的趨勢。

11. 待決策

  • D-1：gateway caller credential 來源。現況 proph_session 是 web 自簽 UI session，proph_user_service_session 是 user-service session token；Task 0.0 必須決定 gateway 驗哪個 cookie / header，且不得信任 web 自簽 session 作為 principal 權威。
  • D-2：登入 URL prefix 統一決策。user-service 現況同時支援 /api/auth/login 與 /v1/auth/login；需決定正式對外契約、alias 保留期限與前端 client 是否遷移。
  • D-3：gateway 對下游注入哪些 principal header？建議至少 x-user-id、x-principal-type、x-principal-id；affiliate 是否額外注入 x-affiliate-id 需與 SPEC-011 對齊。
  • D-4：KYC tier 查詢的權威端點（user-service vs kyc-service）。Task 0.6 blocker；Task 2.1 起草前必須收斂為單一 client。
  • D-5：訂單成本估算公式（gateway 前置檢查用）。Task 0.6 blocker；撮合引擎內部仍以實際撮合鎖定為準，但 gateway 前置需有保守上界。手續費上限以 SPEC-003 為準。
  • D-6：LG-2 開關機制——是環境變數、feature flag service，還是 SPEC-013 的 release gate？Task 0.6 blocker；影響 Task 3.1 的條件渲染實作。
  • D-7：E2E 工具鏈（Playwright vs 既有 admin app 的 gateway mock pattern）。Task 0.6 blocker；決策後需新增或指定實際 npm script（例如 test:e2e:journey）。
