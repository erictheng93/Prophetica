SPEC-016 payment gateway integration implementation plan

版本: v0.1.2
更新日: 2026-05-09
對應規格: SPEC-016
目標: 固定支付 provider 介面、簽章驗證、對帳、chargeback 失敗處理與公開 Beta 前支付啟用證據

0. Public Beta / 真實入金 Gate

在 SPEC-000 §2 LG-2 與 SPEC-016 §3.2 完成前，本模組只能啟用 mock 或 sandbox payment flow，不得開放真實儲值、真實交易或對外行銷。

  • 至少一家 provider 需有 signed terms 或 LOI，明確接受 MCC / prediction-market 類業務與 chargeback 條款。
  • 需完成 sandbox webhook E2E：建立 payment intent、成功入帳、refund、chargeback / dispute created、retry 與 replay。
  • 需產出 PCI SAQ A scope note，確認卡號不進入本平台服務、log、queue 或資料庫。
  • 需完成 refund / chargeback drill log，並回填至 SPEC-000 LG-2 evidence。

1. 流程總覽

Provider Webhook -> provider driver 驗章 -> webhook queue -> idempotent handler -> trade/deposit event -> ledger posting
  • 每個 provider 採獨立 adapter，輸入驗證與 schema 映射獨立管理。
  • Webhook endpoint 只接收已驗證簽名的事件。

2. 驗收門檻

POST /api/internal/webhooks/payment/{provider}
  • 401/403：簽章失敗或重放事件拒絕。
  • 400：payload 不合法，回傳可重試建議。
  • 200：處理成功（含「already processed」）。
  • 公開 Beta 前驗收需附 provider sandbox evidence、PCI scope note 與 refund / chargeback drill log。

3. 帳本與賬戶對應

  • 收款未入帳前屬於 provider 代收，不入 `Bank.TrustAccount`。
  • 簽署 webhook 成功後先寫暫存帳戶 `Pending.Deposit.{provider}`，再依批次完成對 `Bank.TrustAccount.{token_kind}` 歸戶。
  • Chargeback 阈值與封號門檻對齊 SPEC-010 / SPEC-002（>= 1 封號）。

4. 重試與對帳

  1. Webhook 失敗時採 provider 重試；handler 必須冪等。
  2. 每日 reconciliation 檢查 event 數量與 provider 對帳檔一致；差異大於 0 進 `Suspense.Reconciliation`。
  3. 錯誤告警：差異率與重試次數超過閾值即發 P0。

5. 不變式

  • 接收 endpoint 全程 TLS1.3，拒絕明文回報。
  • 同一事件在 24h 內只可進行一次最終處理。
  • 不可在 webhook handler 直接進行長時間外部 call；僅寫入事件並排程 worker。

6. 驗收

  1. 至少一條 provider 的 end-to-end webhook 測試通過。
  2. 至少一家 provider 完成 MCC / prediction-market 接受度書面確認或 signed LOI。
  3. PCI SAQ A 邊界文件完成，且驗證本平台不接觸 PAN / CVV。
  4. 對帳缺口可追溯、能產出補帳單。
  5. chargeback 事件會連動 risk / user status 變更，且累計 chargeback >= 1 立即永久封號與黑名單。
