SPEC-008 — 災備與高可用實作計畫

規格參照：SPEC-008-disaster-recovery.html · 版本：v0.2.1

1. RTO / RPO 實作目標

  • 關鍵服務（ledger、wallet、engine）Region-local RPO = 0。
  • Cross-region RPO ≤ 5 秒（非關鍵數據可放寬）。
  • 關鍵服務 RTO：ledger/wallet < 5 分鐘；engine 市場 < 30 秒。

2. 架構

  • Primary Tokyo + DR Singapore（hot standby）。
  • PostgreSQL：Tokyo synchronous standby + Tokyo→Singapore streaming。
  • Kafka：primary topic 與 mirror 1:1 DR。
  • 撮合引擎：WAL + Kafka dual-write。

3. 不變式

  • lock 與 idempotency 不可落 Redis；須 PG 確保精準一次。
  • WAL / Kafka 中任一故障不得使系統 write without replication。
  • 失效切換後首時間軸必做一致性對帳。

4. 載入重試與客戶端 DR 容錯

  • WebSocket 500ms 起始、2x、±20% jitter、30s cap、30 次。
  • WebSocket heartbeat interval 固定 15s；missed heartbeat 需進入 reconnect flow。
  • GET retry 3 次（200ms, 400ms, 800ms）。
  • POST / PUT / DELETE 寫操作 retry 必須帶 idempotency key，重用 key。
  • Idempotency-Key 採 UUID v7，由共用 helper 產生，禁止各頁面自刻格式。
  • reconcile：per-subscription monotonic seq + 60s tail；seq gap 以 snapshot API 補洞，超過上限進 fail-soft mode。
  • fail-soft mode：顯示單一連線狀態 banner、禁用下單、保留 polling 降級與手動重試。

5. 備份

  • R2/S3 dual backup：pg_basebackup 每日、WAL archive 持續。
  • 月度 cold archive + 7 年保留。
  • 每週 restore 驗證，失敗標記 INVALID 並告警。

6. Kill switch / 多重簽核

  • 停盤 API：POST /api/internal/admin/halt。
  • 解除必須對應 SPEC-010 §9.3 MS-9 流程：2-of-3（CTO/Compliance/SE），寫 audit_logs。
  • admin / Compliance UI 不得為 MS-9 自刻簽核流程，必須使用 SPEC-010 multi-sig central component 與 approval snapshot。

7. 演練

  • 每週 engine pod kill。
  • 每月 DB failover。
  • 每季 區域切換。
  • 每年全局 DR 重建演練。

8. 驗收

  • RTO/RPO 測試通過且結果留檔。
  • failover 演練 3 分鐘內完成主通道恢復。
  • kill switch 與解除流程演練通過。
