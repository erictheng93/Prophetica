SPEC-011-affiliate-commission implementation plan

版本: v0.2.3
更新日: 2026-05-09
對應規格: SPEC-011
目標: 將推薦系統可執行細節集中於工程文件，規格維持商業語意層

1. 目的與邊界

  • 此文件專注實作細節：資料表、job、欄位、約束、批次、審計與安全閘道。
  • 僅涉及第一層推薦，不包含未授權的多層分潤功能。
  • 任何產品可讀需求仍保留於 specs/SPEC-011-affiliate-commission.html。

2. 實作對應

  • §3.1：建立推薦關係資料、狀態欄位與索引
  • §3.2/3.3：推薦碼生成、重試與親屬預檢
  • §4.1：30天觀察期裁決與發放節奏
  • §4.2：交易佣金每日批次與 staging
  • §4.6：上限與人工介入
  • §6.3：INV-6 相關 enforcement

3. 不變式（Invariants）

  • 每位被推薦人只能對應一位 referrer（UNIQUE），不可重綁。
  • 推薦關係採 first-touch：首次帶入 referral code 即為最終綁定結果。
  • 交易佣金不寫入 trade hot path；只從 commission_accruals 匯流後再發放。
  • 介紹獎勵只在 T+30 日檢核完成且無 pending review 時才可發放。
  • Player.Wallet 對現金/應付科目禁止 outflow；違規 route 全部 reject。

4. 資料模型

4.1 referrals

CREATE TABLE referrals (
  id BIGSERIAL PRIMARY KEY,
  referrer_id BIGINT NOT NULL,
  referred_id BIGINT NOT NULL UNIQUE,
  referral_code VARCHAR(32) NOT NULL,
  referred_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  observation_window_ends_at TIMESTAMPTZ NOT NULL,
  qualification_evaluated_at TIMESTAMPTZ,
  qualified_at TIMESTAMPTZ,
  status VARCHAR(32) NOT NULL,
  signup_bonus_txn_id BIGINT,
  metadata JSONB NOT NULL DEFAULT '{}'
);
CREATE INDEX idx_referrals_referrer ON referrals(referrer_id);
CREATE INDEX idx_referrals_pending_eval
  ON referrals(observation_window_ends_at)
  WHERE status = 'pending';
CREATE UNIQUE INDEX idx_referrals_code ON referrals(referral_code);

4.2 commission_accruals

CREATE TABLE commission_accruals (
  id BIGSERIAL PRIMARY KEY,
  referrer_id BIGINT NOT NULL,
  referred_id BIGINT NOT NULL,
  trade_id BIGINT NOT NULL UNIQUE,
  fee_amount BIGINT NOT NULL,
  commission_amount BIGINT NOT NULL,
  accrued_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  paid_out_txn_id BIGINT,
  period_start TIMESTAMPTZ NOT NULL,
  period_end TIMESTAMPTZ NOT NULL,
  status VARCHAR(16) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_commission_accruals_status ON commission_accruals(status);
CREATE INDEX idx_commission_accruals_referrer ON commission_accruals(referrer_id);

4.3 Audit Log 建議表（最小集合）

  • commission_rate_audit_logs：官方管理員調整比例、誰調整、時間、scope
  • affiliate_operation_audit_logs：人工 review、EDD 審核結果
  • points_adjustment_audit_logs：對審核與上限鎖定的補償/調整

5. 算法與流程

5.1 推薦碼生成與碰撞（§3.2.1）

referral_code := lowercase(blake3_6byte_hex(username)) + "_" + crockford_base32_random(4)
  1. 交易內檢查 referrals.referral_code UNIQUE
  2. 衝突時重試 5 次
  3. 仍衝突時回傳 ERROR_CODE_REFERRAL_CODE_COLLISION（需整體 rollback）

5.2 親屬偵測子規則（§3.3.1）

3.3.1 權重模型與特徵仍保留於實作，供反詐欺 score engine 取得；SPEC-011 僅要求最後結果可切到 pending_review/qualified/disqualified。
  • 建議在註冊 KYC Tier1 時計分並更新 referrals.metadata.kinship_flagged。
  • 觀察期結束前對 pending review 的紀錄保留 pending 狀態，等待 Compliance 4-eye 裁決。

5.3 介紹獎勵裁決（§4.1）

cron: affiliate-qualification-evaluator（每日 03:00，台北）

  1. 讀取到期且 status=pending 的 referrals
  2. 校驗 5 項達標條件（儲值、KYC、交易次數、chargeback、referrer 狀態）
  3. 符合者寫 status=qualified 並建立 affiliate_signup_bonus ledger transaction；不符者 status=disqualified
  4. pending_review 保持待人工裁決，不自動發放

5.4 交易佣金批次（§4.2）

事件源：trade service 發出的 trade.events

  1. accrual worker 寫入 commission_accruals（防重複：trade_id unique）
  2. cron affiliate-commission-payout（每日 03:30，台北）依 referrer 匯總 24h 未發放 rows
  3. 以 idempotency key affiliate-commission-{referrer_id}-{date} 寫入單筆 affiliate_commission txn
  4. 回寫 paid_out_txn_id 並更新 state

5.5 交易佣金上限（§4.6）

  • 月成功介紹超 20 則進入 pending_eddreview
  • 終身成功介紹超 200 則進入 pending_eddreview
  • 單月交易佣金超額（TWD 50,000）進入 pending_eddreview
  • 同 IP / device / KYC 群組按合併口徑套用同檻值

6. 帳本與簿記

6.1 方向規則對應（依 SPEC-002）

  • direction = +1：對 Expense/Asset/Player.Locked 表示增加；對 Liability/Revenue 減少
  • direction = -1：對 Expense/Asset/Player.Locked 表示減少；對 Liability/Revenue 增加

6.2 交易樣板

affiliate_signup_bonus:
  Entry 1: Expense.AffiliateCommission (+100, direction=+1)
  Entry 2: Player.Wallet.{referrer}     (-100, direction=-1)
  Entry 3: Expense.AffiliateCommission (+50, direction=+1)
  Entry 4: Player.Wallet.{referred}     (-50, direction=-1)

affiliate_commission (daily):
  Entry 1: Expense.AffiliateCommission (+X, direction=+1)
  Entry 2: Player.Wallet.{referrer}     (-X, direction=-1)

7. 風控與約束（§6.3）

7.1 INV-6 Enforcement

  • Player.Wallet 轉向白名單以 DB CHECK + constraint trigger 強制：
    • Player.Locked
    • Player.Frozen
    • Revenue.TradingFee
    • Revenue.SettlementFee
    • Player.Wallet.{other_user_id}（需 settle_txn_id）
  • 拒絕任何 Player.Wallet -> AccountsPayable / OperatingAccount / Bank / external payout 的 outflow entry
  • 出現違規 code-path 時 CI 做 sentinel-scan，阻擋合併

7.2 監控

  • 推薦碼衝突比率指標：proph_referral_code_collision_total（>1/1000 持續 1 小時告警）
  • pending_eddreview 審核超時告警（依業務 SLA）
  • 交易佣金批次延遲、重試、重放比率

8. 依賴與交叉引用

  • SPEC-010：親屬/反詐欺分數模型與 review 流程
  • SPEC-002：INV-6、ledger direction、帳目防呆
  • SPEC-014：錯誤碼定義（例如 ERROR_CODE_REFERRAL_CODE_COLLISION）
  • SPEC-016：chargeback 導致封號邏輯

9. 驗收（工程）

  1. migrations 套用並通過 schema check
  2. 推薦碼生成測試：格式、碰撞重試、錯誤碼
  3. 觀察期裁決批次與 30 天後可核發流程測試
  4. trade.events 到 payout 的端到端測試（含重放、幂等、重複 trade 防重）
  5. chargeback / kinship / 上限流程測試
  6. INV-6 觸發與 sentinel-scan 審核測試

10. 風險與遷移順序

建議順序
  1. 資料表 + index + trigger
  2. referral service + events 接收
  3. cron 與 payout worker
  4. 前端 / 後台 / 通知
  5. 跨 spec 驗收（SPEC-010/002/016）
