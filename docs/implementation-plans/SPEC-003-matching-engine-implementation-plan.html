SPEC-003-matching-engine implementation plan

版本：v0.2.3 / 對應規格：SPEC-003-matching-engine.html

目標與邊界

  • 落地撮合引擎的實作規格：資料結構、事件流、路由、執行模型、可靠性與測試。
  • 本文件是給工程實作與執行參考，不重複寫重複規格行為。
  • 與產品規格對齊：單寫者、event-sourced、價量匹配與一致性路徑。

1. 核心架構

  • Matching Engine 為 in-process 單一 writer/專屬事件處理模型。
  • 每一筆請求（下單、撤單）轉為 command，交由對應 market shard 的順序佇列。
  • 引擎為 event-sourcing：核心只輸出事件，帳本、推播、持倉由下游服務消費重建。
  • 持久化：append-only WAL（磁碟 + Kafka）+ 定期 snapshot，crash recovery 以 snapshot + replay 方式還原。

3. 匹配流程（實作）

3.1 主流程

  • 接收一筆 order 後，寫入先行事件（accepted）並進行 order type 驗證。
  • 對價位檔進行 while 迴圈撮合：檢查是否可 crossing。
  • 處理 FOK / POST_ONLY 特例：FOK 不可完全成交則回退，POST_ONLY 不可立即成交則 reject。
  • 撮合後若仍有剩餘，依 order type 決定 rest / cancel（Limit 殘餘入簿，IOC/FOK 相關部分取消）。

3.2 事件與輸出

每筆撮合輸出交易事件，包含 bid/ask maker/taker、價格、數量、sequence、時間戳與手續費標註；

Event: OrderAccepted -> Trade* -> OrderPartiallyFilled -> OrderResting/OrderFilled/OrderCancelled

3.3 交易與訂單事件

  • OrderAccepted
  • OrderRejected（POST_ONLY、FOK、invalid、notional 違規）
  • OrderPartiallyFilled / OrderFilled
  • OrderResting
  • OrderCancelled（用戶撤單、超時、IOC 殘餘）
  • MarketStatusChanged（open/closed/settling/settled）
  • BookSnapshot / BookDelta（WS 推播）

4. STP / 防刷保護

  • 對同帳號或可疑關聯的對碰，採 CANCEL_NEWEST / CANCEL_OLDEST / CANCEL_BOTH / DECREMENT_BOTH 四策略之一（預設對零售用戶 CANCEL_NEWEST）。
  • 參數與策略矩陣由配置中心供給，含違規後封鎖與告警。

5. 並發模型與執行時

5.1 Per-Market Single Writer

  • 每個市場一個 shard，接收所有該市場命令。
  • 不使用鎖競爭：單 writer 保持一致的撮合順序與 FIFO 行為。

5.2 跨市場併行

  • 不同市場可在不同 task 中平行運算。
  • 熱市場可提升資源保留（hot path）與 CPU 親和性。

5.3 效能考量

  • BTreeMap 採用 Reverse key 保留 price-time FIFO。
  • 撤單透過 OrderHandle（含價位與 queue marker）達成 O(1) 方向更新。
  • 所有價格與數值採整數（price_pts、qty、fee_bps）避免 float。

6. API / 事件介面（實作）

  • REST PlaceOrder / CancelOrder / BatchOrder / 市場查詢。
  • WS：OrderBook delta/snapshot；個人訂單 feed；seq gap 偵測機制（如發現 gap 需重同步）。
  • Order ID 使用 ULID，序列維持 per-market seq 作為撮合時序主鍵。

7. 路由與部署

7.1 hostNetwork 佈局

  • matching-engine 建議以 DaemonSet + hostNetwork 部署；避免 sidecar 造成額外 latency。
  • 市場路由由市場服務維護到 host 之對應關係。

7.2 路由決策

  • 市場創建/開盤/下單/節點異常/節點擴容皆有狀態機與 reroute 流程。
  • Hot / cold 分類每日計算，Hot markets 可獨佔資源，冷市場可 multiplex。

7.3 熱冷分流

  • 熱市場與冷市場可採不同 runtime 設定（current_thread/local/tasking / pinned / multi-thread fallback）。
  • 設定變更需記錄 governance、告警、回滾計畫。

8. 邊界條件與風險

  • 成交價區間：0~100（內部以 0.01 點位）。
  • 市場關閉後不得新進單；既有未成交單撤銷與鎖定反向處理。
  • snapshot 與 WAL 損毀時要有校驗與恢復路徑。

9. 測試與驗收（工程）

  • 單元測試：核心撮合、撤單、IOC/FOK/POST_ONLY、STP、status transitions。
  • 屬性測試：量守恆、無交叉訂單簿、seq 單調、撤單一致。
  • 重放測試：snapshot+WAL replay 的幂等與 determinism。
  • 壓測與災難回復：1M 單量測試、kill-9 恢復、disk full 行為、Kafka/網路暫時不可用恢復。
  • Mutation testing：關鍵模組定期跑 mutation，達到既定門檻。

10. 開發拆解建議

  1. 搭好 market service <-> routing 介面與指標。
  2. 實作 order book core（資料結構 + 匹配 core + STP）。
  3. 實作 command/event pipeline 與 WAL/Snapshot。
  4. 補齊 API/WS 事件轉換與客戶端 gap 回復。
  5. 佈署與 hot/cold model 與 chaos 驗證。
