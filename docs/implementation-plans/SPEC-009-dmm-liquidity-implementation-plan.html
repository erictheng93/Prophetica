SPEC-009 — DMM 計畫與流動性策略實作計畫

規格參照：SPEC-009-dmm-liquidity.html · 版本：v0.2.1

1. 實作目標

  • 完成 DMM 接口與風險治理，確保平台不持倉。
  • 上線 DMM API（TLS binary protobuf）與履約監控。
  • 建立 liquidity mining 先決條件與反洗交易機制。

2. 紅線與不變式

  • INV-DMM-1：平台、員工、受控帳戶不得直接在訂單簿掛單。
  • INV-DMM-2：任何 DMM 訂單需標記 dmm_id 並通過 per-market limit 審核。
  • INV-DMM-3：LM 需強制 KYC Tier 2+，并阻斷疑似套利 7 日內放款。
  • INV-DMM-4：冷啟動補貼 / 平台公告錢包路徑已永久移除；不得以 system.platform_announcement、uid=4 或任何平台 sentinel 送單。

3. DMM service 實作

  • 服務路徑：services/dmm-gateway。
  • 連線：Rust + tokio + tokio-rustls 的 TLS client endpoint（mTLS optional，先以 API key + token 驗證）。
  • 訊息：LOGON, NEW_ORDER, CANCEL_ORDER, MASS_CANCEL, ORDER_ACK, ORDER_FILL, ORDER_REJECT, MARKET_DATA, HEARTBEAT。
  • 每 connection 可承載 1000 ops/s。
  • 下單 flow：
  1. 驗證允許市場集合。
  2. 檢查每市場 open orders / position 限制。
  3. 標記 dmm_id 寫入 engine。
  4. 失敗回傳 DMM-specific reject code。

4. DMM 履約與治理

  • 日誌欄位：spread、depth、uptime、trade volume、rebate。
  • 超過門檻警示（spread、深度不足、在線率）-> suspend market。
  • 連續 3 個月警示者終止合作並通知 Risk 團隊。

5. Liquidity Mining

  • 啟用前提：AML/anti-fraud 穩定性、DAU、DMM 覆蓋、監管簽核。
  • reward 公式保留：貢獻度（時間×深度×反價差）。
  • 7 日確認期後發放，與洗量交易檢測掛鉤。
  • 列入黑名單設備 / IP / 交易對關係的 LP 不得參與。
  • 流動性不足時只能提高 DMM rebate 或延後市場上架，不得新增平台自營補貼。

6. 排程與報表

  • 每日出每個 DMM 的 uptime、spread、depth 報表。
  • LM 反 wash 交易檢測：同用戶短時間同合約方向對打、兩帳戶互打、共同儲值來源比對。
  • LP reward 發放可追溯至審計 ledger。

7. 驗收

  • DMM 沙盒可完成下單/撤單/接收回報。
  • 履約警示與制裁能自動發送。
  • 代碼中不得殘留平台自營造市路徑。
  • LM 未啟用條件不會進行 reward 寫入。
